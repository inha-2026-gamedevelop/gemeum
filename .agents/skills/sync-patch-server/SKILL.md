# 배포 서버 동기화

## Codex 실행 기준

- 먼저 프로젝트 루트의 `AGENTS.md`와 그 문서가 가리키는 `CLAUDE.md`를 따른다. 아래 일반 경로는 프로젝트 루트 기준이고 Markdown 링크는 이 파일 기준이다.
- 팀장 작업이면 `.claude/docs/preferences/TEAM_LEAD_MODEL_WORKFLOW.md`의 모델 분업을 적용한다. 이 스킬 자체가 직접 코딩이나 다른 모델 사용의 예외를 허용하지 않는다. 세션에서 명시된 예외는 해당 범위에만 적용한다.
- 원본의 질문 도구는 Codex의 사용 가능한 사용자 입력 도구로 대응한다. 선택·명확화에는 `request_user_input_async` 또는 제공된 `request_user_input`을 쓰되 현재 도구 제약을 따른다. 승인이 필요한 질문은 승인 요청을 지원하는 채널로 하고, 답변을 받기 전 의존 작업을 실행하지 않는다. 해당 도구가 없으면 일반 대화로 질문한다.
- 기존 대화의 승인과 사용자 지시를 우선한다. 이미 결정된 내용을 재확인하지 않는다. 확인이 필요하면 초안·근거를 먼저 준비하고 이 SKILL.md의 적용 조항을 링크해 이유를 설명한다.
- 읽기는 사용 가능한 파일/셸 도구, 편집은 패치 도구, 명령 실행은 셸 도구를 사용한다. 존재하지 않는 Claude 전용 도구를 호출했다고 주장하지 않는다.

## 적용 범위

게임·런처 배포 또는 버전 비교에 사용한다. API 코드 배포, DB 변경, 인프라 증설은 이 스킬로 자동 확대하지 않는다. “확인만”은 조회로 끝낸다. 기준은 실제 `launcher/scripts/sync-server.ps1`, `launcher/Launcher.UI/launcher-config.json`, 최신 인수인계이며 오래된 PC 서버 설명보다 현재 설정을 우선한다.

## 먼저 확인할 것

1. 프로젝트 루트를 확인하고 그 위치에서 `launcher/scripts/sync-server.ps1 -Check`를 실행한다. 셸 명령은 현재 OS에 맞게 호출한다.
2. 게임은 `Builds/Development/gemeum_Data/StreamingAssets/build-identity.json`의 releaseId, 런처는 csproj Version, 사람용 게임 번호는 `Builds/test-version.json`과 manifest displayVersion을 대조한다. `Builds/PatchRepo`는 로컬 게시 저장소이므로 원격 반영 증거와 구별한다.
3. 실제 원격 채널 envelope와 launcher/latest.json을 확인한다. 스크립트는 배포 baseUrl이 R2 설정과 일치하거나 `-Upload`가 지정되면 R2 업로드 경로를 사용한다. 키·토큰·서명 개인키를 출력하지 않는다.
4. 현재 자동화 또는 다른 게시가 실행 중인지 확인한다. 파일 잠금이면 그 작업이 끝나기 전에 중복 게시하지 않는다.

## 판단과 실행

| 상태 | 처리 |
|---|---|
| 요청 범위의 로컬/원격 버전과 내용이 같음 | 재게시 없이 결과 보고 |
| 새 게임 빌드가 존재하고 게시 요청됨 | 게임 게시. 런처도 요청 범위에 있으면 필요한 변경만 함께 게시 |
| 런처 코드 변경·버전 동일 | `-BumpLauncher`로 패치 버전 올려 게시. 큰 버전 변경은 사용자가 지정한 정책 적용 |
| 로컬이 원격보다 오래됨 | 롤백 의도가 명시되지 않았다면 멈추고 확인. 의도 확인 후에만 `-Force` |
| 게임 빌드 없음 | 빌드까지 요청·승인된 경우 기존 빌드 절차로 진행. 배포만 요청됐다면 누락 사실과 필요한 빌드를 알림 |
| 원격 응답 없음/내용 불일치 | URL·모드·서명·전송 결과를 조사. 로컬 패키징 완료를 원격 배포 성공으로 보고하지 않기 |

실행할 때 프로젝트 루트 기준으로 다음 기존 명령 중 요청 범위를 선택한다.

- `launcher/scripts/sync-server.ps1 -Only game`: 게임만
- `launcher/scripts/sync-server.ps1 -Only launcher -BumpLauncher`: 런처 변경만
- `launcher/scripts/sync-server.ps1 -BumpLauncher`: 둘 다 필요한 경우
- `-Version`: 사용자가 별도 게임 테스트 번호를 지정한 경우
- `-Notes`: UTF-8 패치 노트 파일을 준비한 경우

명령 실행 전 현재 스크립트 인자를 읽는다. 배포 요청에 이미 포함된 정상 게시를 다시 승인받지 않는다. 테스트 버전은 기본적으로 새 빌드마다 증가하며 멀티플레이 호환 판정은 releaseId다. dirty 빌드·HEAD 불일치는 소스 상태와 함께 보고한다. 패치 노트를 자동 생성했다면 실제 내용이 미커밋 변경까지 설명하는지 확인한다.

R2 모드에서는 실제 업로드와 원격 서명 검증까지 끝내야 한다. 로컬 serve-repo 모드에서만 PC 서버 실행 상태를 확인한다. R2 장애를 해결하려고 임의로 로컬 서버로 전환하거나 baseUrl을 변경하지 않는다.

## 계정 API와 게임 빌드 일치

자체 계정 배포에서는 원격 게임 releaseId와 AWS API의 `GEUMEUM_GAME_BUILD_ID`가 다르면 원정대 입장이 거절될 수 있다. 최신 운영 인수인계에서 대상·접속·가드 절차를 확인한다. 인증 정보 자체를 문서나 출력에 복사하지 않는다.

- 게임 게시 작업에 허용 빌드 동기화가 포함돼 있으면 기존 절차로 값 하나만 맞춘다. 런처만 게시할 때는 게임 허용 빌드를 변경하지 않는다.
- 현재 릴레이는 API 프로세스에 연결돼 있어 API 재시작 시 진행 방이 종료된다. 기존 가드로 활성 방0을 확인하고 설정 백업을 남긴 뒤 변경한다. 활성 방이 있으면 재시작하지 않고 배포 상태와 대기 사유를 보고한다.
- API 허용 빌드 확인 또는 변경에 필요한 접속이 없으면 게임 게시 상태와 서버 동기화 미완료를 분리해 보고한다. 인증 성공을 추정하지 않는다.

## 완료 확인

1. 스크립트 종료 코드와 업로드·서명 검증 결과를 확인한다. 긴 실행은 세션으로 추적하고 진행 상황을 알린다.
2. `-Check` 및 원격 메타데이터로 **요청된 대상**이 일치하는지 확인한다. 변경하지 않은 대상의 기존 차이는 별도로 보고한다.
3. `Builds/publish-history.md` 게시 기록을 확인한다. 필요할 때 실제 공개 exe/DLL 해시를 로컬 산출물과 비교한다.
4. API 설정을 변경했다면 HTTPS ready와 릴레이 리스닝을 검증한다. 게시 성공과 실제 사용자 설치·게임 접속 검증은 분리한다.

## 금지와 보고

채널 sequence·manifest·서명 파일을 손으로 고치지 않는다. 개인키를 이동/출력하지 않는다. 서버 재시작, Discord 공지, 커밋·푸시를 배포 요청에 임의 추가하지 않는다. 실패 후 현재 원격 버전을 먼저 확인하고 복구에 필요한 대상만 재시도한다. 원인 미해결 상태에서 무한 재게시하지 않는다.

최종 보고에는 게임 테스트 버전/releaseId/seq, 런처 버전, 게시 대상, 패치 노트 요약, 원격 검증 결과, API 버전 일치 여부(게임 배포 시), 사용자 업데이트 방법과 미검증 범위를 적는다.

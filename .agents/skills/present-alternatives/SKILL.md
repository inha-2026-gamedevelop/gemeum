# 대안 제시

## Codex 실행 기준

- 먼저 프로젝트 루트의 `AGENTS.md`와 그 문서가 가리키는 `CLAUDE.md`를 따른다. 아래 일반 경로는 프로젝트 루트 기준이고 Markdown 링크는 이 파일 기준이다.
- 팀장 작업이면 `.claude/docs/preferences/TEAM_LEAD_MODEL_WORKFLOW.md`의 모델 분업을 적용한다. 이 스킬 자체가 직접 코딩이나 다른 모델 사용의 예외를 허용하지 않는다. 세션에서 명시된 예외는 해당 범위에만 적용한다.
- 원본의 질문 도구는 Codex의 사용 가능한 사용자 입력 도구로 대응한다. 선택·명확화에는 `request_user_input_async` 또는 제공된 `request_user_input`을 쓰되 현재 도구 제약을 따른다. 승인이 필요한 질문은 승인 요청을 지원하는 채널로 하고, 답변을 받기 전 의존 작업을 실행하지 않는다. 해당 도구가 없으면 일반 대화로 질문한다.
- 기존 대화의 승인과 사용자 지시를 우선한다. 이미 결정된 내용을 재확인하지 않는다. 확인이 필요하면 초안·근거를 먼저 준비하고 이 SKILL.md의 적용 조항을 링크해 이유를 설명한다.
- 읽기는 사용 가능한 파일/셸 도구, 편집은 패치 도구, 명령 실행은 셸 도구를 사용한다. 존재하지 않는 Claude 전용 도구를 호출했다고 주장하지 않는다.

## 언제 발동하나

구현 방식이 하나로 정해지지 않고, 실질적인 트레이드오프가 있는 대안이 2개 이상 있을 때 발동한다.

- 사용자가 직접 "어떤 방법이 있어?", "장단점 비교해줘", "이거 어떻게 구현하는 게 나아?" 라고 물을 때
- 기능을 구현하다가 갈림길을 만났고, 각 갈림길이 서로 다른 성능·복잡도·유지보수 특성을 가질 때
- 아키텍처, 라이브러리, 동기화 전략(서버 권위 vs 클라 예측), 데이터 구조, 자료 저장 방식 등 나중에 되돌리기 비용이 있는 결정을 앞두고 있을 때

**반대로 다음은 대상이 아니다:**
- 정답이 사실상 하나뿐이거나, `docs/coding-convention.md` 같은 컨벤션 문서를 보면 답이 정해지는 경우 — 바로 실행한다
- 순수하게 사용자 취향/선호로만 갈리는 선택(예: 폴더명, 브랜치명) — 대안 분석보다 [clarify-ambiguous-request](../clarify-ambiguous-request/SKILL.md)로 바로 질문하는 편이 낫다
- 대안이 3개 넘게 억지로 만들어질 만큼 사소한 결정 — 과잉 분석하지 않는다

## 방법

1. **먼저 이 프로젝트의 실제 제약을 읽는다.** `CLAUDE.md`(스코프 잠금, 검증 프로필, 네트워크 권위 판단 기준), 관련 기술/게임 디자인 문서, 일정(2026.08.30–11.16, 3인 전원 프로그래머)을 확인한다. 트레이드오프는 교과서 일반론이 아니라 이 프로젝트 조건에 비춰 평가한다.
2. **진짜 후보만 추린다.** 실무에서 고려할 가치가 없는 대안은 나열하지 않는다. 보통 2~4개면 충분하다 — 선택지가 많다고 더 도움이 되지 않는다.
3. **대안마다 같은 틀로 설명한다:**
   - 한두 줄 요약 (무엇을 하는 방식인지)
   - 장점
   - 단점 / 리스크
   - 이 프로젝트 조건에서의 영향 (예: 일정에 미치는 영향, 네트워크 권위 경계와의 충돌 여부, 팀 전원 프로그래머라 인력 문제는 없는지, 스코프 잠금 항목과 충돌하는지)
4. **하나를 명시적으로 권장한다.** "정답은 없다"로 끝내지 않는다. 권장안과 그 이유를 이 프로젝트 조건에 근거해 분명히 말한다. 근거가 약하면 권장을 보류하고 왜 판단하기 어려운지 설명한다 — 없는 확신을 지어내지 않는다.
5. **최종 선택이 사용자의 몫으로 남는 경우**(취향, 팀 합의가 필요한 스코프 확장 등)에는 이 분석을 바탕으로 [clarify-ambiguous-request](../clarify-ambiguous-request/SKILL.md)의 Codex 사용자 입력 단계로 넘긴다 — 분석글만 던지고 끝내지 않는다.
6. 사용자가 하나를 고르면 그 결정을 근거로 계속 진행하고, 같은 사안을 다시 묻지 않는다.

## 예시

```
사용자: "결계(경기장) 축소를 어떻게 서버-클라 동기화할까?"

❌ 서버 권위/클라 예측 두 방식을 교과서적으로 설명만 하고 끝
✅ NETWORK_AUTHORITY.md의 판단 기준("사람마다 다르면 서버")과
   결계 반경이 이미 서버 값 하나로 정의된 것을 확인
   → "서버가 반경 값만 브로드캐스트, 클라가 셰이더/파티클로 표현"과
     "서버가 매 프레임 콜라이더까지 동기화"를 비교
   → 전자를 권장: 후자는 대역폭 낭비이고 3.2절 파생 계산 원칙과도 맞지 않음
```

# 가이드 이슈 등록

## Codex 실행 기준

- 먼저 프로젝트 루트의 `AGENTS.md`와 그 문서가 가리키는 `CLAUDE.md`를 따른다. 아래 일반 경로는 프로젝트 루트 기준이고 Markdown 링크는 이 파일 기준이다.
- 팀장 작업이면 `.claude/docs/preferences/TEAM_LEAD_MODEL_WORKFLOW.md`의 모델 분업을 적용한다. 이 스킬 자체가 직접 코딩이나 다른 모델 사용의 예외를 허용하지 않는다. 세션에서 명시된 예외는 해당 범위에만 적용한다.
- 원본의 질문 도구는 Codex의 사용 가능한 사용자 입력 도구로 대응한다. 선택·명확화에는 `request_user_input_async` 또는 제공된 `request_user_input`을 쓰되 현재 도구 제약을 따른다. 승인이 필요한 질문은 승인 요청을 지원하는 채널로 하고, 답변을 받기 전 의존 작업을 실행하지 않는다. 해당 도구가 없으면 일반 대화로 질문한다.
- 기존 대화의 승인과 사용자 지시를 우선한다. 이미 결정된 내용을 재확인하지 않는다. 확인이 필요하면 초안·근거를 먼저 준비하고 이 SKILL.md의 적용 조항을 링크해 이유를 설명한다.
- 읽기는 사용 가능한 파일/셸 도구, 편집은 패치 도구, 명령 실행은 셸 도구를 사용한다. 존재하지 않는 Claude 전용 도구를 호출했다고 주장하지 않는다.

## 언제 발동하나

사용자가 지금 이야기한 문제나 작업을 GitHub 이슈로 남기고 싶다는 의사를 밝히면 발동한다.
예: "이슈 올려줘", "이슈로 등록해줘", "버그 이슈 만들어줘", "이거 이슈로 남겨두자".

**바로 `gh issue create`를 실행하지 않는다** — 아래 절차를 먼저 거친다.
이미 이 절차로 본문을 확정한 뒤 "그대로 올려"라고 재요청하는 경우는 재점검 없이 실행한다.

## 절차

### 1. 템플릿을 고르고 매번 읽는다

`.github/ISSUE_TEMPLATE/`를 열어 무엇이 있는지 확인하고, 등록할 내용에 맞는 것을 고른다.

| 무엇을 남기나 | 템플릿 | 제목 접두어 | 라벨 |
|---|---|---|---|
| 아직 안 만든 개발 작업 | `01-task.yml` | `[작업] ` | `task` |
| 동작하지 않는 것 | `02-bug.yml` | `[버그] ` | `bug` |
| 수치 조정 제안 | `03-balance.yml` | `[밸런스] ` | `balance` |

- **제목 접두어와 라벨은 템플릿 파일에 적힌 값을 그대로 쓴다.** 기억으로 재구성하지 않는다.
  템플릿이 바뀌었으면 바뀐 쪽을 따른다.
- 템플릿은 YAML 폼이라 `gh issue create`로는 폼을 채울 수 없다.
  **각 필드의 `label`을 그대로 Markdown 제목(`### 라벨명`)으로 옮겨 본문을 만든다.** 섹션을 빼거나 순서를 바꾸지 않는다.
- `dropdown`은 고른 값 한 줄로, `checkboxes`는 `- [ ]` / `- [x]` 목록으로 적는다.
- 어느 템플릿에도 맞지 않으면 사용자에게 어느 쪽으로 낼지 묻는다. 임의로 새 형식을 만들지 않는다.

### 2. 같은 이슈가 이미 있는지 본다

```bash
gh issue list --state all --search "핵심 키워드"
```

- 같은 증상이 이미 있으면 **새로 만들지 않고** 그 번호를 사용자에게 보여주고 댓글로 덧붙일지 묻는다.
- 닫힌 이슈에 같은 증상이 있으면 재발인지 확인한다. 재발이면 새 이슈에 그 번호를 참조로 적는다.

### 3. 사실만 모은다 — 추측으로 채우지 않는다

이슈는 다른 사람이 그것만 읽고 착수하는 문서다. 틀린 단정 하나가 남의 반나절을 쓴다.

- **재현 순서는 실제로 관찰한 순서로 적는다.** 몇 명으로, 어느 씬에서, 무엇을 했을 때인지.
  사용자가 말한 것을 그대로 쓰고, 빠진 단계는 지어내지 않고 사용자에게 묻는다.
- **모르는 항목은 비운다.** 특히 버그 템플릿의 `네트워크 관련`(호스트만/클라만/양쪽/단일 플레이)은
  확인되지 않았으면 체크하지 않고, 그 아래에 "아직 확인되지 않았다, 다음 재현 때 먼저 채운다"를 적는다.
- **심각도는 증상으로 정한다.** 크래시·진행 불가면 `치명`, 핵심 기능이 틀리게 동작하면 `높음`,
  우회 가능하면 `보통`, 보이기만 이상하면 `낮음`.
- 원인을 아직 모르면 "원인 미확인"이라고 쓴다. 의심 지점이 있으면 **의심이라고 표시하고** 파일·메서드까지 적는다.
- 이미 확인한 것과 확인하지 못한 것을 나눠 적는다. 받는 사람이 어디서부터 이어받을지 알 수 있어야 한다.

### 4. 버그면 로그를 실제로 찾아본다

"로그 없음"이라고 쓰기 전에 아래를 직접 확인하고, **찾아본 곳과 결과를 본문에 남긴다.**

| 어디 | 무엇 |
|---|---|
| `%USERPROFILE%\AppData\LocalLow\DefaultCompany\gemeum\Player.log` | 빌드 실행 로그. 직전 실행은 `Player-prev.log` |
| `%USERPROFILE%\AppData\Local\Temp\DefaultCompany\gemeum\Crashes\` | 크래시 덤프(`crash.dmp` + `error.log`) |
| `Builds/*/logs/` | 실행 스크립트가 남긴 로그 |
| `%USERPROFILE%\AppData\Local\Unity\Editor\Editor.log` | 에디터에서 재현했다면 |

- 로그가 있으면 **꼬리에서 관련 구간만** 잘라 `콘솔 로그` 섹션에 넣는다. 수백 줄을 통째로 붙이지 않는다.
- 없으면 없다고 쓰고, **다음 재현 때 어디서 무엇을 가져오면 되는지** 경로를 적어 둔다.
  3인 테스트는 PC마다 로그가 따로 남으므로 어느 PC의 것인지도 함께 적는다.
- 크래시 난 쪽이 호스트인지 클라이언트인지는 로그가 없으면 알 수 없다. 모르면 모른다고 쓴다.

### 5. 라벨 · 담당자 · 마일스톤

- **라벨은 템플릿에 적힌 것만 붙인다.** 없는 라벨을 새로 만들지 않는다.
  붙이려는 라벨이 저장소에 있는지 `gh label list`로 확인한다.
- **담당자는 원인이 어느 파트인지 확정됐을 때만 지정한다.**
  `.github/CODEOWNERS`에서 관련 경로의 소유자를 찾아 사용자에게 확인하고 붙인다.
  원인 파트가 아직 불확실하면 **비워 둔다** — 엉뚱한 사람에게 배정하면 그 사람이 확인하는 시간만 쓴다.
- 작업 템플릿의 `마일스톤`은 일정 판단이다. **임의로 고르지 않고 사용자에게 묻는다.**
- 관련 PR·커밋·다른 이슈가 있으면 본문 끝에 번호로 연결한다. **번호를 지어내지 않는다.**

### 6. 사용자 확인 후 생성

- `gh issue create`를 실행하기 전에 **제목과 본문 전체, 라벨과 담당자를 함께 보여주고 확인받는다.**
- 본문은 스크래치패드의 임시 파일로 넘긴다. 저장소 안에 임시 파일을 만들지 않고, 생성 후 남기지 않는다.

```bash
gh issue create --title "[버그] ..." --label bug \
  --body-file {스크래치패드 임시파일}
```

- `gh`가 없거나 인증되지 않았으면 본문을 그대로 출력하고, 사용자가 웹에서 붙여넣을 수 있게 안내한다.
- 생성 후 이슈 URL을 보고한다.

### 7. 이슈를 만든 뒤에 할 것

- 진행 중인 PR의 `남은 것 / 알려진 문제`에 해당 내용이 있으면 **이슈 번호를 그쪽에도 적는다.**
  PR 본문과 이슈가 서로를 가리켜야 나중에 이력을 따라갈 수 있다.
- 다른 파트가 받아야 할 일이면 이슈만 남기지 말고 전달 문서(`guided-commit` 7절)도 함께 만들지 사용자에게 묻는다.
  이슈는 저장소에 남는 기록이고, 전달 문서는 상대에게 복사해 건네는 자립 문서다.
- 세션을 여기서 끊는다면 인수인계(`write-handoff`)에 이슈 번호를 남긴다.

## 하지 않는 것

- 사용자 확인 없이 `gh issue create` 실행
- 템플릿 섹션을 임의로 빼거나 순서를 바꾸기
- 확인하지 않은 항목을 채우거나 체크하기 — 특히 버그의 `네트워크 관련`과 심각도
- 로그를 찾아보지 않고 "로그 없음"이라고 쓰기
- 원인이 불확실한데 특정 파트 담당자를 배정하기
- 없는 라벨·마일스톤을 새로 만들기
- 이슈 번호·PR 번호를 추측해서 적기
- 이미 같은 이슈가 있는데 중복으로 만들기
- 이슈 본문에 `Co-Authored-By`나 AI 생성 표기 넣기

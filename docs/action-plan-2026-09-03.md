## 0. 한 줄 진단

**지금 이 게임은 끝에서 끝까지 돌지 않는다.** 아키텍처는 건강하고 코드 품질도 좋지만, 서로 다른 다섯 영역에 치명급 결함이 하나씩 박혀 있어 코어 루프의 각 단계가 각각 끊겨 있다.

|---|---|---|---|
| P0-1 | 모든 공격이 항상 월드 +Z로 나간다 | **전투 자체** | 몇 줄 |

## 1. P0 — 지금 즉시

### P0-1. 모든 공격이 월드 +Z로 나간다 (치명)

**위치:** `Assets/01.Scripts/02.Combat/Player/PlayerAttack.cs` — `ApplyMeleeHit`, `FireArrow`

**무엇이 잘못됐나:** 서버가 조준 방향을 `transform.forward`로 읽는데, 이 프로젝트의 플레이어 루트 Transform은 **한 번도 회전하지 않는다.**

| 근거 | 확인 |
|---|---|
| `Player.prefab:268` — `m_Constraints: 112` | FreezeRotation X·Y·Z. 물리로도 안 돈다 |
| `02.Combat`·`01.Network` 전체 | 루트 회전 코드 0건 |
| `PlayerAnimationController.cs:115-125` | 방향은 자식 `VisualPivot`의 `localRotation`에만 적용 |

**실패 시나리오:** 캐릭터가 남쪽 잡귀를 향해 검을 휘두른다. 서버는 `Dot(+Z, 대상방향) >= cos(45°)`를 검사하므로 **눈앞의 적은 안 맞고 등 뒤 적이 맞는다.** 신궁은 어디를 조준하든 화살이 항상 같은 월드 방향으로 날아가고, 총구 오프셋이 캐릭터 등 뒤에 생길 수 있다.

`PLAYER_ATTACK_DESIGN.md` 6장의 "L2 근접 통과 — 잡귀 HP 250 → 240" 관측은 **그 잡귀가 우연히 +Z에 있었던 것**으로 판단한다.

**결정 — 서버 권위 값인 `PlayerPresentation.FacingDirection`을 쓴다.**

```csharp
// Awake에서 _presentation 캐시 후, ApplyMeleeHit·FireArrow 양쪽에서
Vector2 facing  = _presentation.FacingDirection;   // 서버는 _serverFacing
Vector3 forward = new Vector3(facing.x, 0f, facing.y);
```

`PlayerController` 권위 틱이 매 틱 `ServerSetMotion`으로 확정하는 서버 값이므로 권위 경계는 그대로다. 클라이언트가 방향을 보내지 않는 원칙도 유지된다.

**완료 기준:** `Dev_Combat`에서 사방(동·서·남·북)의 잡귀를 각 3회씩 근접·원거리로 공격해 **전부 명중**. 등 뒤 적이 맞는 경우 0회.

**함께 고칠 문서:** `PLAYER_ATTACK_DESIGN.md` 2장 권위 표·4장·5.3·5.4의 `transform.forward` 서술.

### P0-2. 잡귀 공격에 사거리 재검사가 없다 (치명)

**위치:** `Assets/01.Scripts/03.AI/Enemy/EnemyController.cs:242-262` (`ExecuteAttack`)

**무엇이 잘못됐나:** `damageable.TakeDamage(...)`를 거리 검사 없이 호출한다. Brain은 선딜 진입 시점의 거리만 보고, 선딜 중 이탈은 의도적으로 무시한다.

**실패 시나리오:** 허깨비가 사거리 안에서 `Windup`에 들어간 뒤 플레이어가 0.65초 동안 20m를 달아나도, 어그로가 유지되는 한 **원거리에서 피해가 그대로 들어간다.** 창귀는 돌진이 NavMesh 장애물에 막혀 제자리에 있어도 타이머만 지나면 명중한다.

즉 **회피라는 행동이 게임에 존재하지 않는다.** 구르기 무적 0.45초로만 피할 수 있고, 거리를 벌리는 것은 무의미하다. 3인이 패링과 회피를 배울 수 없다.

**결정 — `ExecuteAttack`에서 impact 시점 거리를 다시 검사한다.**

```csharp
float reach = (_status.Kind == EnemyKind.Changgwi) ? _status.ChargeHitRadius : _status.AttackRange;
if (Vector3.Distance(transform.position, target.position) > reach) { return; }   // 피해 없음
```

데이터는 이미 `EnemyStatus`에 있다. `MONSTER_PARRY_LINK_DESIGN.md` 5.2-4가 요구하는 것과 같은 규칙이다.

**완료 기준:** 허깨비 선딜 중 사거리 밖으로 이탈 10회 → 피해 0회. 사거리 안 유지 10회 → 피해 10회.

### P0-3. 창귀 패링 창이 등록되지 않는다 (치명)

**위치:** `Assets/01.Scripts/03.AI/Enemy/ChanggwiBrain.cs:133-142`, `258-262`

**무엇이 잘못됐나:** `IParryWindowTarget.OpenParryWindow`의 실제 호출자는 `ParryTestDummy.cs:79` **하나뿐이다.** `ChanggwiBrain.OnParried`는 어떤 경로로도 호출되지 않는 죽은 코드다.

**즉 지금 어떤 플레이어도 창귀를 패링할 수 없다.** 프로젝트의 시그니처 메커닉이자 팀장 핵심 기술의 유일한 실전 대상이 연결되어 있지 않다.

**좋은 소식 — 선행 조건은 대부분 이미 해소됐다.**

| 설계서가 선행으로 잡은 것 | 실제 상태 |
|---|---|
| 패링 P0 게이트 (단일 활성 window, tombstone 분리, 수신 마감, 복합 키) | **구현됨** — 체크리스트 13개 중 11개 통과 |
| `EnemySO`의 창귀 수치 입력 | **완료** — Aggro 9 / Attack 6 / Windup 1.5 / ChargeSpeed 9 / ChargeDistance 7 / **ParryWindow 0.32** |
| 최소 텔레그래프 조건 `Windup + Charge/Speed >= Window + 0.18` | **통과** (2.28 ≥ 0.66) |
| `IParryWindowTarget` 인터페이스 | **존재** — `ParryController`가 구현 중 |

`PARRY_SYSTEM_DESIGN.md` 7.2와 `MONSTER_PARRY_LINK_DESIGN.md` 6장이 선행으로 잡아둔 "P0 게이트 8~12시간 + 창귀 데이터 2~3시간"은 **이미 지나갔다.**

**결정 — `MONSTER_PARRY_LINK_DESIGN.md` 6장의 3단계부터 착수한다.** 필요한 신규 산출물은 넷이다.

| 산출물 | 위치 | 역할 |
|---|---|---|
| `ChanggwiAttackExecution` | `03.AI/Enemy/` | 공격 1회의 key·정규화 target·절대 시각·취소/impact 플래그 snapshot. `IParryable` 구현체 |
| `AttackTelegraphCue` / `AttackTelegraphEndReason` | `00.Common/Types/` | 텔레그래프 RPC 값 계약 |
| `IAttackTelegraphView` | `00.Common/Interfaces/` | 표현 경계 |
| `ChanggwiTelegraphView` | `05.Art/Enemy/` | 바닥 돌진선·발광·소리 (애니메이션 없이도 읽히는 최소 표현) |

**장수명 `ChanggwiBrain`을 `IParryable` source로 쓰지 않는다** — `OnParried(uint)`에 key가 없어 이전 공격의 늦은 콜백을 구별할 수 없다. 실행 단위 객체가 이 모호성을 없앤다.

**완료 기준 (M2, 3인):** 검 유저 20회 패링 시도에서 성공 시 피해 0 · `Stagger` 진입 · 게이지 정확히 1회 증가. 활·방울 대상에는 window가 열리지 않음. 세 화면의 돌진 방향·종료 사유 일치.

### P0-4. 두 번째 로비에서 아무도 움직이지 못한다 (치명)

**위치:** `Assets/01.Scripts/01.Network/RunManager.cs:264-291` (`ServerReturnToLobby`)

**무엇이 잘못됐나:** `TryFinishRun`이 `SetSimulationEnabled(false)`로 틱을 멈추는데, `ServerReturnToLobby`가 되돌리지 않는다. 다시 켜는 곳은 `StartRun`과 `ResumeRun`뿐이다.

**실패 시나리오:** 런 1 종료 → 로비 복귀 → **로비 #2에서 서버 이동 틱이 죽어 있다.** 소유 클라는 예측으로 움직이지만 재조정이 서버의 고정 위치로 되돌려 제자리에서 고무줄처럼 튄다. 스태미나 회복도 멈춘다. 재현 조건이 "런을 두 번 열었을 때만"이라 추적 비용이 크다.

**결정 — `SetPhase(RunPhase.Lobby)` 직전에 한 줄 추가.**

```csharp
AuthorityTickScheduler.ServerInstance?.SetSimulationEnabled(true);
```

**함께:** `AuthorityTickScheduler.FixedUpdate`의 pending 등록·해제 처리를 `_isSimulationEnabled` 게이트 **밖**으로 뺀다. 지금은 정지 중 큐가 무한정 자라고, 그 사이 파괴된 오브젝트의 델리게이트가 누적된다.

**완료 기준:** 런을 연속 2회 시작·종료한 뒤 로비에서 3인 전원이 정상 이동. 스태미나 회복 정상.

## 2. P1 — P0 직후 (구조적 결함)

### P1-1. 두고 간 자리가 영원히 만료되지 않는다

**위치:** `Assets/01.Scripts/01.Network/Lobby/LobbyRoster.cs:66`, `185-215`, `260-274`

`_vacatedSeats`를 비우는 곳이 `OnStartServer` 하나뿐이다. 그리고 `ServerRestoreVacatedSeat`가 복원할 캐릭터가 지금 로스터에서 비어 있는지 확인하지 않는다.

**실패 시나리오 (3인 정원 안에서 도달 가능):**
1. 런 1에서 A가 이탈 → `_vacatedSeats[A] = {Chasa}`. 런 종료 → 로비
2. D가 들어와 런 2에서 Chasa를 받음. 런 2 종료 → 로비
3. B가 나가 자리가 하나 빔
4. **A가 재접속** → 1단계의 유물이 살아 있어 A에게 Chasa를 다시 찍음
5. 로스터에 Chasa가 둘 → 배분기가 `InvalidCharacter`로 실패
6. **전원 준비 상태인데 런이 시작되지 않는다.** 에러 로그 한 줄 외에 아무 피드백이 없다

같은 원인으로 **입장 잠금도 뚫린다.** 인증기가 `HasVacatedSeat(id)`만 보므로 몇 판 전에 나간 사람이 진행 중인 런에 들어올 수 있다.

그리고 일시정지 재개 조건이 **"누가" 돌아왔는지가 아니라 인원 수만 센다.** 보스전에서 A가 튕겨 얼어 있을 때 오래된 자리를 가진 X가 들어오면 `SlotCount`가 3이 되어 **캐릭터가 중복된 파티로 보스전이 재개된다.**

**결정 — "복귀 대상 집합"이라는 개념을 도입한다.**

1. `RunManager.PauseRun` 시점에 **돌아와야 하는 `PlayerPlatformId` 집합**을 스냅샷으로 잡는다
2. `TryResumePausedRun`은 그 집합이 **전부 채워졌을 때만** 재개한다 (인원 수가 아니라 신원 일치)
3. 인증기의 입장 허용도 `HasVacatedSeat`가 아니라 **이 집합 포함 여부**로 판정한다
4. `ServerReturnToLobby`에서 `_vacatedSeats`를 만료시킨다
5. `ServerRestoreVacatedSeat`는 복원 대상 캐릭터가 이미 다른 슬롯에 있으면 `HasCharacter = false`로 두고 배분기에 맡긴다

이것이 H-1·H-2를 한 번에 닫는다. 지금은 "자리를 기억한다"만 있고 "누가 돌아와야 하는가"가 없어서 생긴 결함이다.

**완료 기준:** 이탈–복귀–런종료–재이탈–재복귀 시퀀스 10회에서 캐릭터 중복 0회, 무관한 인원의 진행 중 런 입장 0회.

### P1-2. 런 시작 실패가 세션을 영구 잠근다

**위치:** `LobbyController.cs:266-267`

`LockAdmission()`을 `StartRun()` **앞에서** 부르는데 `StartRun`은 `void`라 실패해도 호출자가 모른다. 실패하면 역할은 확정된 채 입장만 잠겨 **로비도 런도 아닌 상태로 세션이 죽는다.**

**결정 — `StartRun`을 `bool` 반환으로 바꾸고 순서를 뒤집는다.**

```csharp
if (RunManager.ServerInstance.StartRun()) { LockAdmission(); }
```

**함께:** `LobbyRoleCoordinator.TryCommitRole`이 중간에 실패하면 이미 커밋한 항목을 롤백한다. 지금은 부분 커밋이 남아 재시도가 영구 실패한다.

### P1-3. 패링의 남은 두 구멍

**(a) 만료된 window의 클라이언트 통지 누락** — `ParryController.cs:458-469`

서버는 `ImpactTime`이 지나면 `_activeWindow`를 버리는데 클라이언트에 알리지 않는다. 클라의 `_clientActiveWindow`에 옛 키가 남아 **이후 허공 패링이 전부 `RejectedWindowMismatch`로 거부된다.** 다음 window가 열릴 때까지 영구히.

설계 12장이 규정한 "양쪽 모두 window 없음 → 유효한 허공 패링(비용+후딜)"이 성립하지 않는다. **예측 모션을 붙이기 전에 반드시 고쳐야 한다** — 안 그러면 "거부인데 모션은 계속 재생"으로 드러난다.

**(b) window 길이 유한수 미검증** — `ParryController.cs:325-333`

`Mathf.Clamp(NaN, 0, max)`는 NaN을 그대로 반환하고 `duration <= 0f`도 NaN이면 false다. NaN duration이 들어오면 **`IsExpired`가 영원히 false인 window**가 등록된다.

**결정 — 둘 다 즉시 수정.** (a)는 `CleanupExpiredWindow`에서 `TargetCloseParryWindow(expiredKey)` 한 번, (b)는 `Clamp` 앞에 유한수 게이트.

### P1-4. 일시정지·런 경계에서 진행 중인 공격이 취소되지 않는다

**위치:** `PlayerAttack.cs:197-230` + `RunManager.cs:183,205`

취소 경로가 `ServerUpdateState` 안에 있는데, `PauseRun`/`TryFinishRun`이 **틱 자체를 멈춘다.** 취소 코드가 실행될 기회가 없다.

**실패 시나리오:** 선딜 0.12초 도중 일시정지 → 20초 뒤 재개 → **첫 틱에 20초 전 입력의 판정이 실행된다.** 런 종료 경로는 더 나쁘다 — 로비 복귀로 스폰 지점에 텔레포트된 뒤 다음 런 첫 틱에 **이전 런의 공격이 스폰 지점에서 판정되고 신궁이면 화살이 한 발 나간다.**

**결정 — `PlayerRunAgent.ResetForNewRun`을 런 경계 정리의 단일 창구로 삼는다.** 여기서 `PlayerAttack`·`ParryController`의 진행 상태와 `_lastIdByAttacker`를 함께 초기화한다.

**결정 (부수) — 패링 게이지는 런 경계에서 0으로 초기화한다.** 설계서가 "사망·관전·부활에서는 유지"만 정하고 런 경계를 규정하지 않았다. 다음 런에 치명 charge를 들고 시작하는 것은 로그라이크 런 독립성에 어긋난다.

## 3. 확정된 기획 결정

[기획 검증 문서](design-review-2026-09-03.md)에서 제기한 항목을 팀장 판단으로 확정한다.

### D1. 효율 채점을 유지하되 환율을 고친다 — **비용 0**

**대전제 (2026-09-03 팀장 확정): 이 게임의 점수는 "자원을 적게 쓰고 이기는 것"을 보상하는 효율 채점을 정체성으로 삼는다.**

리더보드가 있는 게임에서 자원 소비가 점수상 공짜면 순위는 "누가 드랍 운이 좋았나"로 수렴한다. 자원을 남기는 쪽에 점수를 주면 상위권 플레이어가 스스로 난도를 올리는 축이 생긴다. 레지던트 이블의 랭크 평가, 히트맨의 Silent Assassin이 같은 설계다. **현재 `ScoreRuleSO`의 "남아 있는 것에 점수를 준다"는 방향 자체는 옳다.**

문제는 철학이 아니라 **환율**이다. 효율 채점이 건강하려면 자원을 쓰는 것이 **가끔은 옳아야** 한다. 항상 옳거나 항상 틀리면 그건 결정이 아니라 정답이다.

**실제로 깨진 곳 — 등급 상승권은 어떤 상황에서도 손해다.**

| 항목 | 값 |
|---|---|
| 비용 | 350냥 × 2점 = **700점** |
| 효과 | 영험(28~42) → 신물(42~65). 한 사람 공격력 약 +53% → 파티 DPS 약 **+18%** |
| 보상 경로 | 보스전 단축 → 시간 보너스. **이것 하나뿐** |
| 5분 보스전 기준 | 46초 단축 × 분당 200점 = **153점** |
| 순손익 | **−547점 (4.5배 손해)** |

보스전을 15분으로 잡아도 457점이라 여전히 손해다. 즉 **보스전 길이와 무관하게 상승권은 절대 사면 안 되는 물건**이고, [7.3절](02-game-design.md)이 설계한 "상승권이냐 물약이냐" 갈등은 성립하지 않는다. 답이 항상 물약이다.

원인은 **"강해지는 것"이 점수로 환산되는 비율이 너무 낮다는 것**이다. 시간 보너스가 분당 200점뿐이라 DPS 상승의 가치가 거의 0에 수렴한다.

**확정 배점:**

| 항목 | 배점 | 변경 |
|---|---:|---|
| 보스 처치 | 10,000 | 신규 (기획서 11.1) |
| 클리어 시간 보너스 | **분당 400** (초당 6.67) | **200 → 400.** 강해지는 것의 가치를 올린다 |
| 잡귀 처치 | 마리당 30 | 신규. 시간 보너스 상승분을 상쇄해 파밍을 받친다 |
| **남은 노잣돈 (잔액)** | **1냥당 1점** | **효율 채점 유지.** 2점 → 1점 조정만 |
| 남은 HP | 1점 | **유지** — 물약 사용을 보상해 "안 사는 쪽"으로 쏠리는 것을 막는다 |
| 무사망 보너스 | 0회 5,000 / 1회 2,000 / 2회 500 / 3회+ 0 | **계단화** |
| 사망 감점 | 1회당 −1,000 | 신규 |
| ~~미사용 특성 포인트~~ | — | **폐기** |

**검산 — 등급 상승권:** 비용 350점, 효과 46초 × 6.67 = 307점. **−43점.** 거의 균형이다. 보스전이 길어지거나 파티가 그 무기에 딜을 몰아주면 이득으로 넘어가고, 아니면 소폭 손해. **이것이 결정이 되는 지점이다.**

**검산 — 파밍:** 1마리 = 30점 + 노잣돈 18~34점 = 48~64점. 시간 비용 6.67점/초 → **손익분기 7~10초/마리.** 빠르게 정리하면 이득, 질질 끌면 손해. 코어 루프의 "욕심 대 생존"이 점수에 그대로 반영된다.

**미사용 특성 포인트만 폐기하는 근거 — 이것은 효율 채점이 아니다.**

- 물약·노잣돈은 **소모품**이다. 안 쓰고 이기면 실력이다. 효율 채점의 정당한 대상이다
- 특성 포인트는 소모품이 아니라 **빌드**다. 안 찍는 것은 실력이 아니라 시스템을 열지 않는 것이다
- 결정적으로 [8.3절](02-game-design.md)이 **"무료로 언제든 초기화 가능. 40분 런 기반 로그라이크에서 빌드 실험은 재미 요소이므로 페널티를 두지 않는다"**고 명시한다. 그런데 이 배점이 **정확히 그 페널티**를 만든다 — 포인트 하나당 20점

즉 철학 차이가 아니라 **기획서와 점수표의 직접 충돌**이다.

**무사망 계단화 근거:** 효율 채점과 충돌하지 않는다. "무사망이 최고 보상"은 그대로 두고, 현행의 절벽(첫 사망 −6,520점, 보스 처치 가치의 65%)만 없앤다. 지금은 한 번 죽고 나면 2·3번째 사망을 조심할 이유가 급감한다.

`CalculateFinalScore`를 부르는 곳이 아무 데도 없고(`ScoreManager` 미존재), `TalentTreeSO._nodes`도 빈 배열이다. **지금 바꾸는 비용이 정확히 0이다.**

### D2. 부활에 협동 경로를 추가한다

```
사망 → Downed(관전)
  ├─ 팀원이 사망 지점 3m 이내에서 3초 상호작용 유지
  │     → 즉시 부활 · HP 50% · 노잣돈 손실 10%
  └─ 아무도 오지 않음 → 30초 뒤 자동 부활 · HP 50% · 노잣돈 손실 20% (현행)
```

- 부활 무적 2초는 양쪽 동일
- 상호작용 취소 조건: 시전자의 이동·공격·구르기 입력. **피해를 받는 것으로는 중단되지 않는다** (단순하게 유지)
- 서버 권위 그대로: 요청은 `[Command]`, 거리·생존·시간 판정과 부활 확정은 `[Server]`
- `IInteractable`이 이미 있고 `ReviveController`가 미구현이므로 **새 시스템이 아니라 아직 짓지 않은 방의 도면**이다

**근거:** 현행은 코옵 게임에서 긴장이 가장 높은 순간이 "30초 기다리기"다. 살아있는 팀원이 할 수 있는 일이 없다. 손실률을 반으로 줄이면 "구하러 갈 가치"가 수치로 생기고, 그 이득이 개인이 아니라 **팀 공용 재화**라 코옵 동기가 맞는다.

### D3. 결계 밖 사망에만 부활 지점을 보정한다

사망 지점이 결계 밖이면 **결계 중심 방향으로 현재 반경의 90% 지점**에 부활시킨다. 결계 안이면 사망 지점 그대로(현행).

**근거:** 3차 결계는 초당 5 피해에 회복 봉쇄인데 부활 무적은 2초다. 2초 뒤 다시 맞기 시작하고 죽을 때마다 노잣돈 20%가 또 빠진다. **억제 장치가 선형이 아니라 복리로 작동한다.** `BarrierJudge`가 이미 XZ 거리와 반경을 계산하므로 방향 벡터 하나면 된다.

### D4. 잡귀 패링 성공은 팀 전체에 이득을 준다

`EnemySO`에 `StaggerDamageMultiplier = 1.5`를 추가하고, 경직 상태의 잡귀가 받는 피해에 곱한다.

**근거:** 패링은 검 전용이고 무기는 무작위 배분이라 **3인 중 2인은 40분 내내 시그니처 메커닉을 조작하지 않는다.** 보스 설계 3.2가 이미 "패링 성공 → 팀 그로기"를 정했으므로 같은 규칙을 창귀에 내리면, 신궁·무녀는 패링을 못 해도 **패링의 수혜자**가 된다. 관전자에서 벗어난다.

**활·방울 전용 위기 대응 액션(백스텝 사격·팀 보호막)은 보류한다.** 스코프가 늘고 `IWeaponAbility` 분리 리팩토링을 끌고 온다. D4만으로 체감이 얼마나 달라지는지 M2에서 먼저 본다.

### D5. 차사 특성 2열을 "검의 길"로 재설계한다

| 직업 | 1열 | 2열 |
|---|---|---|
| 차사 | **패링의 길** — 판정 창 확대, 게이지 축적량, 치명 최소 배율 | **검의 길** — 3타째 강공격, 공격 속도, 스태미나 효율 (**패링 비의존**) |

**근거:** 현행은 두 줄이 모두 패링에 붙어 어느 쪽을 밀든 플레이 방식이 바뀌지 않는다. 8.2절이 말한 "한 줄을 밀거나 섞는 선택"이 신궁(연사/관통)·무녀에서는 성립하는데 차사만 성립하지 않는다. 게다가 패링 불가 구간(액귀 다수, 보스의 패링 불가 패턴)에서 차사는 성장을 전혀 체감하지 못한다.

`TalentTreeSO._nodes`가 빈 배열이라 **비용 0이다.**

### D6. 중반 30분의 페이싱 — 세 가지를 함께 넣는다

**문제 정정:** 초판은 이를 "적이 3종뿐이라 단조롭다"로 봤으나, 적 종류가 적은 것은 나이트레인도 같다. 실제 원인은 셋이다.

1. **조우가 30분 내내 같다** — 거점마다 구성 비율이 같아 대처법이 바뀌지 않는다
2. **중간 이정표가 없다** — 30분을 연속으로 달려 보스 하나
3. **긴장 곡선이 평평하다** — 결계 축소 외에 스파이크가 없다

**레퍼런스 대조 — 2번이 구조적으로 두드러진다.**

| | 구간 길이 | 구간을 닫는 것 |
|---|---|---|
| 엘든 링 나이트레인 | 약 14분 | **밤 보스** (1·2일차) |
| 몬스터 헌터: 월드 | 퀘스트 15~30분 | 대형 몬스터 처치 |
| **그믐** | **30분 연속** | **없음** (보스는 맨 끝 1회) |

나이트레인은 14분 이상 보스 없이 가지 않는다. 그믐은 30분으로 두 배가 넘는다. 가장 정직한 해법은 중간 보스이나 [스코프 잠금](../CLAUDE.md)의 "보스 2마리 이상"에 걸린다. **따라서 보스가 아닌 것으로 구간을 닫는다 — 결계 축소가 그 자리다.**

#### D6-a. 거점 구성을 비율 굴림에서 조합 프리셋으로

현재 `SpawnConfigSO`는 구간별 `RatioHeokkaebi/Changgwi/Aekgwi`로 3~5마리를 굴린다. 그 결과 **모든 거점이 통계적으로 동일**해진다. 이름 붙인 조합으로 교체한다.

| 프리셋 | 구성 | 전술 문제 | 빛나는 직업 |
|---|---|---|---|
| 무리 | 허깨비 5 | 물량·포위 | **무녀** (360° 방울) |
| 돌격대 | 창귀 2 + 허깨비 2 | 연속 돌진, 패링 타이밍 | **차사** |
| 저주진 | 액귀 3 + 허깨비 1 | 원거리 견제, 접근 압박 | **신궁** |
| 혼성 | 허깨비 2 + 창귀 1 + 액귀 1 | 복합 | — |
| 창귀 무리 | 창귀 3 | 3연 돌진, 최고 위험 | 차사 (고위험) |

구간별 등장 풀: 개활은 무리·혼성 / 1차에 돌격대·저주진 추가 / 2차에 창귀 무리 해금.

**두 문제를 동시에 푼다.** 거점마다 다른 퍼즐이 되고, **직업 스포트라이트가 순환한다.** [D4](#d4-잡귀-패링-성공은-팀-전체에-이득을-준다)가 다루는 "3인 중 2인이 관전자" 문제도 여기서 완화된다 — 저주진에서는 신궁이, 무리에서는 무녀가 주인공이 된다.

**비용: 순수 데이터.** `SpawnConfigSO`에 프리셋 배열을 추가하고 `SpawnCluster`가 비율 대신 프리셋을 고르게 한다.

#### D6-b. 결계 축소 시 잡귀가 안쪽으로 밀려든다

각 구간 전환(10:00 / 20:00 / 29:30)에 결계 밖 잡귀를 **비활성화하는 대신 결계 중심 방향으로 이동**시킨다.

- 10초 전 경고와 함께 발생 (경고 이벤트는 `BarrierController`가 이미 발행할 예정)
- 밀려든 개체가 기존 거점에 합류 → **순간 밀도 급증**
- 세계관 정합: 결계가 조여오니 원귀도 갈 곳이 없어진다

**30분 안에 세 번의 긴장 스파이크**가 생기고, 이것이 구간을 닫는 이정표 역할을 한다.

**여기서 결함이 기능이 된다.** [P1-5](#p1-5-ai-쪽-남은-높음-4건)가 지적한 "결계 축소 시 범위 밖 기존 잡귀가 정리되지 않는다"를 정리 대신 **안쪽 이동**으로 처리하면 된다. `SpawnManager.RefreshClusterRange`를 비활성화에서 이동 명령으로 바꾸는 것이고, Brain에 복귀 상태(`AekgwiBrain.EnterReturn`)가 이미 있다.

#### D6-c. 보상 티어를 눈에 보이게 한다

`SpawnCluster`에 `RewardTier`(0/1/2)를 부여하고 `DropTableSO` 조회 키를 `필드레벨 + 티어`로 확장한다. 결계 중심에서 먼 거점일수록 한 단계 상향.

**그러나 플레이어가 볼 수 없으면 결정이 아니다.** 어느 거점이 비싼지 모르면 항상 가까운 곳을 친다.

- 고티어 거점에 시각 표식 — 솟대·장승에 불빛 또는 안개 기둥 (`06.Model/`의 한국 상징물 자체 제작 계획을 활용)
- 미니맵에 등급 표시

**근거:** [게임 디자인 5.3](02-game-design.md)이 "거점형은 다음 무리를 칠지 넘어갈지 판단을 만든다"고 적었지만, **모든 거점의 기대값이 같으면 그것은 선택이 아니라 순서다.**

#### 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 중간 보스 추가 | 스코프 잠금("보스 2마리 이상"). D6-b가 그 역할을 대신한다 |
| 정예 잡귀 배치 | D6-a가 조합으로 다양성을 만들어 불필요해졌다 |

### D7. 무기 배분에 선호 1순위를 도입한다

로비에서 각자 선호 무기 1개를 선언한다. 3인이 서로 다르면 전원 존중, 겹치면 **겹친 사람들끼리만** 무작위.

**근거:** 40분은 원치 않는 직업을 견디기에 긴 시간이다. 로그라이크의 무작위성은 드랍 등급·스탯 롤에서 이미 충분히 제공된다. `LobbyRoleAllocator`가 Mirror·UnityEngine 비의존 순수 계산기라 선호 입력을 얹는 비용이 작고 단위 테스트도 가능하다.

### D9. 시작 지점·보스 지점을 매판 무작위로 하고, 결계 중심이 보스 지점으로 이동한다

**스코프 확인:** [시스템 기획 6장](01-system-design.md)이 "고정 맵 + **랜덤 스폰**. 절차적 지형 생성 없음"으로 확정했다. 지형을 생성하는 것이 아니라 후보 지점 중에서 고르는 것이므로 **스코프 잠금 위반이 아니다.**

#### 채택 근거 — 수동 제약이 구조로 대체된다

[시스템 기획 2.1](01-system-design.md)에 다음 제약이 있다.

> **보스맵 입구는 3차 결계의 최종 반경 안에 배치한다.** 이 제약을 어기면 보스전 진입 자체가 파티 전멸 구간이 된다. 맵 레이아웃 확정 시 `BarrierCenter`에서 보스맵 입구까지의 거리를 3차 최종 반경보다 작게 잡을 것.

사람이 거리를 재서 지켜야 하는 규칙이고, 어기면 증상이 3인 통합 테스트에서야 드러난다. **최종 원이 보스 지점에 수렴하면 이 제약을 어길 수 없게 된다.** 레벨 디자인 실수 한 종류가 구조적으로 사라진다.

부수 이득: 매판 경로가 달라져 고정 맵의 리플레이성이 오르고, [D6-c](#d6-c-보상-티어를-눈에-보이게-한다)의 "결계 중심에서 먼 거점일수록 고티어"가 **매판 다른 거점을 고티어로** 만든다.

#### 확정 구조

```
런 시작 — 서버가 한 번 확정하고 SyncVar로 배포
  ├ 시작 지점  후보 4~6곳 중 1
  └ 보스 지점  후보 3~4곳 중 1   ← 결계의 최종 중심

결계 전환 — 매 단계, 30초 SmoothStep 보간
  중심: 이전 중심 → 보스 지점 방향으로 이동
  반경: 이전 반경 → 목표 반경
```

| 단계 | 중심 | 반경 |
|---|---|---:|
| 개활 | 시작 지점 부근 | 100% (400m) |
| 1차 | 보스 지점 방향 1/3 지점 | 50% |
| 2차 | 2/3 지점 | 30% |
| 3차 | **보스 지점** | 15% |

**거리 제약 필수:** 시작 지점과 보스 지점의 거리가 **맵 크기의 50~80%** 범위인 조합만 후보로 삼는다. 우연히 붙으면 30분 이동이 무의미해지고, 정반대면 이동만 하다 끝난다. 지점 선택은 서버 전용이며 클라이언트가 각자 굴리지 않는다.

#### 코드 변경 — 작다

- `BarrierTransitionState`에 `FromCenter` · `TargetCenter` 추가. 전환당 1회 동기화라 대역폭 영향 없음
- `BarrierJudge`의 순수 함수에 중심 보간 추가

```text
t       = InverseLerp(startTime, endTime, now)
center  = Lerp(fromCenter, targetCenter, SmoothStep01(t))
radius  = Lerp(fromRadius, targetRadius, SmoothStep01(t))
outside = (playerXZ - centerXZ).sqrMagnitude > radius * radius
```

**`BarrierController`가 아직 코드 0줄이므로 지금 결정하면 추가 비용이 0이다.** 고정 중심으로 먼저 만들고 나중에 바꾸는 것이 가장 비싸다.

#### 상호작용 — 반드시 함께 처리할 것 셋

**(1) 몬스터 강화를 기존 개체에 소급하지 않는다.** [게임 디자인 5.2](02-game-design.md)가 "배수는 스폰 시점의 결계 단계로 확정하고 이후 단계가 바뀌어도 다시 계산하지 않는다. 실시간 재계산은 교전 도중 최대 HP가 변해 체력바가 어긋난다"고 확정했다.

**대신 [D6-b](#d6-b-결계-축소-시-잡귀가-안쪽으로-밀려든다)의 밀려드는 시점에 새 단계 강화를 적용한다.** 그 순간은 플레이어와 교전 전이므로 최대 HP가 변해도 체력바 어긋남이 보이지 않는다. 5.2의 우려가 발생하지 않는 유일한 타이밍이다. 서사도 맞는다 — 결계에 쫓겨 들어온 원귀가 결계의 힘으로 뒤틀린다.

**(2) 이 처리를 안 하면 2차 구간에 강화된 잡귀를 볼 일이 거의 없다.** `SpawnConfigSO`의 2차 구간 `RespawnInterval`이 **0**이라 리스폰이 없다. ×1.6 강화는 2차 진입 시 새로 채우는 개체에만 붙는데, 1차 생존 개체가 `ConcurrentMax`(8~10)를 차지하면 신규 스폰이 줄어든다. 여기에 D6-b로 약한 개체까지 밀려들면 예산을 다 먹어 강화 개체가 거의 나오지 않는다. **(1)의 결정이 이 문제까지 함께 푼다.**

**(3) 객주 위치를 다시 잡는다.** [시스템 기획 2.1](01-system-design.md)의 "`ShopKeeper` 위치는 2차 결계 최종 반경보다 작아야 한다"가 중심 이동으로 깨진다. **고정 배치를 버리고 2차 결계 중심 부근에 서버가 배치**하거나, 후보 지점 중 2차 원 안에 드는 곳을 고른다.

#### 진짜 비용은 씬·아트다

| 항목 | 비용 | 담당 |
|---|---|---|
| 결계 중심 이동 (코드) | 작음 | @kjw1237 |
| 시작 지점 후보 4~6곳 배치 | 작음 | 아트 |
| **보스 아레나 후보 3~4곳** | **큼** | **아트 (팀장 겸임)** |
| 객주 배치 방식 변경 | 중간 | 아트 + Systems |
| 클러스터 배치 재검증 (어느 시작점에서도 초반에 적이 있는가) | 중간 | 아트 + AI |

**절충 확정:** 보스 지점을 **3곳으로 제한**하고, 정교한 아레나 대신 **평지 3곳을 지정**한다. 보스 패턴 네 종(`MeleeArc`·`TargetedDash`·`MarkedCircle`·`ConeBurst`)이 전부 평평한 공간만 요구하므로 지형 연출은 후속으로 붙인다. **시작 4곳 × 보스 3곳 = 12가지 경로**면 고정 맵의 리플레이성으로 충분하다.

**이 변경은 `@Stage`의 `BarrierCenter` 고정 마커 계약을 바꾸므로 [04-architecture.md 3.2](04-architecture.md)를 함께 갱신한다.**

## 5. 절단선 — 잘라내는 것

40분 코옵 로그라이크가 **게임으로 성립**하는 데 반드시 필요한 것과, 없어도 런이 끝까지 도는 것을 나눈다.

### 반드시 있어야 함 (절대 자르지 않음)

로비 → 무기 배분 → 이동·공격·패링 → 잡귀 → **결계 축소** → **보스** → 사망·부활 → 결과·점수

### 여유가 없으면 자르거나 줄임 (우선순위 순으로 후퇴)

| 항목 | 없으면 | 최소 대체안 |
|---|---|---|
| 특성 트리 | 레벨업이 최대 HP만 올림 | 레벨당 고정 스탯 상승으로 축소 |
| 객주 상점 | 노잣돈이 점수로만 쓰임 | 상점 생략, 노잣돈은 점수 항목으로만 유지 |
| 장비 드랍·인벤토리 | 무기 공격력이 고정값 | 드랍만 남기고 인벤토리 없이 **즉시 교체**로 축소 |
| 리더보드 | 점수가 화면에만 표시 | 정산 화면만, 저장 생략 |

**이 순서로 후퇴한다.** 특성 트리를 먼저 자르는 이유는, 그것이 없어도 코어 루프("한 번 더 주울까, 물러설까")가 온전히 성립하는 유일한 항목이기 때문이다. 반대로 장비 드랍은 마지막까지 남긴다 — 파밍 대상이 없으면 결계의 압박이 의미를 잃는다.

### 스코프 잠금 유지 (변경 없음)

보스 1마리 · 무기 3종 · 고정 맵 · 절차적 생성 없음 · 제작 합성 없음 · 인벤토리 확장 없음

## 7. 미검증으로 남는 것

- 이 문서의 **체감 관련 주장은 전부 가설이다.** D1~D7의 수치는 계산상 모순을 제거할 뿐이며, 조정 후 값이 재미있는지는 3인 플레이 테스트 전까지 확정하지 않는다
- `Main.unity`의 Dev 스위치 인스펙터 값(`_devAbandonRunKey`, `_devStartHostKey`, `_devAutoReady`, `_devMinPlayers`, `_devForceSword`)은 씬 에셋을 열어 확인하지 않았다. **Dev 스위치가 코드가 아니라 씬 직렬화 값에만 의존하는 구조 자체가 위험하다** — `#if UNITY_EDITOR || DEVELOPMENT_BUILD`로 필드와 사용처를 함께 감싸는 것을 권한다
- 잡귀 Animator Controller가 `VisualState == Attack` 전이 조건을 쓰는지 확인하지 않았다. 쓴다면 P1-5의 표현 상태 유실이 호스트 화면에서도 드러난다
- 액귀 리시 반경이 어그로 반경과 같아 제자리 왕복이 발생하는지는 실제 플레이로만 확인 가능하다

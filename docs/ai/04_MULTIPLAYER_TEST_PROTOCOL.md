# 멀티플레이 테스트 절차

> 이 프로젝트의 결함 대부분은 **단일 플레이에서는 멀쩡하고 3인에서만 깨진다.**
> 그래서 "실행해봤다"는 검증 증거가 되지 못한다. 무엇을 어떻게 확인했는지가 필요하다.

---

## 1. 테스트 등급

| 등급 | 구성 | 언제 |
|---|---|---|
| M0 | 단일 인스턴스 (호스트 혼자) | 컴파일 확인, 로컬 로직 |
| M1 | 호스트 + 클라 1 (같은 PC, ParrelSync 또는 빌드) | 동기화 기본 확인 |
| M2 | 호스트 + 클라 2 (같은 PC) | 3인 로직, 파티 공유 자원 |
| M3 | 호스트 + 클라 2 (**서로 다른 PC**) | 실제 지연 환경 |

**네트워크가 걸린 변경은 최소 M2다.** M0에서 되는 것은 증거가 아니다.

지연 보상, 패링 판정, 투사체 동기화는 **M3까지 확인**한다. 같은 PC에서는 지연이 0에 가까워 문제가 드러나지 않는다.

**M3의 호스트는 팀에서 가장 사양이 좋은 PC로 고정한다.** 리슨 서버라 호스트 PC가 게임 로직과 렌더링을 함께 부담하고, 호스트가 바뀌면 프레임 측정치를 이전 회차와 비교할 수 없다.

## 운영 계정·릴레이 경로

현재 일반 사용자 경로는 자체 계정 런처와 AWS UDP 릴레이다. 서로 다른 PC·계정 3개로 로그인, 수동 방 목록 갱신, 파티 생성/참가, 무기/봇/준비, 출발, 게임 접속과 종료를 검증한다. 포트포워딩이나 Steam 로그인을 요구하지 않는다.

설치 게임 build identity와 API 허용 build ID를 맞춘 뒤 시작한다. 로그아웃/세션 폐기, 호스트 종료, API 재시작, UDP 차단은 서로 다른 실패 조건이다. 같은 PC 3프로세스가 AWS를 경유해도 M2이며 다른 회선 M3를 대체하지 않는다. [릴레이 계약](../unity/ACCOUNT_RELAY.md)을 따른다.

아래 KCP 도구는 개발 검증, Steam 절은 호환 경로 검증이다.

## 2. 같은 PC에서 여러 인스턴스 띄우기

### 2.0 실제로 쓰는 경로 — 스크립트와 준비물

아래 방법 A~C는 선택지이고, **직접 KCP·Steam 개발 검증에는 `tools/` 스크립트를 사용한다.**

| 무엇 | 스크립트 |
|---|---|
| **한 PC 3창** (M2) | Unity 메뉴 `그믐 - 런 테스트 - 이 PC에서 3인 실행 (M2)`. 종료는 같은 메뉴의 `실행한 빌드 전부 종료` |
| **다른 PC 3대** (M3) | `그믐 - 런 테스트 - KCP 호스트 실행` → 다른 PC에서 `KCP 클라이언트 실행` |
| Steam 경로 | `그믐 - 런 테스트 - Steam 호스트 실행` · `Steam 클라이언트 실행` · `Steam 로비 실행` |

**메뉴는 `tools/`의 스크립트를 그대로 부른다.** Unity를 띄우지 않는 PC에서는 직접 실행해도 된다 — 두 경로는 같은 것을 실행한다.

| 메뉴 | 직접 실행 |
|---|---|
| 이 PC에서 3인 실행 | `powershell -ExecutionPolicy Bypass -File tools\run-3clients.ps1` (종료는 `-Kill`) |
| KCP 호스트 · 클라이언트 | `tools\run-host.bat` · `tools\run-client.bat <호스트IP> <포트> <platformid>` |
| Steam | `tools\run-steam-host.bat` · `run-steam-client.bat` · `run-steam-lobby.bat` |

메뉴로 실행하면 **개발 빌드가 없을 때 먼저 알려주고 빌드할지 묻는다.** 릴리스 빌드로 돌려 실행 인자가 조용히 무시되는 사고를 여기서 막는다.

**시작 전에 확인할 것 넷.** 하나라도 어긋나면 3인 검증이 성립하지 않는다.

| | 왜 |
|---|---|
| ✅ **개발용 빌드가 최신인가** | Unity 메뉴 `그믐 - 빌드 - 개발용 빌드`. **릴리스 빌드는 `-platformid` 같은 실행 인자를 무시한다**(`NetworkLaunchArgs`가 `DEVELOPMENT_BUILD`로 감싸여 있다) |
| ✅ **`LobbyController._devMinPlayers`가 3인가** | 1이면 **호스트 혼자 런이 시작되면서 입장이 잠겨 나머지 둘이 거부된다.** 콘솔에 *"Dev 설정으로 1인 런을 시작한다"*가 찍히면 그 상태다 |
| ✅ **`-nocursorlock`이 붙는가** | 한 PC 3창에서 안 붙이면 **창 하나가 마우스를 독점해 나머지 둘이 카메라를 못 돌린다.** `run-3clients.ps1`이 이미 넘긴다. 이때 카메라는 **Alt를 누르는 동안에만** 돈다(씬뷰와 같다) |
| ✅ **테스트할 씬에 대상이 있는가** | 아래 2.0.1 |

#### 2.0.1 씬별로 있는 것과 없는 것

| 씬 | 잡귀 | 카메라 리그 | 빌드 목록 | 쓰임 |
|---|---|---|---|---|
| **`Dev_Combat`** | ✅ 창귀 2 · 액귀 1 (씬 배치) + `ParryTestDummy` | ✅ | ✅ index 0 | **전투 · 카메라 · 락온 L3의 기본 무대** |
| `Dev_AI` | ✅ SpawnManager + 클러스터 3 | ❌ | ❌ | 몬스터 파트 전용 |
| `Main` | ❌ 스포너 없음 | ❌ | ✅ | 개활맵 · 지형 |

> 🔑 **`Dev_Combat`의 잡귀 셋은 스포너가 아니라 씬에 직접 놓은 것이다.** 런 phase에 의존하지 않아
> 호스트를 켜는 즉시 항상 같은 자리에 있다 — 테스트가 재현 가능해야 해서다.
> 죽여 없앴으면 호스트를 다시 켜면 돌아온다. 바닥은 40×40m이고 NavMesh가 구워져 있다
> (`Assets/00.Scenes/Dev_Combat/NavMesh.asset`, 커밋 대상).

### 방법 A — ParrelSync (권장)

프로젝트를 심볼릭 링크로 복제해 에디터를 여러 개 띄운다.

- 장점: 코드 수정이 즉시 반영됨, 브레이크포인트 사용 가능
- 단점: 초기 세팅 필요, 에디터 2~3개가 메모리를 많이 씀

### 방법 B — 빌드 + 에디터

에디터를 호스트로, 빌드된 실행 파일을 클라이언트로 띄운다.

- 장점: 세팅 불필요, 실제 빌드 동작 확인
- 단점: 코드 수정 때마다 재빌드

### 방법 C — Unity Multiplayer Play Mode

Unity 6의 내장 기능. 한 에디터에서 여러 플레이어를 시뮬레이션한다.

- 장점: 가장 빠름
- 단점: 실제 네트워크 스택을 완전히 재현하지 않음

**권장**: 일상 개발은 C, 기능 완료 확인은 A, 주간 통합은 B로 실제 빌드 확인.

## 3. 지연 환경 재현

같은 PC에서는 지연이 0이라 지연 관련 결함이 드러나지 않는다.

| 도구 | 용도 |
|---|---|
| Unity Network Simulator (패키지) | 에디터 안에서 지연 · 패킷 손실 주입 |
| Clumsy (Windows) | OS 레벨에서 네트워크 조건 조작 |

### 확인할 조건

| 조건 | 지연 | 패킷 손실 |
|---|---|---|
| 이상적 | 0ms | 0% |
| 국내 일반 | 30~50ms | 0.1% |
| 나쁨 | 150ms | 2% |

**패링은 세 조건 모두에서 확인한다.** 판정 창이 0.32초인데 150ms 지연이면 체감이 크게 달라진다.

## 4. 시나리오별 체크리스트

### 접속 · 세션

- [ ] 호스트 생성 후 클라 2인이 순차 접속된다
- [ ] 클라이언트 1명이 나가도 나머지가 계속 진행된다
- [ ] 호스트가 나가면 세션이 정상 종료된다 (크래시 아님)
- [ ] 재접속 시 상태가 어긋나지 않는다

### 전투

- [ ] 3인이 동시에 같은 잡귀를 때려도 HP가 정확히 깎인다
- [ ] 패링 성공이 호스트와 클라이언트 양쪽에서 같게 판정된다
- [ ] 패링 게이지가 100에 도달할 때 배율이 한 번만 적용된다
- [ ] 화살 궤적이 세 클라이언트에서 같게 보인다
- [ ] **화살이 벽에 막혀 뒤의 적을 맞히지 않는다** (worldMask 분리, 2026-09-03)
- [ ] **정밀 사격이 세 화면에서 같은 결과를 낸다** — 서버 시각 기준 판정이므로 RTT가 달라도 성공/실패가 일치해야 한다

### 아이템 · 경제

- [ ] 드랍된 아이템을 두 사람이 동시에 주우면 한 명만 획득한다
- [ ] 노잣돈이 세 클라이언트에서 같은 값으로 보인다
- [ ] 두 사람이 동시에 구매해도 잔액이 음수가 되지 않는다
- [ ] 아이템 양도 시 원 소유자에게서 정확히 사라진다
- [ ] 무기 교체로 직업이 바뀌면 특성이 초기화된다

### 결계 · 시간

- [ ] 세 클라이언트의 결계 반경이 같다
- [ ] 축소 경고가 세 명에게 동시에 뜬다
- [ ] 결계 밖 피해가 해당 플레이어에게만 들어간다
- [ ] 게임 내 시각이 세 클라이언트에서 같게 표시된다

### 사망 · 부활

- [ ] 사망 시 30초 타이머가 세 명 모두에게 같게 보인다
- [ ] 부활 시 노잣돈 20%가 정확히 한 번만 차감된다
- [ ] 사망 지점 그대로 부활한다
- [ ] 부활 직후 2초 무적이 적용된다
- [ ] **3명 전원 HP 0일 때만** 전멸 처리된다 (타이밍 차이로 오판정 없음)

### 보스

- [ ] 페이즈 전환이 세 클라이언트에서 동시에 일어난다
- [ ] 공격 예고 표식이 같은 위치에 뜬다
- [ ] 패링 가능 패턴이 클라이언트에서도 패링된다

### 호스트 부하 · 공정성

리슨 서버라 호스트 한 대가 3인분의 판정을 전부 진다. 부하가 한계를 넘는지, 호스트만 유리해지는지는 **측정하지 않으면 알 수 없다.**
아래는 M3 통합 테스트마다 기록한다 — 데디케이티드 서버 전환은 이 수치가 나빠질 때 꺼내는 카드다.

- [ ] 잡귀가 가장 많은 개활 구간(동시 18~22마리)에서 호스트 프레임을 측정했다
- [ ] 같은 구간의 클라이언트 프레임과 비교했다 (호스트가 크게 낮으면 로직이 아니라 렌더링부터 의심한다)
- [ ] 보스전 구간의 호스트 프레임을 측정했다 (잡귀는 0마리, 연출 부하가 최대인 구간)
- [ ] **패링 성공률을 호스트와 클라이언트로 나눠 집계했다** (각 20회 이상)
- [ ] 성공률 차이가 체감할 수준이면 판정 창 조정을 검토했다

패링 성공률 차이는 리슨 서버의 구조적 특성이라 0으로 만들 수 없다 ([네트워크 권위](../unity/NETWORK_AUTHORITY.md)).
없앨 대상이 아니라 **크기를 계속 지켜볼 대상**이다.

#### 프레임을 잴 때 먼저 맞출 조건

**이 조건을 안 맞추면 측정값이 서버 비용 판정에 쓸모가 없다.** 2026-09-01 M2에서 호스트 프레임 저하로 의심했던 현상이 실제로는 한 PC 안의 렌더링 자원 경쟁이었다.

- [ ] 세 인스턴스 모두 **60 FPS 상한**이 걸려 있다 — `@Diagnostics`의 `FrameRecorder._targetFrameRate`가 기본으로 건다. 오버레이 3행에 `60 FPS 상한`이 떠야 한다
- [ ] 세 인스턴스의 **해상도가 같다** — 빌드는 실행 인자 `-screen-width 1280 -screen-height 720 -screen-fullscreen 0`으로 고정한다
- [ ] 세 인스턴스의 **품질 설정이 같다**
- [ ] 호스트도 **에디터가 아니라 개발 빌드**로 실행했다 — 에디터 비용이 얹히면 호스트/클라 비교가 성립하지 않는다
- [ ] 서버 비용을 최종 판정할 때는 **M3(서로 다른 PC 3대)** 로 다시 잰다

같은 PC에서 위 조건 없이 잰 호스트/클라이언트 FPS 차이는 **기능 검증에는 쓰되 성능 판정에는 쓰지 않는다.**

## 5. 검증 기록 형식

PR이나 보고에 아래 형식으로 남긴다.

```markdown
### 멀티플레이 검증

- 등급: M2 (호스트 + 클라 2, 같은 PC, ParrelSync)
- 지연 조건: 0ms
- 확인 항목:
  - [x] 패링 성공이 양쪽에서 같게 판정 — 20회 중 20회 일치
  - [x] 패링 게이지 100 도달 시 배율 1회만 적용
  - [ ] 150ms 지연 환경 — **미검증** (Network Simulator 미설치)
- 호스트 / 클라 평균 프레임: 개활 구간 __ / __ fps, 보스전 __ / __ fps
- 패링 성공률: 호스트 __ / 20, 클라 __ / 20
- 관찰된 문제: 없음
- 남은 위험: 실제 지연 환경 미확인
```

**"3인으로 테스트했습니다"만으로는 증거가 되지 않는다.** 무엇을 몇 번 확인했는지 적는다.

## 6. 자주 놓치는 것

| 함정 | 증상 |
|---|---|
| 호스트에서만 테스트 | 호스트는 지연 0이라 항상 성공한다. 클라이언트 시점에서 반드시 확인 |
| 1회만 확인 | 타이밍 결함은 확률적으로 나타난다. 최소 10회 반복 |
| 순차 실행만 확인 | 동시 실행(동시 획득, 동시 구매)이 실제 결함 지점 |
| 정상 경로만 확인 | 접속 끊김, 사망 중 이벤트 발생 같은 경계 상황 |
| 시각적 일치만 확인 | 보이는 게 같아도 내부 값이 다를 수 있다. 로그로 값을 찍어 비교 |

## 7. 주간 통합 테스트

매주 정해진 요일에 아래를 실행한다.

1. 각자 작업 브랜치를 `develop`에 병합
2. 통합 담당자가 `Main.unity`에 반영
3. **빌드해서 3인 접속** (M3 — 서로 다른 PC)
4. 위 체크리스트 중 이번 주 변경과 관련된 항목 실행
5. 실패 항목을 그 자리에서 이슈로 등록

4주차에 없는 기능을 발견하면 손 쓸 방법이 없다. 주간 테스트는 이를 조기에 발견하기 위한 장치다.

## 8. Steam 경로 테스트

KCP 경로와 달리 **Steam P2P는 같은 PC·같은 계정으로 검증할 수 없다.** 자기 자신에게 연결하면 타임아웃난다.
그래서 Steam 관련 변경은 M2를 건너뛰고 바로 M3다.

### 8.1 준비

| 항목 | 내용 |
|---|---|
| 장비 | PC 3대, Steam 계정 3개, 서로 다른 회선 |
| 계정 | 세 계정이 **서로 친구**여야 한다. 초대를 주고받는 데 필요하다 |
| 빌드 | `그믐 > 빌드 > 개발용 빌드`. **릴리스 빌드로는 안 된다** — 실행 인자와 로비 HUD가 `DEVELOPMENT_BUILD` 안에만 있다 |
| 배포 | `Builds/Development/` **폴더째** 복사. 실행 스크립트와 `steam_appid.txt`가 빌드에 자동으로 들어간다 |
| Steam | 세 대 모두 Steam 클라이언트 실행 + 로그인 |

AppID는 480(Spacewar)이다. 다른 개발자도 같은 AppID를 쓰므로 로비는 항상 `Private`으로 만들고,
로비 데이터의 `game=geumeum`으로 남의 로비를 거른다.

### 8.2 회귀 먼저 — 기존 경로가 살아 있는가

새 코드가 기존 것을 깨지 않았는지부터 본다. **여기서 막히면 8.3으로 가지 않는다.**

| # | 조작 | 기대 |
|---|---|---|
| 1 | PC1 `run-host.bat`, PC2·PC3 `run-client.bat` | 3인 접속, `승인: ... source=Dev`, 역할 3종 중복 없음 |
| 2 | PC1 `run-steam-host.bat` → SteamID64가 클립보드에 복사됨 | `Steam 초기화 성공, 내 SteamID64=...` |

> **호스트 SteamID로 바로 붙는 경로는 막았다.** 예전에는 서버가 로비에 없으면
> 개발 빌드에 한해 로비 검증을 건너뛰었는데, 그러면 검증한 흐름과 실제로 쓰는 흐름이
> 갈라져 로비 쪽 결함이 테스트에서 드러나지 않는다.
> 이제 Steam 경로는 **항상 로비 멤버십을 요구**하므로 `run-steam-client.bat <SteamID64>`는
> `거부(NotLobbyMember)`가 된다. 정상이다. 접속은 8.3의 로비 경로로만 한다.
>
> 그래서 `run-steam-host.bat`은 SteamID를 확인하는 용도로만 남는다.
> 실제 3인 접속은 세 대 모두 로비 화면에서 진행한다.

### 8.3 로비 경로 — 본 검증

`run-steam-host.bat`은 `-host`로 바로 켜므로 로비를 타지 않는다. **세 대 모두 `run-steam-lobby.bat`으로 띄운다.**

```
run-steam-lobby.bat          신원을 무작위로 정한다
run-steam-lobby.bat 1001     신원을 직접 준다
```

**패널은 기본으로 꺼져 있다.** 화면을 가리지 않으려고 그렇게 뒀다. `PageUp`을 누르면 왼쪽에
`Steam 로비 (개발용)` 패널이 열린다. 로그는 `logs/steam-lobby.log`이고, 시작할 때 단축키 목록이 한 줄 찍힌다.

PC 3대를 각자 조작해야 해서 마우스보다 단축키가 빠르다. 아래 키는 패널이 꺼져 있어도 동작한다.

| 키 | 동작 | 누가 |
|---|---|---|
| `PageUp` | 패널 껐다 켜기 | 전원 |
| `Home` | 방 만들기 | 호스트가 될 PC |
| `PageDown` | **클립보드에 있는 로비 ID로 참가** | 클라이언트 PC |
| `End` | 호스트 시작 | 로비 소유자 |

> **키를 새로 잡을 때 주의.** F1~F12는 이미 전부 차 있다. 그런데 일부는 코드 기본값이
> `KeyCode.None`이고 실제 값이 프리팹·씬에 직렬화돼 있어(`_devStartHostKey`=F1,
> `_devAbandonRunKey`=F3) 코드만 grep하면 비어 보인다. `PartyDebugOverlay`의
> `G_KeyHelp` 목록과 프리팹 직렬화 값을 함께 확인할 것.

`PageDown`은 클립보드를 그대로 읽는다. 호스트가 `로비 ID 복사`로 넘긴 값을 복사해 두기만 하면
입력칸에 붙여넣지 않아도 참가한다. 클립보드가 로비 ID가 아니면 경고만 남기고 아무것도 하지 않는다.

**Steam 경로의 인원은 3으로 고정이다.** 씬 값이나 `-minplayers` 인자로 낮출 수 없다.
낮추면 호스트 혼자 런이 시작되면서 입장이 잠겨 나머지 둘이 거부되기 때문이다.
2대로 시험하고 싶으면 Steam이 아니라 KCP 경로를 쓴다.

| # | 조작 | 기대 |
|---|---|---|
| 1 | 세 대 모두 패널 확인 | `단계: SteamReady` |
| 2 | PC1 `방 만들기` | PC1 `단계: Gathering`, `소유자: 나`, `인원: 1 / 3` |
| 3 | PC2·PC3을 로비에 넣는다 | 아래 8.3.1 참조 |
| 4 | 참가 완료 | **세 대 모두** `인원: 3 / 3`. PC2·PC3은 `소유자: <PC1 SteamID>` |
| 5 | 3번까지 PC1의 `호스트 시작` 버튼 상태 | 회색 + `인원이 덜 모였다`. PC2·PC3은 `소유자만 시작할 수 있다` |
| 6 | PC1 `호스트 시작` | 로그 순서가 **`세션 게시` → `접속 신호 발송`** |
| 7 | PC2·PC3 자동 접속 | `호스트 ...에 접속한다` → 호스트 로그에 `승인: ... source=Steam`이 **3줄**(자기 포함) |
| 8 | 역할 확인 | Sword / Bell / Bow 중복 없음 |

#### 8.3.1 참가 방법 세 가지

설계안 6.2가 정한 참가 경로다. **개발 빌드에서는 오버레이 초대가 대개 동작하지 않는다** —
Steam 오버레이는 Steam이 실행한 프로세스에만 주입되는데, `steam_appid.txt`로 띄운 빌드는
Steam이 실행한 것이 아니다. `ActivateGameOverlayInviteDialog`는 이때 실패도 예외도 없이 그냥 아무 일도 안 한다.

패널이 오버레이 가용 여부를 보고 버튼을 바꾼다.

| 방법 | 언제 | 방법 |
|---|---|---|
| **로비 ID 직접 참가**(가장 확실) | 오버레이가 없을 때. 개발 빌드의 기본 경로다 | PC1 패널의 `로비 ID 복사` → 그 값을 PC2·PC3에 전달 → 각자 `로비 ID로 참가` 칸에 넣고(`붙여넣기` 버튼 있음) `참가` |
| **SteamID로 직접 초대** | 초대 경로 자체를 검증할 때 | PC1 패널의 `SteamID로 초대` 칸에 상대 SteamID64를 넣고 `초대 보내기`. **오버레이 없이 동작한다.** 받는 쪽은 Steam 클라이언트 알림으로 받고, 수락하면 참가 콜백 또는 `+connect_lobby`로 이어진다 |
| 실행 인자 | 스크립트로 반복 테스트할 때 | `gemeum.exe -steam +connect_lobby <로비 ID>` |
| 오버레이 초대 | 오버레이가 살아 있을 때만 | 패널에 `친구 초대` 버튼이 보이면 쓸 수 있다 |

로비 ID는 `109775...`로 시작하는 18자리, SteamID64는 `7656119...`로 시작하는 17자리다.

**오버레이가 안 뜬다고 초대 기능 자체가 없는 것은 아니다.** 오버레이는 친구를 고르는 창일 뿐이고,
초대 전송은 `InviteUserToLobby`가 따로 한다. 상대 SteamID를 알면 오버레이 없이 보낼 수 있다.
`초대 전송에 실패했다` 로그가 뜨면 친구 관계가 아니거나 SteamID가 틀린 것이다.

### 8.4 특히 봐야 할 것

에디터 한 대로 확인할 수 없어 여기서만 드러나는 것들이다.

| 확인 | 왜 여기서만 보이나 |
|---|---|
| `승인` 로그의 `platformId`가 **각자 다른 SteamID64** | 한 대에서는 신원이 하나뿐이라 중복 판정을 못 본다 |
| 로그 순서가 `세션 게시` → `접속 신호 발송` | 뒤집히면 받는 쪽이 빈 `nonce`를 읽어 `StaleSession`으로 거부된다 |
| 초대 수락으로 인원이 실제로 늘어남 | `GameLobbyJoinRequested_t` 콜백은 상대가 있어야 온다 |
| 소유자가 아닌 PC에서 공용 데이터 쓰기가 막힘 | 소유자 판정은 멤버가 2명 이상이어야 의미가 생긴다 |
| 재접속 시 자리·역할 복구 | 신원이 `conn.address`(SteamID64)로 유지되는지가 핵심이다 |

### 8.5 막혔을 때 보는 곳

로그는 `<exe 폴더>/logs/`에 남는다.

| 증상 | 원인 |
|---|---|
| 로비 패널이 안 뜬다 | `KCP 경로로 시작한다`가 찍혔으면 `-steam` 인자가 안 들어갔다 |
| `단계: Offline`에서 안 바뀐다 | Steam 클라이언트 미실행 또는 `steam_appid.txt` 누락 |
| `친구 초대` 버튼이 없고 `오버레이 없음`이 뜬다 | 정상이다. 개발 빌드에서 흔하다. 8.3.1의 로비 ID 참가를 쓴다 |
| 초대해도 인원이 안 는다 | 친구 관계 확인. `game` 키가 다르면 남의 480 로비다 |
| 로비 ID로 참가해도 안 들어간다 | 로그의 `로비 참가 거부: <사유>`를 본다. `Full`이면 정원, `NotAllowed`면 Private 로비 권한이다 |
| `호스트 시작`이 계속 회색 | 소유자가 아니거나 인원 미달. 패널 아래 문구가 이유를 말한다 |
| `거부(StaleSession)` | `nonce` 불일치. 호스트 로그의 게시 순서를 본다 |
| `거부(NotLobbyMember)` | 접속자가 로비 멤버가 아니다. 4번에서 세 대 모두 `3 / 3`이었는지 다시 본다 |
| `인증 메시지의 SteamID가 접속 주소와 다르다` | `conn.address`가 SteamID64로 오지 않는다. 트랜스포트 설정을 본다 |
| 호스트가 자기 자신을 거부 | 게시가 `StartHost`보다 뒤에 있다 |

### 8.6 기록

5장 형식에 아래를 더한다.

```markdown
- Steam 경로: 로비 ID __, 호스트 SteamID __, 참가 경로(초대 수락 / +connect_lobby)
- 승인된 platformId 3개: __ / __ / __
- 거부가 발생했다면 코드와 사유: __
```

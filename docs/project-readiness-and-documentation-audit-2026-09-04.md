# 프로젝트 진행 가능성 및 문서 체계 감사

- 검토일: 2026-09-04
- 기준 브랜치: `feature/Minsung`
- 기준 커밋: `6a429e1` (`origin/develop`과 동일)
- 검토 범위: `CLAUDE.md`, `README.md`, `CONTRIBUTING.md`, `docs/` 전체 목록과 핵심 설계·실행·검증·라이선스 문서, 현재 코드·씬·데이터 자산의 교차 확인
- 판정 기준: 구현자가 추가 구두 설명 없이 같은 결론에 도달할 수 있는가, 현재 저장소 상태와 일치하는가, 검증과 출시 조건이 실행 가능한가

## 1. 결론

**현재 계획은 방향 자체는 타당하지만, 문서에 적힌 그대로 여러 담당자가 병렬 구현을 시작하는 것은 권장하지 않는다. 판정은 `조건부 진행 가능(Conditional Go)`이다.**

권한 경계, 씬·메타 파일 안전 규칙, 데이터 주도 설계, 멀티플레이 검증 원칙은 잘 정리되어 있다. 반면 핵심 계약인 시간축, 결계 동작, 조준 방식, 보스 체력·패턴, 실제 씬 구성, 네트워크 전송 계층이 문서마다 다르다. 일부 실행 계획은 이미 반영된 수정을 미착수로 표시하고 있으며, 과거안과 최신안이 같은 문서 안에서 동시에 구현 지시처럼 남아 있다.

따라서 다음처럼 판단한다.

| 범위 | 판정 | 조건 |
|---|---|---|
| 기존 전투·네트워크 코드의 작은 수정 | 진행 가능 | 현재 코드와 담당 파일을 먼저 확인하고 L3 검증 수행 |
| 결계·조준·보스의 신규 구현 | 일시 보류 | 이 문서의 D-P0-1~4를 먼저 확정 |
| 팀 단위 주차 계획 실행 | 조건부 진행 | 실제 완료 상태를 재반영하고 W1 종료 시 범위 축소 게이트 적용 |
| 포트폴리오/수업 제출 빌드 | 조건부 불가 | 최소 수직 슬라이스와 제3자 자산 증빙 완료 필요 |
| Steam 배포 빌드 | 현재 불가 | 라이선스, 전체 루프, Steam 경로 검증, 출시 정책 확정 필요 |

가장 먼저 고쳐야 할 것은 문서의 양이 아니라 **정답이 하나만 존재하도록 만드는 것**이다. 아래 네 계약을 1~2일 안에 확정하면 구현은 계속 진행해도 된다.

1. 런 전체 시간축과 모든 구간 경계
2. 결계 중심·외부 적 처리·회복 인터페이스
3. 자유 조준만 사용할지, 폐기된 락온/유도 조준을 완전히 제거할지
4. 보스 체력 모델, 페이즈 진입 조건, 패턴별 패링 가능 여부

## 2. 사실, 판단, 미확인 사항

### 2.1 확인된 사실

- 저장소는 검토 시점에 변경 사항이 없고, 현재 브랜치와 `origin/develop`이 같은 커밋을 가리킨다.
- Unity 버전은 `6000.4.7f1`이며 최상위 문서와 실제 프로젝트 설정이 일치한다.
- 프로젝트 소유 C# 파일은 주로 Common, Network, Combat, AI에 있고 Systems와 Art에는 현재 C# 구현이 없다.
- 실제 씬에는 `Dev_Title`, `Dev_Lobby`, `Dev_Combat`, `Main` 등이 있으나 여러 문서가 지시하는 `Dev_System.unity`, `Dev_Art.unity`, `Boss_Arena.unity`는 존재하지 않는다.
- FizzySteamworks와 Steamworks.NET이 이미 패키지와 코드에 포함되어 있다. KCP 전용으로 설명하거나 Fizzy를 미래 검토 항목으로 둔 문서는 현재 상태와 다르다.
- 현재 코드에는 이미 반영된 수정이 있다. 예: 플레이어 표시 방향 기반 공격, `StartRun()` 실패 반환과 로비 롤백, 로비 복귀 시 시뮬레이션 재활성화.
- 반면 적 공격 거리 재검증과 장귀 패링 창 연결은 아직 열린 핵심 위험이다.
- `BossPatternSO`의 페이즈·패턴과 `TalentTreeSO`의 노드가 비어 있다.
- 저장소 내부 상대 Markdown 링크 검사에서는 깨진 링크가 발견되지 않았다.
- 제3자 자산 대장의 대부분은 출처·라이선스가 `미확인` 상태다.

### 2.2 이 보고서의 판단

- 문서 구조와 안전 규칙은 좋지만 최신성 및 단일 진실 공급원 관리가 약하다.
- 현재 주차 계획의 총 작업량과 개인별 시간은 낙관적이다. 모든 달력 날짜를 사실상 가용 시간으로 보는 계산은 구현·통합·재작업 비용을 충분히 반영하지 못한다.
- 시스템, 아트, 보스가 비어 있는 상태이므로 현재 빌드는 완성 루프가 아니라 기반 기능이 모인 단계에 가깝다.
- 지금 가장 큰 위험은 설계 부재보다 서로 다른 설계를 각자 정답으로 구현하는 것이다.

### 2.3 아직 확인이 필요한 사항

- 11월 16일 목표가 수업/포트폴리오 제출인지, 외부 공개 데모인지, Steam 상용 출시인지
- 보스가 각 페이즈별 독립 체력 풀을 갖는지, 총체력 하나를 비율로 나누는지
- `Boss_Arena`를 새 씬으로 만들지 `Main` 내부 구간으로 구성할지
- WeatherMaker 참조가 팀 외부 의존성을 포함하는지와 재현 가능한 설치 절차
- 모든 유료/무료 에셋의 실제 구매 계정, 취득일, EULA 증빙 보관 위치

## 4. 잘 되어 있는 부분

### 4.1 작업 안전성과 소유권

`CLAUDE.md`, AI 실행 정책, 씬·자산 안전 문서는 담당 영역, `.meta`, 씬 저장, LFS, 외부 패키지 변경을 명시적으로 다룬다. 여러 명과 AI가 같은 Unity 프로젝트를 다룰 때 흔히 발생하는 손상을 예방하는 데 충분히 실용적이다.

### 4.2 검증 수준의 명시

L3는 단순 컴파일이 아니라 호스트·클라이언트 실제 동작 확인을 요구하고, M2는 여러 인스턴스 검증을 요구한다. 네트워크 게임에서 중요한 권한·동기화 문제를 문서 단계에서 강제하는 점이 좋다.

### 4.3 데이터 주도 설계

전투 수치, 결계 단계, 보스 패턴을 ScriptableObject로 분리하려는 방향은 튜닝과 담당 분리를 돕는다. 수치와 코드 동작을 분리하려는 큰 방향은 유지하는 것이 좋다.

### 4.4 구체적인 승인 기준

최신 보스 연출·체험판 문서는 타임아웃, 실패 처리, 전환 조건 등 경계 상황을 비교적 구체적으로 적는다. 이런 형식을 핵심 시스템 문서 전체로 확장하면 품질이 빠르게 좋아질 수 있다.

### 4.5 링크 무결성

검토 시점에 저장소 내부 상대 링크가 깨진 사례는 없었다. 문서 이동 시 링크 검사를 자동화하면 이 장점을 유지할 수 있다.

## 5. 중대 문서 문제와 개선 우선순위

### D-P0-1. 런 시간축이 문서마다 다름

**근거**

- 시스템 설계: `0~10`, `10~19`, `19~25`, `25~26`, 보스 `26~40`
- 게임 설계 일부: 2차 수축 `20~29.5`, 상점 `12~15`, 단계 구분 `0~20 / 20~29.5`
- 실행 계획 일부: `10 / 20 / 29:30`
- 아키텍처 표: 1차 수축 종료 `20`과 2차 수축 시작 `19`가 겹침
- README: `0~7 / 7~12 / 12~15 / 15+`

**영향**

결계, 상점, 스폰, 연출, 보스 진입을 서로 다른 시간으로 구현할 수 있다. 이는 네트워크 상태 전환과 레벨 배치까지 번지는 통합 오류다.

**개선**

`docs/01-system-design.md`의 단일 표를 유일한 규범으로 지정하거나 새 `RUN_TIMELINE_CONTRACT.md`를 만든다. 다른 문서에는 수치를 복제하지 말고 링크만 둔다. 런타임 값은 `BarrierPhaseSO`에서 읽고 다음 불변 조건을 자동 검증한다.

```text
phase[i].start < phase[i].end
phase[i].end == phase[i+1].start
shopOpen >= runStart
bossStart > finalShrinkEnd
runEnd >= bossStart
```

**완료 기준**

- 모든 활성 문서에서 동일한 시간축만 검색됨
- 해당 SO 검증기가 잘못된 구간을 저장/빌드 전에 차단함
- M2에서 호스트와 클라이언트의 단계 전환 시각이 일치함

### D-P0-2. 결계 계약이 최신 결정과 충돌함

**근거**

최신 결정은 동적 중심과 결계 밖 적의 안쪽 이동을 지시한다. 반면 기술·아키텍처·결계 설계 문서의 활성 본문은 고정 중심과 외부 적 비활성화를 지시한다. 결계 회복 인터페이스 예시도 실제 코드의 `IsDead`, `TryRestoreHealth(float)`와 다르다.

**영향**

AI, 전투, 시스템 담당자가 서로 반대 동작을 구현할 수 있다. 회복 계약 불일치는 컴파일 오류 또는 중복 인터페이스를 유발한다.

**개선**

결계 문서 첫 부분에 다음 계약을 확정하고, 충돌하는 본문은 삭제하거나 `역사적 초안`으로 이동한다.

- 중심 계산 주체와 업데이트 주기
- 중심 후보가 없을 때의 대체 규칙
- 외부 플레이어, 다운 플레이어, 적, 투사체의 각 처리 방식
- 경계에 걸친 대상의 판정 기준
- 실제 `IRecoveryTarget` 시그니처와 서버 권한
- 클라이언트가 받는 표현 이벤트와 재접속 시 복구 방식

**완료 기준**

- `BARRIER_INVENTORY_SHOP_DESIGN.md`, 기술 설계, 아키텍처가 같은 계약을 참조함
- 외부 적을 `비활성화`하라는 활성 지시가 남아 있지 않음
- 실제 인터페이스 이름과 문서 예제가 일치함

### D-P0-3. 자유 조준과 폐기된 락온/유도 조준이 같은 문서에 공존함

**근거**

조준 보정 문서 상단은 락온을 폐기하고 자유 조준만 사용한다고 선언한다. 그러나 본문에는 `LockOnSystem`, 후보 대상 ID, 화살 유도, 호밍 튜닝, 관련 구현 단계와 검증 항목이 여전히 실행 지시로 남아 있다. 기술·아키텍처 문서도 폐기된 타입을 현재 구조처럼 설명한다.

**영향**

불필요한 네트워크 메시지와 타깃 선택 코드를 다시 도입할 수 있다. 공격 방향 버그를 이미 수정한 현재 코드와도 충돌한다.

**개선**

활성 문서는 자유 조준 계약만 남긴다.

- 입력 방향이 없으면 표시 방향 사용
- 화살 발사 후 호밍 없음
- 서버는 발사 방향과 비용·쿨다운·상태를 검증
- 카메라/조준 UI 보정은 로컬 표현이며 권한 판정에 사용하지 않음

폐기된 락온 설계는 `docs/archive/`로 옮기고 파일명과 상단에 `폐기됨`을 표시한다.

**완료 기준**

- 활성 문서에서 `LockOnSystem`, `ArrowGuidance`가 구현 요구로 검색되지 않음
- `PLAYER_ATTACK_DESIGN.md`의 알려진 한계가 현재 코드와 일치함

### D-P0-4. 보스 체력·페이즈·패링 규칙이 구현 불가능할 정도로 충돌함

**근거**

- 보스 문서의 최신 표와 오래된 본문에서 `TargetedDash`의 패링 가능 여부가 다름
- 페이즈 진입을 체력 50%로 설명하는 부분과, 1페이즈/2페이즈를 독립 체력처럼 설명하는 부분이 공존함
- 최신 총체력 후보 `55,000`과 주차 계획의 `25,000`, 과거 문서의 `3,000`이 함께 남아 있음
- 실제 `BossPatternSO`의 페이즈와 패턴은 비어 있음

**영향**

체력 UI, 패턴 스케줄러, 사망 판정, 연출 전환, 밸런스가 모두 다른 모델을 전제로 구현될 수 있다.

**개선**

보스 계약표 한 장에서 다음을 확정한다.

| 결정 항목 | 반드시 하나를 선택 |
|---|---|
| 체력 모델 | 총체력 단일 풀 / 페이즈별 독립 풀 |
| 2페이즈 진입 | 절대 체력 / 체력 비율 / 1페이즈 풀 소진 |
| 총체력과 페이즈 체력 | 정확한 값과 튜닝 허용 범위 |
| 패턴별 패링 | 가능/불가와 성공 효과 |
| 패턴 선택 | 가중치, 연속 사용 제한, 최소·최대 간격 |
| 전멸·시간 초과 | 결과 상태와 로비 복귀 방식 |

과거 본문을 남겨야 한다면 활성 문서 안이 아니라 결정 기록으로 분리한다.

**완료 기준**

- 보스 문서, 게임 설계, 주차 계획이 같은 숫자를 사용함
- `BossPatternSO`에 최소 수직 슬라이스 패턴이 채워짐
- 보스 한 사이클을 M2에서 재현 가능함

### D-P1-1. 실행 계획의 완료 상태가 실제 코드보다 오래됨

**근거**

주차 계획은 공격 방향, `StartRun()` 실패 처리, 로비 롤백 등을 미착수로 적지만 기준 커밋의 코드에는 이미 반영되어 있다. 반대로 장귀 패링 연결과 공격 거리 재검증은 여전히 실제 위험이다.

**개선**

작업 항목마다 다음 필드를 둔다.

```yaml
status: todo | in_progress | code_done | verified | blocked | superseded
verified_at_commit: <sha 또는 null>
verification_level: L0 | L1 | L2 | L3 | M2
evidence: <테스트/영상/로그/PR 링크>
owner: <GitHub handle>
```

`code_done`과 `verified`를 분리해야 “코드가 있음”을 “완료됨”으로 오인하지 않는다.

### D-P1-2. 실제 씬 구조와 온보딩 문서가 다름

**근거**

README와 여러 안전·검증 문서는 존재하지 않는 `Dev_System.unity`, `Dev_Art.unity`를 가리킨다. 실제 시스템 씬은 `Dev_Title.unity`, `Dev_Lobby.unity`로 나뉜다. `Boss_Arena.unity`는 계획 상태지만 일부 문맥에서는 현재 자산처럼 읽힌다.

**개선**

씬 표에 `현재/계획` 열을 추가하고 실제 경로를 기준으로 갱신한다. 새 씬을 만들기 전에는 계획 문서에서만 `planned`로 표시한다. README의 캐릭터 설명과 문서 개수도 현재 상태로 고친다.

### D-P1-3. 네트워크 전송 계층 설명이 실제 구현과 다름

**근거**

최상위 지침과 기술 설계는 KCP를 중심으로 설명하고 FizzySteamworks를 미래 검토 대상으로 둔다. 실제 프로젝트에는 두 Steam 패키지와 전송 계층 선택 코드, 로비·인증 코드가 있다.

**개선**

다음처럼 실행 환경별 경로를 명시한다.

| 환경 | 전송/서비스 | 목적 | 필수 검증 |
|---|---|---|---|
| 로컬 개발 | KCP | 빠른 반복, 단일 PC 테스트 | L3, M2 |
| Steam 테스트/배포 | FizzySteamworks + Steamworks.NET | 로비·초대·배포 경로 | 두 Steam 계정/환경의 M2 |

전송 계층 선택 실패와 Steam 미실행 시 대체 동작도 계약에 포함한다.

### D-P1-4. 멀티플레이 테스트 프로토콜이 최신 생존·부활 규칙을 반영하지 않음

**근거**

테스트 문서는 자동 부활과 같은 위치 부활을 중심으로 작성되어 있으나 최신 설계에는 팀 부활, 원형 경계 보정, 삼켜짐 상태가 추가되어 있다. 보스 전실 전환, 늦은 로드, 매니저 지속성, 체험판의 리더보드 제외도 부족하다.

**개선**

다음 M2 시나리오를 필수로 추가한다.

- 서로 다른 핑에서 결계 단계 전환과 동적 중심 일치
- 경계 밖 사망, 팀 부활, 자동 부활, 90% 반경 복귀 위치
- 삼켜짐 중 피격·사망·연결 해제·부활
- 상점 진입과 이탈 중 연결 해제/재접속
- `Main → Antechamber → Boss` 전환 시 NetworkManager 중복 없음
- 늦게 들어온 클라이언트의 현재 페이즈·보스 상태 복구
- 체험판 모드 종료 후 리더보드 기록 미생성

### D-P1-5. 제3자 자산 증빙이 배포 기준을 충족하지 않음

**근거**

제3자 자산 대장의 다수가 `미확인`이며, 자체 정책상 미확인 자산은 제출·배포 빌드에 포함할 수 없다. 사운드 문서는 라이선스 디렉터리가 비어 있다고 설명하지만 실제로는 대장 파일이 존재한다.

**개선**

모든 자산에 다음을 채운다.

- 제작자와 원본 URL
- 에셋/음원 이름과 버전
- 취득일 및 취득 계정
- 적용 EULA/라이선스 원문 또는 캡처 보관 위치
- 상업적 사용, 수정, 재배포, 크레딧 요구 여부
- 프로젝트 내 실제 사용 경로
- 제거/대체 담당자와 기한

Suno 관련 문구도 최신 공식 정책을 기준으로 수정해야 한다. 유료 플랜에서 생성된 콘텐츠의 상업적 이용 권리는 생성 시점의 구독 상태에 좌우되며 과거 무료 플랜 생성물에 소급되지 않는다. 또한 현재 가격표는 stem 기능을 Premier 전용으로만 설명하지 않는다. 다운로드 한도와 권리 문구는 변경될 수 있으므로 생성일별 증빙을 함께 보관한다.

- [Suno Terms of Service](https://suno.com/terms/)
- [Suno Pricing](https://suno.com/pricing)
- [Suno Terms 업데이트 안내](https://suno.com/blog/suno-updates-tos)
- [상업적 이용 권리의 비소급 안내](https://help.suno.com/en/articles/2425729)

### D-P1-6. 저장 데이터 정책에 첫 예외가 생겼으나 최상위 계약에 반영되지 않음

**근거**

최상위 지침은 지속 데이터가 리더보드뿐이라고 설명한다. 보스 체험판 문서는 처음에는 저장하지 않는다고 하면서 뒤에서는 `PlayerPrefs` 기반 해금 값을 제안한다.

**개선**

둘 중 하나를 명시적으로 선택한다.

1. 체험판 해금을 저장하지 않고 개발 플래그 또는 항상 개방으로 운영
2. `BossTrialUnlocked`를 리더보드 외 유일한 허용 예외로 최상위 정책에 추가하고 버전·삭제·키 충돌 규칙을 정의

### D-P1-7. 일정 문서가 가용 시간을 확정 사실처럼 사용함

**근거**

현재 계획의 “시간은 제약이 아니다”라는 결론은 달력상 거의 모든 날을 예정 시간만큼 사용할 수 있다는 가정에 의존한다. 통합, 학습, 에셋 재작업, L3/M2 실패 비용이 별도 버퍼로 충분히 보이지 않는다. 팀 리드에게 구현·통합·아트·오디오가 집중되어 있다.

**개선**

- 가용 시간은 W0/W1 실제 처리량이 나오기 전까지 `미검증 가정`으로 표시
- 각 주 작업량의 25~35%를 통합·검증·재작업 버퍼로 예약
- W1부터 누적 게이트를 적용하고 실패하면 즉시 범위 축소
- 팀 리드가 독점하는 통합 작업과 승인 작업을 별도 용량으로 계산
- “완료 시간”보다 “검증 완료한 수직 슬라이스 수”를 진척 지표로 사용

### D-P2-1. 문서 버전과 상태 표기가 신뢰를 떨어뜨림

핵심 문서 일부는 9월 변경을 포함하면서도 `v0.3`, 최종 수정 `2026-08-23`을 표시한다. 한 파일 안에 예전 상태표와 최신 상태표가 겹치고, 상단 경고문이 아래의 구체적 지시를 덮어쓰는 방식이 반복된다.

**개선**

모든 활성 설계 문서에 동일한 머리말을 사용한다.

```yaml
status: active | draft | superseded | archived
owner: <GitHub handle>
last_verified: 2026-09-04
verified_at_commit: 6a429e1
source_of_truth_for:
  - <이 문서가 책임지는 계약>
supersedes:
  - <이전 문서 또는 섹션>
related_decisions:
  - <ADR 링크>
```

새 결정이 이전 본문을 바꾸면 상단에 덧붙이지 말고 본문을 실제로 갱신한다. 과거 논의가 필요하면 ADR 또는 archive에 보관한다.

### D-P2-2. AI 지식 맵이 이미 결정된 내용을 미정으로 표시함

AI 지식 맵은 부활 조정이 없고, 보스 패턴·사운드 방향이 미정이라고 적지만 이후 문서에서 결정되었다. AI가 첫 진입점으로 읽는 파일이므로 오래된 한 줄이 여러 잘못된 구현을 낳을 수 있다.

**개선**

AI 지식 맵은 상세 수치를 복제하지 말고 현재 규범 문서 링크와 상태만 유지한다. 주차 계획 갱신 시 같은 체크리스트에서 함께 갱신한다.

### D-P2-3. 복구 명령이 사용자 변경을 덮어쓸 수 있음

일부 협업 문서는 실수로 저장한 씬을 바로 Git 명령으로 되돌리는 예를 든다. 다른 작업자의 미커밋 변경과 섞인 경우 손실 위험이 있다.

**개선**

먼저 해당 파일의 변경 내용을 확인하고, 변경 소유자가 분명한 경우에만 선택적으로 복구하도록 문구를 바꾼다. 변경이 섞였으면 담당자에게 알리고 수동 분리한다.

## 6. 실제 프로젝트 준비도

| 영역 | 현재 판단 | 주요 근거 | 다음 통과 조건 |
|---|---|---|---|
| 네트워크/로비 | 부분 준비 | KCP와 Steam 경로 코드 존재, 로비 흐름 있음 | 두 경로 M2 회귀 테스트와 문서 동기화 |

| 결계/런 흐름 | 설계 충돌 | 최신 계약과 기존 기술 문서 불일치 | D-P0-1, D-P0-2 확정 후 수직 슬라이스 |

현재 단계에서 “핵심 기반이 전혀 없다”는 평가는 맞지 않는다. 그러나 “계획대로 조립만 하면 된다”는 평가도 맞지 않는다. 실제 통합 난이도는 결계와 씬 전환을 붙인 첫 수직 슬라이스에서 확인해야 한다.

## 7. 권장 문서 구조

### 7.1 문서 계층

```text
CLAUDE.md
└─ 프로젝트 불변 규칙과 작업 안전 정책
   └─ docs/00-reading-guide.md
      ├─ contracts/       현재 구현을 구속하는 단일 계약
      ├─ plans/           일정, 담당, 상태, 검증 증거
      ├─ decisions/       왜 그렇게 결정했는지 기록한 ADR
      ├─ operations/      빌드, 멀티플레이 테스트, 배포 절차
      ├─ licenses/        외부 자산 및 증빙
      └─ archive/         폐기되거나 대체된 과거 문서
```

기존 파일을 당장 모두 이동할 필요는 없다. 먼저 각 파일에 `active/draft/superseded/archived`를 표시하고, 활성 문서의 책임 범위만 중복되지 않게 나누는 것이 안전하다.

### 7.2 단일 진실 공급원 표

| 계약 | 권장 유일 문서 | 다른 문서가 할 일 |
|---|---|---|
| 런 시간축 | 시스템 설계 또는 전용 Timeline Contract | 링크만 제공 |
| 전투 수치 | `CombatConfigSO` 스키마와 데이터 자산 | 숫자 복제 금지 |
| 결계 동작 | Barrier Contract | 개요와 링크만 제공 |
| 보스 체력·패턴 | Boss Contract | 연출 문서는 이벤트만 참조 |
| 씬 목록 | Scene Inventory | 현재/계획 상태를 참조 |
| 네트워크 경로 | Network Runtime Contract | 테스트 문서는 시나리오만 정의 |
| 주차 상태 | Weekly Plan | 설계 문서에 진행률 기록 금지 |
| 자산 권리 | Third-Party Asset Register | 개별 문서는 등록 번호만 참조 |

### 7.3 문서 변경 체크리스트

핵심 계약을 바꾸는 PR은 다음을 확인한다.

- [ ] 이 결정의 단일 진실 공급원을 지정했다.
- [ ] 이전 활성 본문을 실제로 삭제·수정하거나 archive로 이동했다.
- [ ] README, 읽기 가이드, AI 지식 맵의 링크/상태를 갱신했다.
- [ ] 코드·SO·씬의 실제 이름과 경로를 확인했다.
- [ ] 주차 계획의 상태와 검증 커밋을 갱신했다.
- [ ] 네트워크 동작이면 L3/M2 시나리오를 갱신했다.
- [ ] 외부 자산이면 라이선스 대장을 갱신했다.
- [ ] 상대 링크와 문서 내 금지된 과거 용어를 자동 검사했다.

## 8. 48시간 문서 정비 계획

### 1단계: 구현 차단 계약 확정 — 2~3시간

팀 리드와 담당자가 D-P0-1~4의 선택지만 확정한다. 문장 다듬기보다 정확한 값과 동작을 먼저 결정한다.

산출물:

- 런 시간축 1표
- 결계 계약 1표
- 자유 조준 계약 1표
- 보스 계약 1표

### 2단계: 활성 문서 정리 — 4~6시간

- 충돌 본문을 수정하고 과거안을 archive/ADR로 분리
- 기술 설계·아키텍처에서 실제 클래스와 SO 이름으로 교체
- 실제 씬 목록, KCP/Steam 경로, 저장 정책 반영
- AI 지식 맵과 읽기 가이드 갱신

### 3단계: 계획 재기준선 설정 — 2~3시간

- 이미 반영된 P0/P1 항목을 `code_done` 또는 `verified`로 재분류
- 열린 위험인 적 거리 재검증과 장귀 패링 연결을 최상단으로 이동
- 모든 작업에 기준 커밋과 검증 수준 추가
- W1 누적 게이트와 범위 축소 조건 추가

### 4단계: 자동 점검 — 2~4시간

최소한 다음 검사를 CI 또는 에디터 검증기에 추가한다.

- 상대 Markdown 링크 검사
- 활성 문서의 폐기 용어 검사: `LockOnSystem`, `ArrowGuidance`, 존재하지 않는 씬명 등
- `BarrierPhaseSO` 시간 구간 불변 조건
- 비어 있는 필수 `BossPatternSO`, `TalentTreeSO` 차단
- 배포 빌드에 포함된 제3자 자산의 라이선스 대장 누락 검사

## 9. 일정과 범위 운영 개선안

### 9.1 W1 조기 게이트

W1 종료 시 아래가 M2로 통과하지 않으면 바로 범위를 줄인다.

- 두 플레이어가 로비에서 런을 시작함
- 결계가 한 단계 이상 전환되고 양쪽에서 같은 상태로 보임
- 적이 결계 규칙에 따라 이동함
- 한 플레이어가 다운되고 팀/자동 부활 중 최소 한 경로가 동작함
- 상점 또는 보스 전실 중 하나로 전환됨

### 9.2 최소 수직 슬라이스

11월 목표 빌드의 최소 범위를 다음으로 고정하는 편이 안전하다.

1. 타이틀과 2인 로비
2. 전투 가능한 한 구역
3. 결계 2단계와 적 2종
4. 다운/부활 한 세트
5. 상점 구매 1종 또는 특성 1종
6. 보스 전실과 보스 패턴 2종
7. 성공/실패 후 로비 복귀
8. 필요한 자산 100% 라이선스 증빙

이 루프가 통과하기 전에는 추가 적, 추가 특성, 복잡한 시네마틱, 고급 오디오 변형을 확대하지 않는다.

### 9.3 범위 축소 순서

일정이 밀릴 때 다음 순서로 줄인다.

1. 보스 패턴 수와 연출 변형
2. 특성/상점 선택지 수
3. 적 변형과 웨이브 조합 수
4. 고급 음향 변형과 보조 VFX
5. 체험판 해금 저장

로비→런→보스→결과의 전체 흐름, 네트워크 권한, 라이선스 증빙은 축소 대상이 아니다.

## 10. 출시 목표별 문서 분리

보스 체험판 문서는 비상업적 포트폴리오를 전제로 하지만 저장소에는 Steam 통합과 상업 이용 가능한 자산 정책이 함께 존재한다. 목표를 다음 단계로 분리해 적어야 한다.

| 단계 | 목적 | 필수 품질 |
|---|---|---|
| 내부 개발 빌드 | 기능 검증 | 임시 자산 허용, 외부 공유 금지 |
| 수업/포트폴리오 빌드 | 제한 공개 | 사용 범위가 허용된 자산만, 전체 수직 슬라이스 |
| Steam 테스트 빌드 | 서비스 검증 | Steam M2, 패키징, 계정/초대 흐름 |
| Steam 출시 빌드 | 상용 배포 | 모든 자산 권리 증빙, 안정성, 개인정보/서비스 정책 검토 |

어느 단계를 2026-11-16의 완료로 볼지 한 줄로 확정해야 일정과 라이선스 기준이 흔들리지 않는다.

## 11. 최종 진행 조건

다음 조건을 만족하면 문서 위험 때문에 구현을 멈출 이유는 없다.

- [ ] D-P0-1~4가 단일 계약으로 확정됨
- [ ] 실제 씬과 네트워크 경로가 최상위 문서에 반영됨
- [ ] 주차 계획이 현재 코드 상태와 다시 맞춰짐
- [ ] 열린 코드 위험인 적 공격 거리와 장귀 패링 연결의 담당·검증 기준이 지정됨
- [ ] W1 최소 네트워크 수직 슬라이스 게이트가 일정에 포함됨
- [ ] 제출/배포에 사용할 자산의 라이선스 확인 계획과 담당이 지정됨

이 조건을 충족하기 전에도 독립적인 버그 수정과 프로토타이핑은 가능하다. 다만 결계·조준·보스처럼 충돌이 확인된 영역을 문서 그대로 병렬 구현하는 것은 재작업 가능성이 높으므로 피해야 한다.

## 12. 검토 한계

- 본 감사는 현재 저장소 스냅샷을 기준으로 하며 Unity Editor에서 모든 씬을 직접 플레이한 기능 검증 보고서는 아니다.
- 문서의 구조·내용과 코드·자산 존재 여부를 교차 확인했지만 모든 C# 경로의 런타임 정확성을 보증하지 않는다.
- 외부 서비스 정책은 변경될 수 있다. 특히 생성형 AI 서비스와 에셋 스토어 라이선스는 자산을 취득하거나 배포하는 시점에 공식 원문을 다시 보관해야 한다.
- 이 문서는 기존 설계를 대체하는 규범 문서가 아니라, 어떤 규범을 먼저 확정해야 하는지 제시하는 감사 결과다.

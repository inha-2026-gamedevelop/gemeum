# 디자인 패턴 지도

**2026-09-06 신설.** 이 저장소에 실제로 적용된 패턴이 무엇이고, 각각이 **왜 그 자리에 있는지**를 적는다.

> 이 문서의 목적은 두 가지다.
> 1. **선택 규칙을 남긴다.** 경계를 넘어 알리는 방법이 넷인데 어느 것을 언제 쓰는지가 어디에도 없었다. 3인이 각자 즉흥으로 고르면 그 지점부터 갈라진다.
> 2. **이미 있는 것을 보이게 한다.** 아래 목록을 만들면서 우리 스스로 빌더 하나를 빠뜨렸다. 코드를 처음 읽는 사람은 더 못 본다.

---

## 0. 대원칙 - 패턴이 먼저가 아니다

이 프로젝트에서 패턴을 넣는 근거는 **셋 중 하나여야 한다.**

| 근거 | 예 |
|---|---|
| **지금 있는 중복을 없앤다** | 세 파일이 같은 5단계를 각자 다시 쓰고 있었다 |
| **되돌리면 깨지는 순서를 고정한다** | 자원 차감이 게이트보다 먼저 오면 거부된 요청이 스태미나를 먹는다 |
| **아직 없는 파트를 기다리지 않게 한다** | 결계 구현 전에도 무녀 치유를 만들 수 있다 |

**"패턴을 쓰고 싶어서"는 근거가 아니다.** 아래 표의 "왜 여기에" 칸을 코드로 답할 수 없으면 그 패턴은 빼는 것이 맞다.

---

## 1. 경계를 넘어 알리는 방법 - 선택 규칙

넷 다 쓰고 있고, 넷 다 맞는 자리가 다르다.

| 무엇을 알리나 | 기전 | 왜 |
|---|---|---|
| **내 캐릭터의 이산 전이** | **C# event** | 생명 상태, 락온 걸림/풀림, 무기 교체, 치명타 준비. 드물게 갈리므로 이벤트가 싸다 |
| **내 캐릭터의 연속값** | **프로퍼티 폴링** | 게이지, 남은 시간, 진행도. **매 서버 틱 바뀌는 값에 이벤트를 달면 초당 수십 번 호출이 나가는데 UI가 하는 일은 같다** |
| **주인 없는 세계의 사실** | **`GameEventBus`** | 런 단계 전환, 잡귀 사망, 결계 축소 |
| **구현이 통째로 갈릴 수 있는 협력자** | **정적 로케이터** | 아트의 연출 구현, 결계 판정. 없을 때는 Null Object가 받는다 |
| **갈아 끼울 것이 없는 순수한 값** | **정적 값 채널** | 카메라 각도. 로케이터를 세 번째로 만들 이유가 없다 |

### 1.1 버스에 "내 값"을 싣지 않는 이유

`GameEventBus`는 방향이 없다. `SceneSingleton`이라 서버와 클라이언트 양쪽에 하나씩 떠 있고 `Publish`를 아무나 부를 수 있다.

HP 같은 자기 캐릭터 값을 버스에 실으면 **누구의 값인지 페이로드에 넣어야 하고 받는 쪽이 다시 걸러야 한다.** 3인이면 내 HP 바가 남의 HP 변화를 매번 받아서 버린다. `PlayerStatus.Local`이 이미 하는 일을 더 비싸게 다시 하는 것이다.

**버스는 주인이 없는 사실에만 쓴다.** 이벤트 종류를 늘리는 것 자체가 목표가 아니다.

## 2. 적용된 패턴

### 2.1 생성

| 패턴 | 어디 | 왜 여기에 |
|---|---|---|
| **싱글턴** | `PersistentSingleton<T>` / `SceneSingleton<T>` | 씬을 넘기는 것과 씬에 사는 것을 **타입으로 갈랐다.** 어느 쪽인지 상속만 보면 안다 |
| **팩토리 메서드** | `EnemyController.CreateBrain(EnemyKind)` | 잡귀 종류가 서버에서 정해지고 브레인은 그 뒤에 만들어진다. 호출부가 구체 타입을 몰라야 잡귀가 늘어도 안 고친다 |
| **빌더** | `RunTimelineBuilder.Build(BarrierPhaseSO)` | 런 타임라인을 SO 하나에서 조립한다. 겹침 검증을 조립 시점에 한 번만 한다 |
| **오브젝트 풀** | `LocalObjectPoolService` + `IPoolable` | 로컬 연출 전용. `PresentationPoolPrewarmer`, `PlayerCombatPresentation`, `PooledVisualLifetime`이 사용 |

### 2.2 구조

| 패턴 | 어디 | 왜 여기에 |
|---|---|---|
| **서비스 로케이터** | `CombatFeedbackLocator`, `BarrierStateLocator` | 전투가 아트와 결계의 구현 클래스를 참조하지 않는다. **아직 없는 파트를 기다리지 않고 착수할 수 있다** |
| **널 오브젝트** | `NullCombatFeedback` (로케이터 폴백) | 등록이 없으면 아무것도 안 하는 구현을 돌려주므로 **호출부에 null 체크가 없다** |
| **퍼사드 / 메디에이터** | `LocalCombatState` | UI가 전투 컴포넌트 다섯을 각자 잡는 대신 창구 하나만 안다 -> 아래 2.5 |
| **값 채널** | `CameraFrame` | 카메라 각도와 락온 상태. 오브젝트가 아니라 값만 오간다 -> 아래 2.6 |

### 2.3 행위

| 패턴 | 어디 | 왜 여기에 |
|---|---|---|
| **옵저버** | `GameEventBus` + C# event | 위 1장 |
| **전략** | `EnemyBrainBase` <- `Changgwi` / `Aekgwi` / `Heokkaebi` | 잡귀 종류마다 행동 결정만 다르고 이동, 공격 실행은 `EnemyController`가 공유한다 |
| **템플릿 메서드** | `EnemyBrainBase` (추상 `Tick` + 가상 훅), `PlayerActionPipeline` | 순서는 베이스가 고정하고 각 구현이 빈칸만 채운다 |
| **커맨드** | `IPlayerAction` + 요청 구조체(`ParryRequest`, `PlayerMoveInput`) | 아래 2.4 |
| **상태** | 잡귀 브레인의 `enum` 스위치 | **의도적으로 클래스로 빼지 않았다** - 상태 다섯 개가 단순하다. 보스는 다르다(4장) |

### 2.4 커맨드 + 템플릿 메서드 - 단발 행동 (2026-09-06)

```
TryAccept(requestId) -> 게이트 -> 자원 차감 -> 커밋 -> 거부 사유 반환
```

`PlayerActionPipeline`이 이 순서를 소유하고, `IPlayerAction` 구현체(공격, 구르기)가 빈칸을 채운다.

**왜 넣었나 - 근거는 이미 있던 중복이다.** 공격, 구르기, 패링이 각자 `RequestIdTracker`를 들고 같은 순서를 다시 쓰고 있었다. 순서를 손으로 다시 쓰면 한 단계를 빼먹어도 컴파일이 되고, **실제로 그렇게 났던 적이 있다** - `RequestIdTracker`를 `readonly` 필드로 잡아 방어 복사본이 생기는 바람에 중복 차단이 통째로 동작하지 않았다.

**요청마다 커맨드 객체를 새로 만들지 않는다.** `NetworkBehaviour` 자신이 인터페이스를 구현한다. 전투는 초당 여러 번 도는 경로라 매 입력 GC 할당을 만들면 안 된다.

**거부 사유를 돌려주는 것이 이 변경의 절반이다.** 그전까지 공격과 구르기는 거부되면 조용히 `return`이라 **사람도 로그도 "입력이 씹혔다"와 "거부됐다"를 구분할 수 없었다.** 패링만 `ParryResultCode`로 이것을 하고 있었고, 그 부분을 뼈대로 끌어올렸다.

**패링은 이 뼈대를 지나지 않는다.** 시각 재조정(클라 추정 시각 클램프)과 최소 요청 간격이 뼈대에 없는 단계이고, 무엇보다 0.32초 판정 창은 이미 L2를 여러 번 통과한 코드다. **뼈대에 맞추려고 손대면 그 검증이 통째로 무효가 된다.**

> **패턴 이름을 하나로 우기지 않는다.** 요청 구조체는 커맨드고, 실행 순서는 템플릿 메서드다. 둘 다 맞다.

### 2.5 퍼사드 / 메디에이터 - `LocalCombatState` (2026-09-06)

UI가 전투를 읽는 유일한 창구. **값을 전달만 하는 자리가 아니라 셋을 한 군데서 푼다.**

1. **자기 캐릭터를 언제 잡을 수 있는지.** UI는 스폰보다 먼저 켜져 있을 수 있어 패널마다 null 분기를 다시 쓰게 된다
2. **늦게 구독한 화면에 현재 값을 흘려 주는 것.** `PlayerStatus`는 `RaiseAll`로 이미 하고 있었는데 **락온과 부활에는 없어서, 나중에 열린 패널은 잠긴 대상을 모른 채 시작했다**
3. **사망, 재접속으로 인스턴스가 갈릴 때 구독을 옮기는 것.** 패널마다 하면 언젠가 하나가 파괴된 컴포넌트를 붙들고 있는다

이것으로 **UI 쪽 의존이 다섯에서 하나로** 줄었다.

### 2.6 값 채널 - `CameraFrame`

로케이터를 세 번째로 만들지 않은 자리다. 카메라 각도는 갈아 끼울 구현체가 아니라 그냥 숫자다.

```
yaw    05.Art     -> 00.Common -> 02.Combat
락온   02.Combat  -> 00.Common -> 05.Art
```

**방향이 반대인데 어느 쪽도 상대 어셈블리를 참조하지 않는다.** 카메라가 없는 씬에서는 yaw가 0이라 이동이 지금과 똑같이 동작하고, 카메라를 붙이면 저절로 살아난다.

## 3. 일부러 하지 않은 것

**안 한 이유가 적혀 있지 않으면 다음 사람이 "빠뜨린 것"으로 보고 넣는다.**

| 무엇 | 왜 안 하나 |
|---|---|
| **화살을 오브젝트 풀에 넣기** | **설계상 불가능하다.** `LocalPoolRoot`는 네트워크 개체를 걸러내는 화이트리스트고, 화살은 `NetworkServer.Spawn`으로 뜬다. 네트워크 개체 풀링은 Mirror의 스폰 핸들러를 등록하는 **별개의 작업**이다 |
| **보스 패턴 10종을 클래스로 빼기** | 계약이 **예고 템플릿 4종 x 파라미터**로 축을 고정했다. 10개를 클래스로 빼면 **9개가 서로 복붙**이 된다. 템플릿 4종이 이미 전략 4개다 |
| **잡귀 상태를 클래스로 빼기** | 상태 다섯 개가 단순하고 `enum` 스위치로 읽힌다. **복잡도가 기준이지 일관성이 기준이 아니다** |
| **특성, 장비, 상점에 미리 패턴 잡기** | 패턴은 이미 골라져 있다 - GameDB SO. **더 얹는 것이 과설계다** |
| **이벤트 버스 이벤트 늘리기** | 위 1.1 |
| **패링을 커맨드 뼈대에 넣기** | 위 2.4 |

## 4. 이후 확장 자리

| 패턴 | 어디에 | 언제 |
|---|---|---|
| **상태** | **보스 페이즈** | `BossPhaseStateBase`, `Phase1State`, `Phase2State`로 구현됐다. 새 페이즈를 추가할 때 같은 경계를 유지한다 |
| **데코레이터 또는 책임 연쇄** | **피해, 스탯 수정자** | **특성과 장비 수치가 정해진 뒤.** 지금 깔면 요구가 안 맞을 때 체인을 통째로 뒤집게 된다 |

## 5. 현재 확인 사항

- `RunTimelineBuilder`는 `BarrierPhaseSO`에서 런 타임라인을 만드는 빌더다.
- `BarrierTargetAdapter`는 결계 대상 등록과 수명 주기를 구현한다. 이름만 있는 빈 타입이 아니다.
- 표의 패턴 이름보다 실제 책임 경계와 호출 방향을 우선한다.

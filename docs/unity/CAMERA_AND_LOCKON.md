# 카메라와 락온 — 구현 사양

**2026-09-05 신설.** 조작을 《엘든 링: 밤의 통치자》 기준으로 맞추기로 확정하면서([게임 디자인 2.4](../02-game-design.md)), 카메라·락온·그에 딸린 이동/조준/애니메이션/네트워크를 한곳에 정한다.

> 🔒 **이 문서는 값까지 정한 구현 사양이다.**
> **미확정으로 남긴 것은 다섯 개뿐이고 전부 "화면과 손맛을 봐야 정해지는 값"이다** — 카메라 거리 넷(4.5 / 9.0 / 7.0 / 0.6m)과 신궁 그로기 환율(8). 나머지는 그대로 구현한다.

---

## 0. 왜 이 문서가 생겼나

**사운드 시스템을 리뷰하다 드러났다.** 3D 효과음의 감쇠 거리를 논의하던 중 *"소리를 내는 곳만 얘기했고 듣는 곳은 어디 있는가"*라는 질문이 나왔고, 실측 결과가 이랬다.

```
Main.unity   Main Camera (264.79, 109.53, 131.41)  회전 (4.5°, 136°, 0°)  ← 씬에 고정
             AudioListener가 여기 붙어 있다
Assets/01.Scripts/  "camera" 문자열                 0건                    ← 카메라 코드가 없다
이동 입력    Input.GetAxisRaw(H/V) → 그대로 서버로                        ← 카메라 무관
조준 방향    _presentation.FacingDirection = 마지막 이동 방향             ← 카메라 무관
```

**3D 사운드가 성립하지 않는다.** 감쇠 거리를 어떻게 잡든 귀가 마당 위 109m 한 점에 못 박혀 있다.

**그리고 지금까지 3인 테스트가 통과한 것은 `Dev_Combat` 카메라가 `(0, 8, -8)`이라 좁은 무대에서만 놀았기 때문이다.** `Main`의 768m 맵에서 실제로 뛰어본 적이 사실상 없다.

## 1. 구조와 소유

| | 어디 | 네임스페이스 |
|---|---|---|
| 카메라 리그 구현 | **`05.Art/Camera/`** | `Geumeum.Art` |

| 락온 상태·판정 | `02.Combat/Player/` | `Geumeum.Combat` |

### 1.1 의존 방향 — 오브젝트가 아니라 값을 넘긴다

이동을 카메라 기준으로 바꾸면 `PlayerController`가 카메라의 yaw를 알아야 한다. 그런데 `02.Combat` → `05.Art` 참조는 [8.1 의존 방향](../04-architecture.md) 위반이다.

**로케이터를 세 번째로 만들지 않는다.** `ICombatFeedback`·`IBarrierState`의 로케이터는 *"구현체가 통째로 갈릴 수 있는 것"*에 쓰는 장치다. **카메라 각도는 갈아 끼울 대상이 아니라 그냥 숫자다.**

```csharp
// 00.Common — 카메라가 미는 것은 오브젝트가 아니라 값이다
public static class CameraFrame
{
    public static float Yaw          { get; set; }   // 카메라가 매 프레임 민다
    public static bool  InputEnabled { get; set; }   // UI가 끈다 (아래 8장)

    public static Vector2 ToWorld(Vector2 input);    // 입력 축 → 월드 방향
}
```

**카메라가 없으면 `Yaw`는 0이고 지금과 똑같이 동작한다. 붙으면 저절로 살아난다.**

## 2. 카메라 리그

| 항목 | 값 | 근거 |
|---|--:|---|
| 기본 거리 | **4.5m** ⚠️ | 아래 2.1 |
| 높이 | **1.6m** | 눈높이 |
| 측면 오프셋 | **0.6m** ⚠️ | 오버숄더 — **화면 정중앙이 비어 조준선이 된다** |
| pitch 범위 | **−30° ~ +60°** | 위 30 / 아래 60 |
| 마우스 감도 | X **0.15** · Y **0.12** °/px | **옵션 노출 + Y 반전 옵션** |
| 위치 스무딩 | `SmoothDamp` **0.08초** | |
| 회전 스무딩 | **없음(즉시)** | 스무딩하면 **입력 지연으로 느껴진다** |
| 갱신 시점 | 🔑 **`LateUpdate`** | 아래 2.2 |
| FOV | **60 고정** | 아래 2.3 |

### 2.1 ⚠️ 기본 거리 4.5m — 3.5m는 근거가 없었다

`02-game-design 2.4`가 *"카메라 거리 3.5m, 높이 1.6m"*라고 적고 있었으나 **근거가 없다.**

그리고 오늘 확정한 것 둘이 부딪힌다.

```
무녀 범위 힐 반경 6m — "코옵에서 뭉쳐 다니게 만드는 이유"
카메라 거리 3.5m
```

**6m 안에 셋이 뭉치는데 카메라가 3.5m면 남의 캐릭터가 화면을 채운다.** 설계로 뭉치게 해놓고 뭉치면 안 보이게 만든 셈이다. 4.5m로 올리고, **최소 거리에서는 디더 페이드**로 처리한다(7장).

> **4.5 · 9.0 · 7.0 · 0.6m 넷은 임시값이다.** 화면을 봐야 정해진다. **다만 "근거 없이 박혀서 아무도 안 건드리는 3.5m"보다는 "임시값이라고 적힌 4.5m"가 낫다.**

### 2.2 `LateUpdate`인 이유 — 떨림과 직결된다

```
원격 캐릭터   NetworkTransform이 보간          (Rigidbody 보간 OFF · isKinematic)
내 캐릭터     PlayerPrediction이 Update에서 예측
```

**카메라가 같은 `Update`에서 돌면 실행 순서에 따라 한 프레임 뒤처진다.** `LateUpdate`에서 그 프레임의 모든 이동이 끝난 뒤에 붙인다.

### 2.3 🔒 FOV는 고정한다

달릴 때 FOV가 넓어지는 연출은 흔하지만 **넣지 않는다.**

- 멀미를 만든다
- **패링 창 0.32초를 판단하는 데 방해된다.** 화면이 계속 움직이면 보스 모션을 읽기 어렵다

**같은 이유로 카메라 회전 흔들림도 최대 0.5°로 제한한다**(6장).

## 3. 락온

> 📄 **대상 선택·조준점·유도는 [신궁 화살 조준 보정 설계](ARROW_AIM_ASSIST_DESIGN.md)가 소유한다.** 그 문서가 2026-09-03에 더 정교하게 정해 두었고, **락온 폐기 때 무효 표시됐다가 이번에 되살아났다.** 아래는 그 값을 그대로 옮긴 것이다.

| 항목 | 값 |
|---|---|
| **입력** | **중클릭** 토글 · **휠** 대상 전환 |
| 후보 탐색 거리 / 유지 거리 | **25m / 30m** |
| 후보 탐색 반각 / **유지 반각** | **35° / 55°** |
| 가림 유예 | **0.20초** |
| 선택 순서 | **화면 중심 각도가 작은 순, 같으면 가까운 순** |
| 재탐색 | **락온 버튼을 누른 순간에만.** 유효성 재검사는 10Hz 또는 상태 변화 시 |
| 대상별 카메라 거리 | 잡귀 **4.5** · 보스 몸통 **9.0** · 보스 꼬리 **7.0** m ⚠️ |
| 회전 속도 (락온 중) | **1080°/s** (비락온은 현행 720°/s 유지) |

> 🔧 **2026-09-05 정정 — 이 표의 앞 네 줄은 처음에 다르게 적었다.**
> 획득 각도 45° · 가림 유예 0.5초 · `(각도 0.7 + 거리 0.3)` 가중 점수로 잡았는데, **`ARROW_AIM_ASSIST_DESIGN`을 보지 않고 만든 값이었다.**
> 그 문서 쪽이 낫다 — **각도 히스테리시스(35°/55°)가 있어** 짧은 회피나 카메라 흔들림에 락온이 풀리지 않고, **가중 점수보다 "각도 우선, 동률 시 거리"가 예측 가능하다.**

**입력이 중클릭·휠인 이유** — 우클릭은 이미 세 직업이 나눠 쓰고 있고(차사 패링 · 신궁 정밀 사격 · 무녀 치유), **인게임 무기 교체가 없어 휠이 비어 있다.** 소울즈 관습 그대로다.

**거리와 각도가 획득/유지로 갈리는 이유** — 같으면 경계에서 붙었다 떨어졌다 한다.

**회전을 즉시로 하지 않는 이유** — 대상이 빠르게 돌 때 캐릭터가 뚝뚝 튄다.

### 3.0 🔑 락온은 루트가 아니라 조준점을 향한다

```csharp
public interface IAimAssistTarget { Vector3 AimPoint { get; } }
```

| 대상 | 조준점 |
|---|---|
| 잡귀 | 캡슐 중심보다 위인 가슴. 2m 캡슐 기준 로컬 **Y 1.1m** |
| **보스** | 몸통 anchor + **부위별 anchor** |
| 계약 없는 임시 대상 | collider `bounds.center` 폴백 |

**보스 꼬리 3덩이가 여기에 걸린다.** 꼬리 구간마다 anchor가 있어야 3.2의 *"그로기 진입 시 표식 꼬리로 자동 전환"*이 실제로 그 꼬리를 향한다.

**`PlayerAttack`은 AI의 구체 클래스를 참조하지 않는다** — `00.Common` 계약 또는 collider/`NetworkIdentity`만 쓴다.

### 3.1 대상별 거리 — 안 보이면 못 싸운다

**보스 몸통 락온이 9.0m인 이유는 꼬리 펼침을 화면에 담기 위해서다.** 오버숄더 4.5m에서는 보스 몸통도 다 안 들어온다.

> 🔒 **이것은 연출이 아니라 조작이다.** 안 보이면 싸울 수 없다. [스코프 잠금](../../CLAUDE.md)의 *"프로토타입 단계의 카메라 연출"*에 걸리지 않는다.

### 3.2 자동 전환 — "대상이 사라졌을 때"로만 한정한다

```
대상 사망            → 다음 대상 자동
시야 차단 0.5초 초과  → 다음 대상 자동
꼬리 파괴            → 다음 표식 꼬리 → 없으면 몸통
그로기 진입          → 표식 꼬리로 1회 자동
🔒 살아있는 대상      → 절대 안 옮긴다
```

| 부가 규칙 | 값 | 왜 |
|---|--:|---|
| 재전환 금지 | **1.0초** | 바위 뒤로 들락날락할 때 대상이 계속 바뀌는 것을 막는다 |
| 시야 차단 유예 | **0.20초** | 3장의 값. 기둥 모서리에서 마커가 깜빡이는 것만 완화한다 — **사격 관통을 허용하는 것이 아니다** |

**소울즈에서 사람들이 싫어하는 것은 *"멀쩡히 잠겨 있는데 옮겨가는 것"*이다.** 위 조건에는 그런 경우가 하나도 없다.

**그로기 진입 자동 전환만 예외적으로 "살아있는 대상"을 옮긴다.** 자동 전환이 싫은 이유는 *"원하지 않을 때 옮겨가서"*인데, **그로기 중에는 25% 게이트 때문에 모두가 꼬리를 원한다.** 원하지 않을 가능성이 0인 유일한 순간이다.

## 4. 이동 · 조준 · 구르기

### 4.1 🔑 값 셋으로 가른다

```
지금        FacingDirection 하나에 이동 · 바라봄 · 조준 셋이 묶여 있다
```

락온 스트레이프는 **"옆으로 걸으며 앞을 본다"**라 이동과 바라봄이 달라야 한다.

| 값 | 정의 |
|---|---|
| `MoveDirection` | **카메라 기준으로 변환된** 입력 |
| `FacingDirection` | 락온 중이면 **대상 방향**, 아니면 이동 방향 |
| `AimDirection` | `FacingDirection`을 따른다 |

> **지금 당장은 `AimDirection`이 `FacingDirection`과 늘 같다. 그래도 이름을 가른다.**
> 이름이 하나면 **락온을 붙이는 사람이 어디를 고쳐야 하는지 모른다.**

### 4.2 변환

```csharp
Vector3 world = Quaternion.Euler(0f, CameraFrame.Yaw, 0f) * new Vector3(input.x, 0f, input.y);
```

**변환은 클라이언트가 한다.** 서버는 원래도 방향을 신뢰했고(크기만 `ClampMagnitude`) **예측 구조가 바뀌지 않는다.** 서버가 변환하면 `Yaw`를 함께 보내고 예측에도 넣어야 한다.

> 🚨 **L3 회귀가 필수다.** 서버가 받는 값의 의미가 **"입력 축"에서 "월드 방향"으로 바뀐다.**
> 예측과 서버 재현의 좌표계가 어긋나면 **2026-08-31에 한나절 태운 떨림 버그**가 그대로 재현된다.

### 4.3 ⚠️ 구르기 — 부호 하나가 보스 품으로 굴러들어가게 만든다

| 상황 | 방향 |
|---|---|
| 입력 있음 | 그 방향 (카메라 기준 변환) |
| 입력 없음 · 비락온 | `FacingDirection` (현행 동작) |
| **입력 없음 · 락온** | 🔑 **대상의 반대 방향** (백스텝) |

**락온 중 입력 없는 구르기가 뒤로 가는 것은 소울즈의 핵심이다** — 패링 실패 후 살아나는 유일한 길이다.

**지금 `ResolveRequestedDirection`은 입력 축을 그대로 쓰므로 이 문제가 아직 없다.** `FacingDirection`이 대상 방향이 되는 순간 **부호를 뒤집지 않으면 보스 품으로 굴러들어간다.**

## 6. 카메라 셰이크

**새 계약이 필요 없다.** `ICombatFeedback`이 이미 있고, [04-architecture 4.5](../04-architecture.md)가 셰이크를 `CombatFeedbackImpl`의 몫으로 적어 두었다. **전투는 로케이터만 부르고, 아트 구현체가 카메라 리그에 요청한다.**

| 트리거 | 강도 | 지속 |
|---|--:|--:|
| 피격 `PlayHit(Light)` | 0.06m | 0.12초 |
| 피격 `PlayHit(Heavy)` | 0.12m | 0.18초 |
| **패링 성공** | **0.20m** | 0.15초 |
| 치명타 | 0.15m | 0.15초 |
| 그로기 진입 | 0.25m | 0.30초 |
| 꼬리 파괴 | 0.30m | 0.35초 |

- **위치 흔들림만.** 회전 흔들림은 **최대 0.5°** — FOV를 고정한 것과 같은 이유
- 🔒 **합산 상한 0.30m.** 여러 개가 겹쳐도 넘지 않는다
- 감쇠는 지속시간 동안 선형

> 🔒 **접근성 옵션 필수** — 셰이크 강도 슬라이더 0~100%, **0이면 완전히 끈다.**

**피격이 약하고 패링 성공이 센 이유** — 결과를 알리는 셰이크는 세도 되지만, **다음 패링을 방해하는 셰이크는 약해야 한다.** 패링 창이 0.32초다.

## 7. 카메라 충돌

**"미룬다"는 말이 틀렸다.** 아레나는 **담장 R=22와 마당 R=18의 4m가 이미 카메라 완충으로 설계돼 있어** 충돌 처리 없이 된다. 그러나 **개활맵 768m에 바위 275개는 뚫린다.** 개활이 게임의 30분이다.

| 항목 | 값 |
|---|--:|
| 방식 | `SphereCast` 반경 **0.25m** |
| 레이어 | `Ground` + `Default`(바위) |
| 최소 거리 | **0.8m** |
| 당길 때 | **0.05초 스무딩** |
| 풀 때 | **6 m/s** |
| 최소 거리 도달 시 | **캐릭터 디더 페이드** |

**디더 페이드 셰이더는 2.1의 "뭉친 팀원 가림" 처리와 같은 것을 쓴다.** 카메라와 대상 사이에 들어온 캐릭터를 반투명하게 만든다.

## 8. 커서와 개발 플래그

```csharp
CameraFrame.InputEnabled = false;   // UI가 끈다. 카메라는 이유를 모른다
```

**UI가 끄고 카메라가 읽는다.** 카메라가 UI를 참조하지 않으므로 `05.Art` → `06.UI` 의존이 생기지 않는다.

| 상태 | `Cursor.lockState` |
|---|---|
| 기본 | `Locked` |
| UI 열림 | `None` + `InputEnabled = false` |

### 🚨 개발 플래그 `-nocursorlock` — 테스트를 어렵게 만드는 변경은 그 자체가 위험이다

3인 테스트는 대부분 **한 PC에서 창 세 개**로 한다. 커서를 잠그면 **창 하나가 마우스를 독점해** 나머지 둘이 카메라를 못 돌린다.

**LAN PC 3대를 매번 켜야 하면 테스트 빈도가 떨어지고, 그러면 L3를 덜 하게 된다.** 이 프로젝트의 주된 결함 유형이 *"단일 플레이에서 되는 것이 3인에서 안 되는 것"*이다.

**`NetworkLaunchArgs`에 `-nocursorlock`을 추가한다.** 켜지면 잠금 없이 **Alt 홀드 중에만 카메라 회전** — 유니티 씬뷰와 같아 손에 익는다.

## 10. 컷신 카메라

**필요한 곳은 페이즈 전환 하나뿐이다.**

```
전환 15초 = 컷신 8초 (입력 잠금) + 숨 고르기 7초 (입력 자유)
                                    ↑ 무녀 힐 3회가 여기 걸려 있다
```

상세 타임라인은 [보스 연출 설계 2장](BOSS_STAGING_DESIGN.md)에 이미 있다.

| | |
|---|---|
| 도구 | **Timeline 1.8.12** (설치됨) |
| **Cinemachine** | 🔒 **깔지 않는다** — 2장의 카메라 리그를 통째로 다시 짜야 한다 |
| 동기화 | 서버가 `RpcBeginPhaseCutscene()`, **각자 로컬 재생.** 페이즈 전환은 이미 서버 판정이다 |
| 리그 인계 | **컷신 중 카메라 리그는 꺼지고 Timeline이 잡는다. 끝나면 돌려준다** |

> 🔒 **첫 조우는 컷신으로 만들지 않는다.** [보스 연출 설계](BOSS_STAGING_DESIGN.md)가 *"입력 잠금 0, 엽전 소리 하나로 3인을 동시에 잡는다"*로 확정했다. **소리로 시선을 끄는 것이 그 장면의 전부다.**

## 11. 네트워크

### 11.1 락온은 로컬이 아니다 — 두 번 정정했다

| 시점 | 판단 | 왜 틀렸나 |
|---|---|---|
| 최초 | *"락온은 순수 로컬 표현"* | ❌ |
| 1차 정정 | *"판정에는 안 들어가고 표현에는 들어간다"* | 부분적으로 맞음 |
| **확정** | **표현에도 판정에도 들어간다** | **화살 유도를 넣기로 하면서 궤적이 대상에 의존하게 됐다** |

**바라보는 방향이 동기화돼야 하는 이유** — 남의 화면에서 그 사람이 옳게 서 있어야 한다. **패링이 0.32초인 게임에서 차사가 보스를 보고 자세를 잡는 것이 안 보이면 남들은 아무것도 예측할 수 없다.**

### 11.2 🔑 SyncVar를 늘리지 않고 승격한다

```csharp
// 지금 — 속력만 오고 방향이 없다. "바라보는 방향 = 이동 방향"이었으므로 문제가 없었다
[SyncVar] private Vector2 _serverFacing = Vector2.up;
[SyncVar] private float   _serverSpeed  = 0f;

// 변경 — 스트레이프는 바라보는 방향 + 이동 방향 둘이 있어야 어느 클립을 틀지 정해진다
[SyncVar] private Vector2 _serverFacing   = Vector2.up;
[SyncVar] private Vector2 _serverVelocity = Vector2.zero;   // 방향 + 크기가 속력
```

- **필드 수는 그대로다.** `MoveSpeed`는 `_serverVelocity.magnitude`라 **호출부가 바뀌지 않는다**
- 대역폭: `syncInterval` 0.1초 기준 **초당 10회 × 4B × 3인 = 120 B/s.** 무시해도 된다

### 11.3 명령과 검증

```csharp
[Command] void CmdSetLockOn(uint targetNetId);   // 걸 때 · 풀 때만
```

| 서버가 검증할 것 | |
|---|---|
| `netId`가 실재하는가 | 없는 대상을 보고 서 있는 캐릭터가 생기지 않게 |
| 대상이 살아 있는가 | |
| **25m 이내인가** | 맵 반대편 잡귀를 잠그는 것을 막는다 |
| 요청자가 살아 있는가 | |
| **화살 발사 시점에 대상이 아직 유효한가** | 유도가 판정이므로 한 번 더 본다 |

| 항목 | 권위 |
|---|---|
| 락온 대상 **선택** | 로컬 |
| 락온 여부 + 바라보는 방향 | **동기화** (`_serverFacing`) |
| **화살 유도** | **서버** (아래 12장) |
| 락온 UI(마커 · 화살표) | 로컬 |

## 12. 🚨 락온 화살 유도 — 2026-09-05 아침 결정을 뒤집는다

**같은 날 아침에 [`02-game-design 4.1`](../02-game-design.md)에 *"유도는 넣지 않는다"*고 썼다. 저녁에 되돌린다.**

### 12.1 4.2의 특성 축은 살아남는다

폐기 당시 무너졌던 이유는 초판이 ***"연사만 락온 유도 적용"***이었기 때문이다. **유도가 특성의 축이었다.**

**유도를 락온의 공통 기능으로 두면 연사와 관통이 똑같이 받으므로 축이 되지 않는다.** 두 특성은 여전히 **연사 = 관대함 / 관통 = 위력**으로 갈린다.

### 12.2 정밀 사격의 대가도 유지된다

정밀 사격의 조건은 *"예고 중 약점 명중"*이라 **대상이 거의 움직이지 않는다.** 유도가 도와줄 것이 별로 없다. *"겨누는 동안 느리고 무방비"*라는 대가는 그대로다.

**유도가 실제로 도움이 되는 것은 움직이는 잡귀이고, 정밀 사격은 그것을 노리지 않는다.** 층이 겹치지 않는다.

### 12.3 값 — 폐기 기간에 안 지운 필드가 살아난다

> 📄 **구현 상세는 [신궁 화살 조준 보정 설계 5.4 · 5.5](ARROW_AIM_ASSIST_DESIGN.md)가 소유한다.** 여기는 값과 경계만 적는다.

| `ArrowConfigSO` 필드 | 값 | 적용 |
|---|--:|---|
| `_aimAssistAngle` | **12°** | 발사 순간 락온 대상 쪽으로 초기 보정 |
| `_guidanceDegreesPerSecond` | **30°/s** | 비행 중 유도 (`Vector3.RotateTowards` — 비례 보간이 아니다) |
| `_guidanceDuration` | **0.4초** | 유도 지속 |

**12°가 탐색 반각 35°와 다른 이유** — **탐색됐다고 발사 보정까지 허용되는 것은 아니다.** 선딜 0.25초가 끝나는 release 틱에 대상 생존·거리·시야와 12°를 **다시** 확인하고, 실패하면 다른 적을 찾지 않고 비락온 방향으로 쏜다.

**락온 중일 때만 적용된다.** 락온이 없으면 직선으로 날아가고 [4.2의 명중 보조 반경 0.4m](../02-game-design.md)만 걸린다.

`ArrowProjectile.ServerInitialize`에 **대상 `netId` 하나를 더 넘긴다.** 화살 판정은 계속 서버가 한다.

### 12.4 ⚠️ 관통 특성은 유도를 못 받는다 — 그래도 축은 아니다

유도 종료 조건 하나가 **관통 특성**이다([5.5](ARROW_AIM_ASSIST_DESIGN.md)). **여러 적을 뚫고 지나가야 하는 화살이 휘면 안 되므로 물리적 필연이다.**

**그러면 "연사는 유도를 받고 관통은 못 받는다"가 되어 축이 되는 것 아닌가?** 그렇게 보이지만 아니다.

- [4.2](../02-game-design.md)가 이미 ***"관통은 단발 위력을 높여 보상한다"***로 정해 두었다. **대가가 하나 늘었으니 보상값을 다시 볼 뿐, 축의 성격은 그대로다**
- 이 제약은 **관통을 고른 사람만** 받는다. 초판이 무너졌던 이유는 *"연사만 유도"*라 **기본 사격에 이미 격차가 있었기** 때문이다

> **참고** — [`class-identity-and-boss-2026-09-03.md` 49줄](../class-identity-and-boss-2026-09-03.md)의 *"관통 특성엔 유도가 없어 창귀 실효 창은 Windup 1.5초뿐"*이라는 계산은 **여전히 유효하다.**

### 12.5 ⚠️ 재검토 표시

| 값 | 지금 | 왜 다시 봐야 하나 |
|---|---|---|
| **신궁 그로기 환율 8** | [보스 패턴 계약 6.1](BOSS_PATTERN_CONTRACT.md) | 8로 낮춘 근거가 *"락온이 조준을 돕는다"*였다. **유도까지 붙으면 더 쉬워진다** |
| **관통 특성 위력 보상** | [4.2](../02-game-design.md) | **유도가 없던 시절에 정해졌다.** 유도가 공통이 되면서 관통의 상대적 손해가 커졌다 |

둘 다 M2 실측 때 함께 본다.

# 밸런스 데이터 작업

> 그믐의 모든 수치는 프로토타입용 시작점이다. 10월 집중개발 중 절반은 바뀐다.
> 그때마다 코드를 고치고 빌드하면 팀 전체가 기다린다.

---

## 1. 원칙

**밸런스 수치를 코드 상수로 박지 않는다.**

```csharp
// 잘못
private const float ParryWindow = 0.32f;

// 맞음
[SerializeField] private CombatConfigSO config;
// config.parryWindow 를 참조
```

## 2. ScriptableObject 대상

| 데이터 | 담는 것 | 소유 파트 |
|---|---|---|
| `CombatConfigSO` | 스태미나, 신력, 이동, 구르기, 패링 수치 (**HP 제외**) | 네트워크 · 전투 |
| `ArrowConfigSO` | 발사각 보정, 유도 각도 · 지속 | 네트워크 · 전투 |
| `EnemySO` | 잡귀 3종 스탯, 강화 배수 | 몬스터 · 보스 |
| `BarrierPhaseSO` | 단계별 시간, 반경, 피해량 | 게임플레이 시스템 |
| `SpawnConfigSO` | 구간별 밀집도, 구성 비율, 리스폰 주기 | 몬스터 · 보스 |
| `BossPatternSO` | 페이즈별 패턴, 쿨다운, 예고·판정 정보 | 몬스터 · 보스 |
| `EquipmentSO` | 등급별 롤 범위, 무기별 특수옵션 풀 | 게임플레이 시스템 |

## 3. 설계도와 인스턴스 분리

장비처럼 개별 드랍마다 값이 다른 것은 두 층으로 나눈다.

| 구분 | 역할 | 형태 |
|---|---|---|
| `EquipmentSO` | 원본 설계도. 등급, 이름, 롤 범위, 특수옵션 풀 | ScriptableObject |
| `EquipmentInstance` | 개별 드랍 결과. 실제 굴려진 수치 | 런타임 클래스 |

이렇게 해야 같은 무기라도 드랍마다 스탯이 달라지는 구조가 깔끔하다.
스탯 재조정권과 등급 상승권도 이 구조를 그대로 재사용하므로 추가 구현 비용이 거의 없다.

## 4. 값을 바꿀 때

### 승인 없이 가능

- 자기 파트 소유 ScriptableObject의 값 조정
- 프로토타입 · 집중개발 기간 중

### 팀에 알려야 함

- 다른 파트 소유 데이터의 값
- 여러 시스템에 연쇄 영향을 주는 값 (예: 플레이어 HP → 잡귀 공격력 전부 재조정 필요)
- 스코프에 영향을 주는 구조 변경 (필드 추가 · 삭제)

### 사전 승인 필요

- ScriptableObject의 **필드 구조 변경**. 기존 에셋의 값이 초기화될 수 있다

---

## 5. 필드 구조를 바꿀 때

ScriptableObject에 필드를 추가하거나 이름을 바꾸면 기존 에셋의 값이 날아갈 수 있다.

| 변경 | 안전한가 |
|---|---|
| 필드 추가 | 안전. 기본값으로 채워짐 |
| 필드 삭제 | 값 소실. 기록해두고 진행 |
| 필드 이름 변경 | **값 소실.** `[FormerlySerializedAs("옛이름")]`를 붙인다 |
| 타입 변경 | 값 소실. 되도록 피한다 |
| enum 값 재배열 | **직렬화된 값이 어긋난다.** 명시값을 유지하고 기존 값을 재배열하지 않는다 |

```csharp
using UnityEngine.Serialization;

[FormerlySerializedAs("parryTime")]
[SerializeField] private float parryWindow;
```

## 6. 검증

| 변경 | 최소 검증 |
|---|---|
| 값만 조정 | L1 + 해당 값이 실제로 반영되는지 1회 확인 |
| 필드 추가 | L1 + 기존 에셋의 다른 값이 유지됐는지 확인 |
| 필드 이름 · 타입 변경 | L1 + **모든 관련 에셋을 열어 값 확인** |
| 연쇄 영향 있는 값 | L2 + 영향받는 시스템 회귀 확인 |

값을 바꾼 뒤 **인스펙터에서 실제로 반영됐는지 눈으로 확인한다.** 코드만 보고 넘어가지 않는다.

## 7. 문서와의 동기화

기획 문서(`docs/02-game-design.md`)의 수치와 실제 ScriptableObject 값이 갈라지는 것은 **정상이다.**

- 코드와 데이터가 최신
- 문서는 설계 의도와 근거를 담는다
- 큰 변경이 있으면 문서도 갱신하되, 매번 동기화하려 애쓰지 않는다

**충돌 시 데이터를 우선하고, 차이가 크면 보고한다.**

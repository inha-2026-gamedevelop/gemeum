# 네트워크 권위 규칙

> 이 프로젝트에서 가장 자주, 가장 늦게 드러나는 결함이 권위 경계 위반이다.
> 단일 플레이에서는 멀쩡하고 3인 접속에서만 깨지므로, 발견 시점에는 이미 여러 시스템이 그 위에 얹혀 있다.

---

## 1. 판단 기준은 하나다

> **이 값이 사람마다 달라도 게임 결과가 같은가?**

- 같다 → 클라이언트가 각자 계산한다
- 다르다 → 서버(호스트)가 판정하고 결과를 보낸다

조명이 A의 화면에서 조금 더 어두워도 아무도 죽지 않는다.
히트박스가 다르면 A에서는 맞고 B에서는 안 맞는다.

## 3. 클라이언트가 각자 하는 것

| 영역 | 항목 |
|---|---|
| 렌더링 | 조명, 스카이박스, 안개, 포스트프로세싱 |
| 이펙트 | 파티클, 히트 이펙트, 검흔 트레일 |
| 카메라 | 위치, 셰이크, 줌, 컷신 재생, **락온 대상 "선택"** — ⚠️ **락온 자체는 로컬이 아니다. 아래 표 참조** |
| 애니메이션 | 블렌딩, 레이어 가중치 |
| 사운드 | 재생, 믹싱 |
| UI | 체력바 보간, 미니맵 그리기, 알림 |
| 성능 | LOD, 오클루전 컬링 |

### 3.1 🚨 락온 — 2026-09-05에 두 번 정정했다

**락온을 "카메라 기능"으로 보고 로컬로 분류했다가 두 번 틀렸다.** 최종 판단은 아래다.

| 항목 | 권위 | 왜 |
|---|---|---|
| 대상 **선택** | **로컬** | 내가 누굴 잠글지는 나만 정한다 |
| 락온 여부 + **바라보는 방향** | 🔑 **동기화** | **남의 화면에서 그 사람이 옳게 서 있어야 한다.** 패링이 0.32초인 게임에서 **차사가 보스를 보고 자세를 잡는 것이 안 보이면 남들은 아무것도 예측할 수 없다** |
| **화살 유도** | 🚨 **서버** | 궤적이 대상에 의존하므로 **판정이다** |
| 락온 UI (마커 · 화살표) | 로컬 | |

**정정 이력**

| 시점 | 판단 | 무엇이 틀렸나 |
|---|---|---|
| 최초 | *"순수 로컬 표현"* | `_serverFacing`이 이미 SyncVar인데 락온 대상은 로컬만 안다 → **남의 화면에서 엉뚱한 곳을 본다** |
| 1차 정정 | *"판정에는 안 들어가고 표현에는 들어간다"* | 유도를 넣기로 하면서 **판정에도 들어갔다** |
| **확정** | **표현에도 판정에도 들어간다** | |

**동기화 비용은 사실상 0이다** — `_serverSpeed`(float)를 `_serverVelocity`(Vector2)로 **승격**하면 필드 수가 그대로다. `CmdSetLockOn(uint targetNetId)`은 걸 때·풀 때만 보낸다.

> 🔒 **서버가 검증할 것** — `netId` 실재 · 대상 생존 · **25m 이내** · 요청자 생존, 그리고 **화살 발사 시점에 대상이 아직 유효한가**.
> 검증이 없으면 클라가 맵 반대편 잡귀를 잠그고 그쪽으로 화살을 휘게 만들 수 있다.

상세는 [카메라와 락온 11~12장](CAMERA_AND_LOCKON.md).

## 4. 파생 계산 원칙

서버는 **원본 값 하나만** 보낸다. 표현은 클라이언트가 만든다.

| 서버가 보내는 것 | 클라이언트가 만드는 것 |
|---|---|
| 경과 시간 `900` | 게임 내 시각, 조명 프리셋, 스카이박스, 안개 색 |
| 결계 반경 `120` | 원통 셰이더, 미니맵 원, 경계 파티클, 경고 UI |
| 플레이어 HP `42` | 체력바 애니메이션, 저체력 화면 효과 |
| 등급 `영험`, 공격력 `35.2` | 아이템 색상, 반짝임 이펙트, 툴팁 |

`DayCycleSO` 같은 조명 프리셋은 네트워크를 전혀 타지 않는 로컬 리소스다.

**안티패턴**: 서버가 조명 색 RGB를 매 프레임 브로드캐스트하는 것.
경과 시간 하나면 충분한데 대역폭을 낭비하고, 조명을 고칠 때마다 네트워크 코드를 건드리게 된다.

## 5. 함정 — 보이지만 판정에 걸리는 것

아래는 이펙트처럼 보이지만 **클라이언트마다 위치가 다르면 안 된다.**

- 보스 공격 예고 표식 (장판, 범위 표시)
- 결계 경계선
- 액귀 투사체
- 아이템 드랍 위치

**처리 방식**: 서버가 이벤트만 보내고(무엇을 · 언제 · 어디서) 클라이언트가 그것을 렌더링한다.
클라이언트가 스스로 위치나 타이밍을 계산하게 두면 안 된다.

```
잘못: 클라이언트가 보스 애니메이션 이벤트를 보고 장판 위치를 계산
맞음: 서버가 "패턴 3, 좌표 (12, 0, 45), 1.2초 후 발동" 브로드캐스트
      → 클라이언트는 그 좌표에 장판을 그리기만
```

## 5.5 Mirror에서의 구현 매핑

이 프로젝트는 **Mirror**를 사용한다. 위 규칙을 Mirror의 API로 옮기면 아래와 같다.

### 기본 대응

| 개념 | Mirror |
|---|---|
| 네트워크 오브젝트 | `NetworkIdentity` + `NetworkBehaviour` 상속 |
| 서버 → 모든 클라이언트 상태 | `[SyncVar]`, `SyncList`, `SyncDictionary` |
| 클라이언트 → 서버 요청 | `[Command]` |
| 서버 → 모든 클라이언트 호출 | `[ClientRpc]` |
| 서버 → 특정 클라이언트 호출 | `[TargetRpc]` |
| 서버에서만 실행 | `[Server]` / `[ServerCallback]` |
| 클라이언트에서만 실행 | `[Client]` / `[ClientCallback]` |

### 그믐 시스템별 매핑

| 시스템 | Mirror 처리 |
|---|---|
| 플레이어 HP, 스태미나 | `[SyncVar(hook = ...)]` — 훅에서 UI 갱신 |
| 결계 반경, 현재 단계 | `[SyncVar]` — 클라이언트가 이 값으로 셰이더 · 미니맵 그림 |
| 경과 시간 | `[SyncVar]` 하나. 조명은 클라이언트가 계산 |
| 노잣돈 (팀 공용) | 서버 단일 값 + `[SyncVar]`. 구매는 `[Command]` |
| 공격 · 패링 입력 | `[Command]` 로 전송, 서버가 판정 |
| 패링 성공 연출 | `[TargetRpc]` — 해당 플레이어에게만 |
| 잡귀 스폰 · 사망 | 서버가 `NetworkServer.Spawn` / `Destroy` |
| 장비 드랍 | 서버가 굴리고 `NetworkServer.Spawn` |
| 아이템 획득 | `[Command]` 요청 → 서버가 선착순 판정 |
| 보스 패턴 예고 | `[ClientRpc]` 로 패턴 ID · 좌표 · 발동 시각 전송 |
| 히트 이펙트, 사운드 | 동기화하지 않음. 각 클라이언트가 로컬 재생 |

### 주의할 Mirror 함정

**1. `[Command]`는 기본적으로 소유 오브젝트에서만 호출된다.**
다른 오브젝트에 대한 요청은 `[Command(requiresAuthority = false)]`를 쓰되, **서버에서 호출자 검증을 반드시 한다.** 안 하면 클라이언트가 남의 아이템을 주울 수 있다.

**2. `[SyncVar]` 훅은 클라이언트에서만 호출된다.**
호스트는 서버이자 클라이언트라 훅이 호출되지만, 순수 서버 로직을 훅에 넣으면 데디케이티드 전환 시 깨진다.

**3. `SyncList` 변경은 요소 단위로 전송된다.**
인벤토리처럼 자주 바뀌는 것은 괜찮지만, 매 프레임 갱신되는 것을 넣으면 대역폭을 잡아먹는다.

**4. `NetworkTransform`의 역할.**
`NetworkTransformReliable`은 서버 위치 전달과 원격 플레이어 보간에 사용한다.
소유 플레이어의 입력 예측·마지막 처리 sequence·재조정은 별도 `PlayerPrediction` 계약으로 처리하며,
`NetworkTransform` 자체에 맡기지 않는다.

**보간 책임은 한 계층만 갖는다.** 원격 인스턴스는 `NetworkTransform`, 소유 클라이언트는 `PlayerPrediction`이다.
비서버 인스턴스의 Rigidbody는 `isKinematic = true`와 함께 `interpolation = None`으로 둔다 —
두 계층이 같은 프레임에 Transform을 밀면 떨림이 된다.

**5. 화면 표현을 Transform 위치 차분으로 역산하지 않는다.**
위치에는 서버 이동·스냅샷 보간·재조정 보정이 섞여 들어온다. 이걸 이동 방향으로 되돌리면
서버가 위치를 뒤로 보정한 순간 모델이 뒤를 본다.
방향·속도는 `PlayerPresentation`이 역할별 소스에서 받아 보관하고, 회전은 물리 루트가 아니라
`VisualPivot`에만 적용한다. 루트 회전을 쓰지 않으므로 `syncRotation`은 꺼 둔다.

**6. 호스트는 지연이 0이다.**
호스트에서만 테스트하면 지연 관련 결함을 절대 못 찾는다. [멀티플레이 테스트 절차](../ai/04_MULTIPLAYER_TEST_PROTOCOL.md) 참조.

**7. `syncInterval`을 오브젝트 종류마다 다르게 잡는다.**
기본값 그대로 두면 잡귀 22마리가 플레이어와 같은 주기로 3연결에 전송된다.
조작 대상인 플레이어는 촘촘하게, 잡귀처럼 보간으로 메울 수 있는 것은 성기게 잡는다. 값은 `Constants.Network`에 있다.

**8. `GameEventBus`는 네트워크가 아니다.**
호스트 프로세스에서 발행한 이벤트는 원격 클라이언트에 전달되지 않는다. 지속 상태는
`SyncVar`/`SyncList`, 전체 일회성 결과는 `ClientRpc`, 개인 결과는 `TargetRpc`로 별도 전달한다.

**9. Mirror의 정적 연결 이벤트에 `+=`로 구독하면 조용히 지워진다.**

`NetworkManager`가 서버·클라이언트를 시작할 때 이 이벤트들을 **대입으로 덮어쓴다.**

```csharp
// Mirror/Core/NetworkManager.cs
NetworkServer.OnConnectedEvent    = OnServerConnectInternal;   // += 가 아니다
NetworkServer.OnDisconnectedEvent = OnServerDisconnect;
NetworkClient.OnConnectedEvent    = OnClientConnectInternal;
NetworkClient.OnDisconnectedEvent = OnClientDisconnectInternal;
```

밖에서 `+=`로 걸어 둔 구독은 `StartHost`/`StartClient`가 불리는 순간 통째로 사라진다.
**예외도 경고도 없다.** 이벤트가 한 번도 오지 않는 것으로만 드러나므로 원인을 찾기 어렵다.

2026-09-02에 이 함정으로 Steam 세션 단계가 `Ready`로 넘어가지 않았다. 3PC 테스트 로그에서
`Connection established` 뒤에 단계 전환 로그가 없는 것을 보고서야 찾았다.

**대신 `NetworkManager`를 상속해 콜백을 오버라이드하고, 거기서 프로젝트 이벤트를 다시 낸다.**

```csharp
public override void OnClientConnect()
{
    base.OnClientConnect();
    ClientConnected?.Invoke();
}
```

`GeumeumNetworkManager`가 `ClientConnected`·`ClientDisconnected`를 이 방식으로 제공한다.
연결 수명을 알아야 하는 코드는 Mirror의 정적 이벤트가 아니라 이쪽을 구독한다.

### 트랜스포트

배포 기본은 자체 계정 `AccountRelayTransport`와 AWS 암호화 UDP 릴레이다. 로컬 개발은 직접 KCP, Steam 호환은 이미 도입된 FizzySteamworks를 사용한다. 연결 경로가 달라도 게임 판정 권위는 방장 리슨 서버에 남는다.

FastAPI는 로그인·파티 명단·호스트 임대·접속 티켓·허용 빌드·릴레이 자격을 확정한다. 방장 게임은 인증된 명단으로 시뮬레이션한다. 계정 모드의 준비·무기 선호·봇 편성은 런처/API 경로를 사용하며 Unity 클라이언트의 변경 Command는 거부한다.

## 6. 패링 판정 — 이 프로젝트의 핵심 난제

판정 창이 0.32초인데 네트워크 지연이 50~150ms 발생하면, 호스트의 판정 결과와 클라이언트의 체감이 어긋난다.

### 설계 방향

1. 서버가 공격별 `parryWindowId`, 대상, 시작·종료 서버 시각, 소비 여부를 보유
2. 클라이언트가 패링 request ID, window ID, 입력 순서와 추정 서버 시각을 함께 전송
3. 호스트가 시각을 `MAX_INPUT_TIME_BEHIND/AHEAD` 범위로 제한하고 현재 무기·생명 상태·
   쿨다운·자원·window 대상/소비 여부를 검증한 뒤 `ParryJudge` 호출
4. 성공하면 window를 먼저 소비하고 권위 결과를 한 번만 커밋
5. 클라이언트는 패링 **모션을 즉시 재생**하되, 성공 연출은 호스트 응답 후 확정한다.
   판정 불일치 시 롤백 대신 호스트 결과를 우선한다

### 검증 시 확인할 것

- 지연 0ms(로컬), 50ms, 150ms 조건에서 각각 성공률을 비교한다
- 클라이언트가 "맞았다고 느꼈는데 실패"하는 빈도를 기록한다
- 호스트 플레이어와 클라이언트 플레이어의 성공률 차이를 본다

**호스트가 유리한 것은 리슨 서버의 구조적 특성이다.** 완전히 없앨 수는 없고, 체감 가능한 수준인지만 확인한다. 차이가 크면 판정 창을 늘리는 쪽으로 대응한다.

## 7. 데디케이티드 전환 여지

현재는 호스트 권위 리슨 서버지만, 추후 데디케이티드로 옮길 가능성을 열어둔다.

**규칙**: 권위 판정 로직을 호스트 전용 코드에 직접 박지 않는다.

```
잘못: if (isServer && isClient) { /* 호스트 전용 판정 로직 300줄 */ }
맞음: 판정 로직을 [Server] 메서드로 분리하고,
      호스트인지 데디케이티드인지 로직이 알지 못하게 한다
```

**Mirror에서는 다행히 이게 자연스럽다.** `[Server]` 특성을 붙인 메서드는 리슨 서버든 데디케이티드든 동일하게 동작한다.
문제가 되는 것은 `isLocalPlayer`나 호스트 전용 분기에 판정 로직을 섞는 경우다.

- 판정은 `[Server]` 메서드 안에서만
- `isLocalPlayer` 분기는 입력 · UI · 카메라에만
- 이 둘을 섞지 않으면 권위 게임플레이 로직은 재사용할 수 있다. 다만 데디케이티드 전환에는
  헤드리스 빌드, 서버 시작 방식, 포트·호스팅, 인증·텔레메트리, 클라이언트 전용 컴포넌트 제거가
  별도 작업으로 남는다

## 8. 코드 리뷰 체크리스트

네트워크가 걸린 PR에서 확인한다.

- [ ] 새로 추가한 상태 변수가 서버 권위 대상인지 판정했다
- [ ] 클라이언트가 게임 결과에 영향을 주는 값을 스스로 계산하지 않는다
- [ ] 서버가 표현용 값(색, 이펙트 파라미터)을 브로드캐스트하지 않는다
- [ ] 판정 로직이 `IsHost` 분기 안에 직접 박히지 않았다
- [ ] Mirror의 정적 연결 이벤트에 `+=`로 구독하지 않았다 (5.5절 함정 9)
- [ ] 3인 접속 상태에서 테스트했다
- [ ] 호스트와 클라이언트 양쪽 시점에서 확인했다

## 9. 판단이 애매할 때

표에 없는 항목이면 아래 순서로 판정한다.

1. 이 값이 다르면 누군가 죽거나, 아이템을 얻거나, 점수가 달라지는가? → 서버
2. 이 값이 다르면 화면만 조금 달라 보이는가? → 클라이언트
3. 그래도 애매하면 **서버로 두고 팀에 물어본다.** 나중에 클라이언트로 내리는 것이, 클라이언트에 뒀다가 서버로 올리는 것보다 훨씬 싸다.

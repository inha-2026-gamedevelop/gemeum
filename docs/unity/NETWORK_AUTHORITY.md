# 네트워크 권위 규칙

> 이 프로젝트에서 가장 자주, 가장 늦게 드러나는 결함이 권위 경계 위반이다.
> 단일 플레이에서는 멀쩡하고 3인 접속에서만 깨지므로, 발견 시점에는 이미 여러 시스템이 그 위에 얹혀 있다.

---

## 1. 판단 기준은 하나다

> **이 값이 사람마다 달라도 게임 결과가 같은가?**

- 같다 → 클라이언트가 각자 계산한다
- 다르다 → 서버(호스트)가 판정하고 결과를 보낸다

조명이 A의 화면에서 조금 더 어두워도 아무도 죽지 않는다.
히트박스가 다르면 A에서는 맞고 B에서는 안 맞는다.

---

## 2. 서버가 판정하는 것

| 영역 | 항목 |
|---|---|
| 플레이어 | 위치, HP, 스태미나, 신력, 레벨, 경험치, 특성 포인트 |
| 전투 | 공격 판정, 피격 판정, 패링 성공 여부, 패링 게이지 |
| 투사체 | 화살 궤적, 유도 상태 전환, 명중 판정 |
| 적 | 잡귀 AI 상태, HP, 보스 페이즈와 패턴 선택 |
| 아이템 | 드랍 결정, 등급 룰렛, 스탯 롤, 소유권, 양도 |
| 경제 | 노잣돈 잔액, 객주 구매 처리 |
| 결계 | 현재 단계, 반경, 범위 밖 피해 적용 |
| 시간 | 경과 시간 (초 단위 값) |
| 생사 | 사망 판정, 부활 타이머, 전멸 판정 |
| 점수 | 런 종료 시 정산 |

## 3. 클라이언트가 각자 하는 것

| 영역 | 항목 |
|---|---|
| 렌더링 | 조명, 스카이박스, 안개, 포스트프로세싱 |
| 이펙트 | 파티클, 히트 이펙트, 검흔 트레일 |
| 카메라 | 위치, 락온 추적, 셰이크, 줌 |
| 애니메이션 | 블렌딩, 레이어 가중치 |
| 사운드 | 재생, 믹싱 |
| UI | 체력바 보간, 미니맵 그리기, 알림 |
| 성능 | LOD, 오클루전 컬링 |

## 4. 파생 계산 원칙

서버는 **원본 값 하나만** 보낸다. 표현은 클라이언트가 만든다.

| 서버가 보내는 것 | 클라이언트가 만드는 것 |
|---|---|
| 경과 시간 `900` | 게임 내 시각, 조명 프리셋, 스카이박스, 안개 색 |
| 결계 반경 `120` | 원통 셰이더, 미니맵 원, 경계 파티클, 경고 UI |
| 플레이어 HP `42` | 체력바 애니메이션, 저체력 화면 효과 |
| 등급 `영험`, 공격력 `35.2` | 아이템 색상, 반짝임 이펙트, 툴팁 |

`DayCycleData` 같은 조명 프리셋은 네트워크를 전혀 타지 않는 로컬 리소스다.

**안티패턴**: 서버가 조명 색 RGB를 매 프레임 브로드캐스트하는 것.
경과 시간 하나면 충분한데 대역폭을 낭비하고, 조명을 고칠 때마다 네트워크 코드를 건드리게 된다.

---

## 5. 함정 — 보이지만 판정에 걸리는 것

아래는 이펙트처럼 보이지만 **클라이언트마다 위치가 다르면 안 된다.**

- 보스 공격 예고 표식 (장판, 범위 표시)
- 결계 경계선
- 액귀 투사체
- 아이템 드랍 위치

**처리 방식**: 서버가 이벤트만 보내고(무엇을 · 언제 · 어디서) 클라이언트가 그것을 렌더링한다.
클라이언트가 스스로 위치나 타이밍을 계산하게 두면 안 된다.

```
잘못: 클라이언트가 보스 애니메이션 이벤트를 보고 장판 위치를 계산
맞음: 서버가 "패턴 3, 좌표 (12, 0, 45), 1.2초 후 발동" 브로드캐스트
      → 클라이언트는 그 좌표에 장판을 그리기만
```

## 5.5 Mirror에서의 구현 매핑

이 프로젝트는 **Mirror**를 사용한다. 위 규칙을 Mirror의 API로 옮기면 아래와 같다.

### 기본 대응

| 개념 | Mirror |
|---|---|
| 네트워크 오브젝트 | `NetworkIdentity` + `NetworkBehaviour` 상속 |
| 서버 → 모든 클라이언트 상태 | `[SyncVar]`, `SyncList`, `SyncDictionary` |
| 클라이언트 → 서버 요청 | `[Command]` |
| 서버 → 모든 클라이언트 호출 | `[ClientRpc]` |
| 서버 → 특정 클라이언트 호출 | `[TargetRpc]` |
| 서버에서만 실행 | `[Server]` / `[ServerCallback]` |
| 클라이언트에서만 실행 | `[Client]` / `[ClientCallback]` |

### 그믐 시스템별 매핑

| 시스템 | Mirror 처리 |
|---|---|
| 플레이어 HP, 스태미나 | `[SyncVar(hook = ...)]` — 훅에서 UI 갱신 |
| 결계 반경, 현재 단계 | `[SyncVar]` — 클라이언트가 이 값으로 셰이더 · 미니맵 그림 |
| 경과 시간 | `[SyncVar]` 하나. 조명은 클라이언트가 계산 |
| 노잣돈 (팀 공용) | 서버 단일 값 + `[SyncVar]`. 구매는 `[Command]` |
| 공격 · 패링 입력 | `[Command]` 로 전송, 서버가 판정 |
| 패링 성공 연출 | `[TargetRpc]` — 해당 플레이어에게만 |
| 잡귀 스폰 · 사망 | 서버가 `NetworkServer.Spawn` / `Destroy` |
| 장비 드랍 | 서버가 굴리고 `NetworkServer.Spawn` |
| 아이템 획득 | `[Command]` 요청 → 서버가 선착순 판정 |
| 보스 패턴 예고 | `[ClientRpc]` 로 패턴 ID · 좌표 · 발동 시각 전송 |
| 히트 이펙트, 사운드 | 동기화하지 않음. 각 클라이언트가 로컬 재생 |

### 주의할 Mirror 함정

**1. `[Command]`는 기본적으로 소유 오브젝트에서만 호출된다.**
다른 오브젝트에 대한 요청은 `[Command(requiresAuthority = false)]`를 쓰되, **서버에서 호출자 검증을 반드시 한다.** 안 하면 클라이언트가 남의 아이템을 주울 수 있다.

**2. `[SyncVar]` 훅은 클라이언트에서만 호출된다.**
호스트는 서버이자 클라이언트라 훅이 호출되지만, 순수 서버 로직을 훅에 넣으면 데디케이티드 전환 시 깨진다.

**3. `SyncList` 변경은 요소 단위로 전송된다.**
인벤토리처럼 자주 바뀌는 것은 괜찮지만, 매 프레임 갱신되는 것을 넣으면 대역폭을 잡아먹는다.

**4. `NetworkTransform`의 보간 설정.**
기본값은 부드럽지만 반응이 느리다. 패링처럼 타이밍이 중요한 게임은 보간 시간을 줄이고 클라이언트 예측을 넣어야 한다.

**5. 호스트는 지연이 0이다.**
호스트에서만 테스트하면 지연 관련 결함을 절대 못 찾는다. [멀티플레이 테스트 절차](../ai/04_MULTIPLAYER_TEST_PROTOCOL.md) 참조.

### 트랜스포트

Mirror 기본은 **KCP Transport**다. UDP 기반이라 지연이 낮고 별도 설정이 거의 없다.
추후 Steam 출시를 고려하면 `FizzySteamworks`로 교체할 수 있다. 트랜스포트 교체는 컴포넌트 수준이라 게임 로직에 영향이 없다.

## 6. 패링 판정 — 이 프로젝트의 핵심 난제

판정 창이 0.32초인데 네트워크 지연이 50~150ms 발생하면, 호스트의 판정 결과와 클라이언트의 체감이 어긋난다.

### 설계 방향

1. 클라이언트가 패링 입력 **시각(타임스탬프)** 을 함께 전송
2. 호스트가 해당 시각 기준으로 판정 (지연 보상)
3. 클라이언트는 패링 **모션을 즉시 재생**하되, 성공 연출은 호스트 응답 후 확정
4. 판정 불일치 시 롤백 대신 호스트 결과를 우선하고, 시각 효과로 무마

### 검증 시 확인할 것

- 지연 0ms(로컬), 50ms, 150ms 조건에서 각각 성공률을 비교한다
- 클라이언트가 "맞았다고 느꼈는데 실패"하는 빈도를 기록한다
- 호스트 플레이어와 클라이언트 플레이어의 성공률 차이를 본다

**호스트가 유리한 것은 리슨 서버의 구조적 특성이다.** 완전히 없앨 수는 없고, 체감 가능한 수준인지만 확인한다. 차이가 크면 판정 창을 늘리는 쪽으로 대응한다.

## 7. 데디케이티드 전환 여지

현재는 호스트 권위 리슨 서버지만, 추후 데디케이티드로 옮길 가능성을 열어둔다.

**규칙**: 권위 판정 로직을 호스트 전용 코드에 직접 박지 않는다.

```
잘못: if (isServer && isClient) { /* 호스트 전용 판정 로직 300줄 */ }
맞음: 판정 로직을 [Server] 메서드로 분리하고,
      호스트인지 데디케이티드인지 로직이 알지 못하게 한다
```

**Mirror에서는 다행히 이게 자연스럽다.** `[Server]` 특성을 붙인 메서드는 리슨 서버든 데디케이티드든 동일하게 동작한다.
문제가 되는 것은 `isLocalPlayer`나 호스트 전용 분기에 판정 로직을 섞는 경우다.

- 판정은 `[Server]` 메서드 안에서만
- `isLocalPlayer` 분기는 입력 · UI · 카메라에만
- 이 둘을 섞지 않으면 데디케이티드 전환 시 `NetworkManager` 설정만 바꾸면 된다

## 8. 코드 리뷰 체크리스트

네트워크가 걸린 PR에서 확인한다.

- [ ] 새로 추가한 상태 변수가 서버 권위 대상인지 판정했다
- [ ] 클라이언트가 게임 결과에 영향을 주는 값을 스스로 계산하지 않는다
- [ ] 서버가 표현용 값(색, 이펙트 파라미터)을 브로드캐스트하지 않는다
- [ ] 판정 로직이 `IsHost` 분기 안에 직접 박히지 않았다
- [ ] 3인 접속 상태에서 테스트했다
- [ ] 호스트와 클라이언트 양쪽 시점에서 확인했다

## 9. 판단이 애매할 때

표에 없는 항목이면 아래 순서로 판정한다.

1. 이 값이 다르면 누군가 죽거나, 아이템을 얻거나, 점수가 달라지는가? → 서버
2. 이 값이 다르면 화면만 조금 달라 보이는가? → 클라이언트
3. 그래도 애매하면 **서버로 두고 팀에 물어본다.** 나중에 클라이언트로 내리는 것이, 클라이언트에 뒀다가 서버로 올리는 것보다 훨씬 싸다.

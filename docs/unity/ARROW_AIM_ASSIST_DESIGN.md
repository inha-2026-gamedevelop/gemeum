>

> **신궁이 위나 아래를 겨눌 수 없고, 카메라가 보는 곳과 화살이 가는 곳이 어긋난다.**
>
> 정밀 사격은 "겨눈다"가 메커닉의 전부인데 겨눌 수단이 이동 방향뿐이면 성립하지 않는다.

> 클라이언트가 조준 방향을 보내게 되므로 **서버 검증 규칙**(각도 상한·거리·시야)을 함께 정한다 — 2장 권위 경계.

## 1. 결론

> ⚠️ **아래는 2026-09-04에 다시 쓴 결론이다.** 초판 결론은 명시적 락온을 권고했으나 락온은 폐기됐다. 초판 문장은 [부록 A](#부록-a-폐기된-락온-결론-2026-09-03-오전)에 남긴다.

## 자유 조준 계약 — 이것이 유일한 경로다

**신궁은 락온을 쓰지 않는다.** 자동 조준이 맞혀주면 [정밀 사격](../02-game-design.md)의 "멈춰 서서 겨눠 맞힌다"가 성립하지 않기 때문이다. 시그니처가 둘일 수 없다.

| # | 규칙 | 근거 |
|---|---|---|
| **1** | **조준 방향은 카메라 중앙 ray다.** 입력 방향이 없으면 `PlayerPresentation.FacingDirection`을 쓴다 | 대상 자동 선택이 없으므로 방향 하나가 전부다 |
| **2** | **발사 후 유도는 없다.** 화살은 발사 방향으로 직진한다 | 유도가 있으면 조준 실력이 결과를 정하지 않는다 |
| **3** | **명중 여유는 `0.4m` SphereCast 하나뿐이다** | 손맛 보정이지 자동 조준이 아니다 |
| **4** | **서버는 발사 방향·자원·쿨다운·상태를 검증한다.** 대상은 검증하지 않는다 | 보낼 대상이 없다 |
| **5** | **카메라·조준 UI 보정은 로컬 표현이고 판정에 쓰지 않는다** | 사람마다 다르면 결과가 갈린다 |

**클라이언트가 보내는 것은 `RequestId`와 `AimDirection`뿐이다.** 후보 대상 netId는 보내지 않는다.

### 남은 구현 항목은 둘이다

| 항목 | 상태 |
|---|---|
| 조준 방향 정상화 (`transform.forward` → `FacingDirection`) | ✅ **완료** — `PlayerAttack.cs:301` 실측 |
| **월드 장애물 판정** (`ArrowConfigSO.WorldMask`가 비어 있다) | ❌ **미착수. 벽 뒤 적이 맞는다** |

**이 문서에서 지금 실행되는 지시는 위 표 하나뿐이다.** 5.1·5.4·5.5·7장의 `LockOnSystem`·`ArrowGuidance`, 8장 4·5단계는 전부 폐기됐고 구현 대상이 아니다.

## 2. 레퍼런스 게임에서 확인되는 방식

상용 게임의 내부 수식·보정 각도·추적 속도는 공개되지 않았다. 아래에서 `확인`은 공식 매뉴얼/지원 문서로 확인 가능한 동작이고, `관찰`은 플레이 결과와 커뮤니티 보고에서 반복적으로 보이는 체감이며 내부 구현의 확정 사실이 아니다.

### 2.1 Elden Ring

**확인**

- R3로 가까운 적을 락온하고 오른쪽 스틱으로 대상을 바꾼다.
- 락온 중에는 대상이 항상 플레이어 정면에 오도록 카메라와 이동 체계가 동작한다.
- 활은 락온 사격과 별개로 정밀 조준 모드와 줌을 제공한다.
- 출처: [Bandai Namco Elden Ring Starter Guide](https://en.bandainamcoent.eu/elden-ring/news/elden-ring-starter-guide-tips-know-playing-the-game)

**관찰 · 구현 추정**

- 일반 화살의 락온은 주로 발사 순간의 대상 조준점을 향하게 할 뿐, 빠르게 횡이동하는 적을 강하게 선행 조준하거나 끝까지 추적하지 않는다.
- 그래서 락온은 “명중 보장”이 아니라 카메라·캐릭터 방향을 잡아 주는 장치에 가깝고, 먼 거리나 이동 표적은 정밀 조준과 타이밍이 필요하다.
- 반복 보고 예: [이동 표적에서 락온 화살이 빗나간다는 사용자 사례](https://www.reddit.com/r/Eldenring/comments/txp10o/bow_users_how_do_you_aim/)

**그믐에 가져올 것**

- 락온과 정밀/자유 조준을 별도 모드로 둔다.
- 락온이어도 조준 후보를 서버가 무조건 명중으로 바꾸지 않는다.
- 자동 선행 조준은 넣지 않아 플레이어의 발사 타이밍을 남긴다.

### 2.2 Dark Souls III

**확인**

- 적 락온을 제공한다. 매뉴얼 원문은 "ターゲットの固定：…近くにいる敵をターゲットとして固定します"다.
- 출처: [FromSoftware Dark Souls III 공식 웹 매뉴얼 — 액션](https://www.fromsoftware.jp/manual/darksouls3/ps4/action1.html)

**관찰 · 구현 추정**

- 락온과 별개로 확대된 수동 정밀 조준이 있고, 락온은 근·중거리, 먼 거리의 특정 지점 사격은 수동 조준을 쓰는 구조로 보고된다. **공식 매뉴얼 액션 페이지에 활 조준 설명이 없어 `확인`이 아니라 `관찰`이다.** 출처: [두 조준 방식 설명과 영상](https://www.digitaltrends.com/gaming/dark-souls-iii-guide/)
- 일반 화살은 락온 대상 방향으로 발사되지만, 이동하는 표적을 지속해서 휘어 따라가는 유도탄과는 다르다.
- 락온 거리와 대상 중심점의 제약 때문에 장거리 저격 또는 약점 사격은 수동 조준이 유리하다.

**그믐에 가져올 것**

- 작은 잡귀를 빠르게 정리하는 락온 사격과, 관통/약점 사격용 비락온 사격의 역할을 분리한다.
- 락온 중심점 하나가 보스의 모든 부위를 대신하지 않게 한다. 보스가 들어오면 부위별 aim anchor 또는 수동 조준을 제공한다.

### 2.3 Monster Hunter: World

**확인**

- `Lock-on Camera`는 선택한 몬스터를 계속 따라가고, `Target Camera`는 버튼을 눌렀을 때 한 번만 카메라를 대상으로 돌린다.
- 즉, “대상을 기억하는 기능”과 “플레이어 조준을 계속 강제하는 기능”을 설정으로 분리한다.
- 출처: [Capcom 공식 지원 — 두 카메라 방식의 차이](https://www.capcom.co.jp/support/faq/platform_pc_monsterhunter_world_0141881.html) · [Monster Hunter: World 공식 웹 매뉴얼](https://game.capcom.com/manual/MHW/)

**관찰 · 구현 추정**

- 활은 화면 조준선으로 부위를 직접 노리는 비중이 크다. 카메라가 몬스터를 추적하더라도 화살 자체를 강한 유도탄으로 만들지는 않는다.
- 조준 중 회피 후 이전 조준점을 유지하는 동작처럼, 보조의 중심이 “투사체 자동 추적”보다 “입력과 카메라를 덜 흔들리게 하는 것”에 가깝다.

**그믐에 가져올 것**

- 카메라 락온, 조준 방향, 투사체 유도를 서로 다른 계층으로 구현한다.
- 수동 조준에서는 카메라 중앙 레이로 월드 조준점을 만든 뒤, 실제 총구에서 그 점으로 쏴 오버숄더 시차를 해결한다.
- 보정 여부가 불분명하지 않도록 락온 마커와 조준점을 UI로 명확히 보여 준다.

### 2.4 비교 요약

| 게임 | 락온의 주 역할 | 수동 조준 | 일반 화살 체감 | 그믐에 적용 |
|---|---|---|---|---|
| Elden Ring | 카메라·캐릭터를 대상에 정렬 | 정밀 조준/줌 | 이동 표적 명중을 보장하지 않음 | 명시적 락온 + 약한 단기 유도 |
| Dark Souls III | 근·중거리 대상 고정 | 장거리 정밀 조준 | 대상 중심 사격, 제한된 추적 | 잡귀 락온과 관통 수동 조준 분리 |
| Monster Hunter: World | 지속 추적/한 번 재정렬을 선택 | 부위 직접 조준 비중 큼 | 화살보다 카메라·조준 입력 보조 중심 | 카메라와 투사체 보정을 분리 |

## 3. 현재 프로젝트 상태

### 3.1 이미 있는 것

- [`PlayerAttack`](../../Assets/01.Scripts/02.Combat/Player/PlayerAttack.cs)이 서버에서 화살을 생성한다.
- [`ArrowProjectile`](../../Assets/01.Scripts/02.Combat/Arrow/ArrowProjectile.cs)이 서버 물리 틱마다 이동하고, 이동 구간을 `SphereCastNonAlloc`으로 훑는다.
- 한 대상의 여러 콜라이더는 `NetworkIdentity.netId`로 중복 피해를 막는다.
- [`ArrowConfigSO`](../../Assets/01.Scripts/00.Common/Data/ArrowConfigSO.cs)에 아래 값이 이미 있다.

| 값 | 현재 설정 |
|---|---:|
| 화살 속도 | 30m/s |
| 수명 | 3초 |
| 락온 초기 보정 허용각 | 12도 |
| 유도 회전 속도 | 30도/초 |
| 유도 시간 | 0.4초 |
| 비락온 명중 반경 | 0.4m |
| 기본 고유 대상 명중 수 | 1 |

### 3.2 구현 전에 먼저 해결할 사실

1. **실제 조준 방향이 없다.** `CmdRequestAttack`은 `requestId`만 받고, 화살은 `transform.forward`로 발사된다.
2. **플레이어 루트는 방향 표현의 원본이 아니다.** 현재 이동 구조는 루트를 돌리지 않고 `PlayerPresentation`의 방향으로 `VisualPivot`만 회전한다. 따라서 `transform.forward`를 카메라/이동 조준으로 간주하면 안 된다.
3. **카메라 구현이 없다.** `CameraRig.cs`가 구조 문서에 계획으로만 있고 폴더에는 구현이 없다. *(2026-09-04 정정: 초판은 `LockOnSystem.cs`도 함께 "없다"고 적었으나 **그것은 만들지 않는 파일이라 결함이 아니다.**)*
4. **화살이 월드 장애물을 검사하지 않는다.** 현재 SphereCast 마스크는 Enemy/Boss이므로 지형·벽을 맞혀 소멸하는 계약이 없다.
5. **락온 수치가 사용되지 않는다.** `AimAssistAngle`, `GuidanceDegreesPerSecond`, `GuidanceDuration`은 데이터에만 있고 런타임에서 읽지 않는다.
   다만 `EquipmentOptionKind`에 `ArrowSpeed = 300`, `GuidanceDuration = 301`, `PierceCount = 302`가 이미 정의되어 있다. **이 세 값은 나중에 장비 옵션으로 증가하는 값이므로, SO 값을 그대로 상수처럼 쓰지 말고 화살 스폰 시점의 snapshot으로 넘겨야 한다**(6.2절 8번과 같은 이유).
6. **락온과 비락온의 충돌 반경을 분리하지 않았다.** 현재 `UnlockedHitRadius`가 모든 화살 판정 반경으로 사용된다. 유도를 추가하면 락온 화살에 보정이 중첩될 수 있다.

## 4. 목표 체감

### ~~4.1 락온 기본 사격~~ 🚫 폐기 — 구현 대상 아님

- 화면에 락온 마커가 있는 잡귀는 정면을 향해 이동하는 동안 안정적으로 맞는다.
- 좌우로 걷는 잡귀는 가까운 거리에서 대체로 맞지만, 발사 직후 빠른 돌진/회피를 하면 피할 수 있다.
- 화살이 90도로 꺾이거나 뒤돌아가거나 벽을 돌아 맞지 않는다.
- 대상이 죽거나 사라지면 현재 방향 그대로 직진한다. 다른 적으로 자동 재유도하지 않는다.

### 4.2 비락온 사격

- 화면 중앙 조준점에 맞춰 플레이어가 직접 쏜다.
- 카메라 옆에 캐릭터가 있어도 조준점과 실제 탄도가 일치한다.
- 적을 스쳐 지나가는 작은 오차는 `0.4m` 보조 반경이 받아 준다.
- 관통 화살은 이 모드를 강제해 여러 적을 꿰는 방향 선택을 플레이어 몫으로 남긴다.

### 4.3 보정이 실패해야 하는 상황

- 조준 방향과 락온 대상 방향 차이가 12도를 넘는다.
- 대상이 서버 기준 최대 거리 밖, 사망, despawn, 유효하지 않은 레이어다.
- 총구와 대상 사이가 벽/지형으로 막혀 있다.
- 대상이 화살 뒤쪽으로 넘어가 최대 유도각을 벗어난다.
- 클라이언트가 존재하지 않는 netId나 다른 플레이어 netId를 보낸다.

위 상황에서 **공격 전체를 취소하지 않는다.** 조준 방향 자체가 유효하면 락온 후보만 버리고 비락온 화살을 발사한다. 공격 수락 뒤 대상이 사라졌다고 스태미나를 환급하지도 않는다.

### 5.2 조준점

락온은 Transform 루트가 아니라 명시적 조준점을 향해야 한다.

권장 계약:

```csharp
public interface IAimAssistTarget
{
    Vector3 AimPoint { get; }
}
```

- 일반 잡귀: 캡슐 중심보다 약간 위인 가슴 위치. 현재 2m 캡슐 기준 로컬 `Y 1.1m`부터 시작한다.
- 보스: 몸통 기본 anchor를 두고, 약점/부위 파괴를 구현할 때 부위별 anchor를 추가한다.
- 계약이 없는 임시 대상: canonical collider의 `bounds.center`로 fallback한다.
- `PlayerAttack`은 AI의 구체 클래스를 참조하지 않고 Common 계약 또는 collider/NetworkIdentity만 사용한다.

### 5.3 비락온 카메라-총구 시차 해결

오버숄더 카메라에서는 `camera.forward`로 총구에서 바로 쏘면 가까운 표적을 빗나간다. 다음 두 단계가 필요하다.

```text
카메라 중앙 ray ──▶ 조준점(첫 월드 충돌 또는 최대 거리 점)
실제 총구 ────────▶ 조준점 방향으로 화살 발사
```

1. 로컬 카메라 중앙에서 월드 충돌 레이를 쏴 `AimPoint`를 구한다.
2. 충돌이 없으면 카메라 앞 `MaxAimDistance` 지점을 쓴다.
3. 클라이언트는 로컬에서 계산한 총구 위치에서 그 점을 향한 정규화 방향만 request에 넣는다. 카메라 위치·총구 위치·조준점 좌표는 보내지 않는다.
4. 서버는 자신의 총구 위치를 만들고 받은 방향을 검증해 사용한다.
5. 총구 바로 앞에 벽이 있으면 카메라에서는 보이더라도 화살은 벽에 맞는다. 이것이 정상이다.

### ~~5.4 락온 초기 발사각 보정~~ 🚫 폐기 — 초기 보정 없음

서버가 후보를 검증한 뒤 다음 조건일 때만 방향을 대상 조준점으로 바꾼다.

```csharp
Vector3 requested = request.AimDirection.normalized;
Vector3 desired   = (target.AimPoint - muzzlePosition).normalized;

bool canSnap = Vector3.Angle(requested, desired) <= arrow.AimAssistAngle;
Vector3 initialDirection = canSnap ? desired : requested;
```

- `12도`는 후보 탐색 각도 35도와 다른 값이다. 탐색됐다고 발사 보정까지 허용되는 것은 아니다.
- 선딜 0.25초가 끝나는 release 틱에 대상 생존·거리·시야와 12도를 다시 확인한다.
- 실패하면 다른 적을 찾지 않고 request의 비락온 방향으로 쏜다.
- 방향은 XZ 평면으로 눌러 버리지 않는다. 높낮이가 있는 지형과 공중 적을 위해 3D 벡터를 유지한다.

### ~~5.5 발사 후 약한 유도~~ 🚫 폐기 — `ArrowGuidance`는 만들지 않는다

유도는 비례 보간이 아니라 초당 최대 회전각이 고정되는 `Vector3.RotateTowards`로 계산한다.

```csharp
float maxRadians = guidanceDegreesPerSecond * Mathf.Deg2Rad * deltaTime;
direction = Vector3.RotateTowards(direction, desiredDirection, maxRadians, 0f).normalized;
```

매 서버 틱 순서:

1. 수명과 유도 종료 시각 확인
2. 대상 netId로 현재 target/aim point 확인
3. 유효하면 방향을 최대 `30도/초`만 회전
4. 기존 위치에서 새 위치까지 SphereCast
5. 거리순으로 벽/적 충돌 처리
6. 남았으면 위치와 회전을 갱신

종료 조건:

- 발사 후 0.4초 경과
- 대상 사망 또는 despawn
- 목표 방향이 현재 진행 방향에서 35도 이상 벗어남
- 목표가 화살 뒤쪽으로 넘어감
- 관통 특성

0.4초 동안 가능한 총 회전량은 최대 12도다. 30m/s 기준 그동안 약 12m를 이동하므로, 가까운 잡귀의 횡이동을 조금 따라가되 멀리 도망간 적을 추격하는 유도탄은 되지 않는다.

### ~~5.6 이동 표적 선행 조준~~ 🚫 폐기 — 유도가 없으므로 선행 조준도 없다

MVP에서는 넣지 않는다.

- 소울류처럼 이동 표적은 발사 타이밍으로 피할 여지를 남길 수 있다.
- 현재 적 속도 추정값과 네트워크 지연 보정 계약이 없다.
- 초기 보정 + 0.4초 제한 유도 + 0.4m 명중 반경을 함께 쓰면 이미 보정이 세 겹이다.

L3 테스트에서 8~12m 거리의 평범한 횡이동 잡귀 명중률이 목표보다 낮을 때에만, 유도 시간을 늘리기 전에 서버 속도 기반 최대 `0.1초` 선행을 별도 실험한다.

### 5.7 충돌 반경과 장애물

현재 `UnlockedHitRadius = 0.4m`는 반경 `0.5m`인 일반 잡귀 캡슐과 합쳐져 체감 폭이 약 `0.9m`가 된다. 프로토타입에서는 기존 기획값을 유지하되 락온 유도와 중첩되는지 반드시 계측한다.

권장 데이터 분리:

| 필드 | 시작값 | 용도 |
|---|---:|---|
| `UnlockedHitRadius` | 0.40m | 비락온 명중 보조 |
| `LockedHitRadius` | 0.15m | 초기 보정+유도를 받는 락온 화살 |
| `WorldCollisionRadius` | 0.08m | 벽 모서리 통과 여부 |

적 판정은 선택된 `LockedHitRadius` 또는 `UnlockedHitRadius`, 월드 판정은 `WorldCollisionRadius`를 써야 하므로 같은 반경의 SphereCast 하나로 합치지 않는다. 두 번의 NonAlloc sweep 결과를 작은 공용 후보 버퍼에 합쳐 거리순 처리한다.

- 벽이 첫 충돌이면 그 뒤 적은 맞지 않고 화살을 소멸시킨다.
- 적이 먼저면 피해/관통 수를 처리하고, 남은 구간의 벽을 만나면 소멸한다.
- `targetMask`와 `worldMask`는 분리해 Inspector 오설정을 부트 검증에서 잡는다. 현재 프로젝트의 `Ground`뿐 아니라 실제 벽·건축물·지형이 사용하는 레이어를 실측해 worldMask에 포함한다.
- 버퍼가 가득 차면 벽 누락으로 벽 뒤 피해가 날 수 있으므로 피해를 적용하지 않고 fail-closed로 소멸한다.

### 6.2 서버 검증

순서:

1. request ID 중복·역순 검사
2. `AimDirection`의 NaN/Infinity와 최소/최대 길이 검사
3. 런 상태·생명·무기·행동 잠금·스태미나 검사
4. 현재 서버 무기가 Bow인지 확인
5. 후보 netId를 `NetworkServer.spawned`에서 조회
6. Enemy/Boss 여부, `IDamageable.IsDead`, 거리, 12도, 총구-조준점 시야 검사
7. 실패하면 후보만 0으로 만들고 유효한 free aim은 유지
8. 수락한 순간의 SO 값을 화살 실행 snapshot으로 복사

클라이언트가 임의의 방향으로 쏘는 것은 카메라 자유 조준으로도 가능한 입력이므로, 방향만으로 치팅을 판정하지 않는다. 치팅 방지는 서버의 공격 주기·자원·무기·대상·거리·장애물·피해 판정에서 한다.

### 6.3 대상 이동과 지연

- 입력 시점: 클라이언트가 현재 조준 방향과 후보 netId를 보낸다.
- Command 수락 시점: 서버가 후보를 1차 검증하고 공격 상태를 commit한다.
- release 시점: 서버가 **현재** 대상 조준점으로 2차 검증해 초기 방향을 정한다.
- 비행 중: 서버만 현재 조준점을 읽어 제한 유도를 계산한다.
- 클라이언트: 서버 `NetworkTransform` 결과를 보간해 그리기만 한다.

과거 위치 rewind는 하지 않는다. 지연이 클 때 보이는 조준점과 서버 결과가 자주 어긋나면 판정 권위를 옮기지 않고, 로컬 발사 예측과 서버 결과 보정 표현을 추가한다.

## 8. 구현 순서

### 1단계 — 조준 방향의 정상화

3. 사망/despawn/각도 이탈 시 직진 전환한다.
4. 락온/비락온 hit radius를 분리하고 명중률을 계측한다.

### ~~5단계 — 관통 특성 연결~~ 🚫 폐기 — 끌 유도가 없다. 관통은 특성 시스템에서 사거리·관통 수만 다룬다

특성 시스템이 생긴 뒤에만 `GuidanceDuration = 0`, `CandidateTargetNetId = 0`을 서버 snapshot으로 강제한다. 클라이언트가 “관통이니 유도 없음”을 결정하게 하지 않는다.

## 9. 검증 기준

### 9.1 순수 계산 테스트

- 초기 각도 `0 / 11.9 / 12.1도`에서 보정 여부가 경계값과 일치한다.
- 30도/초 유도가 한 틱에서 최대 0.5도만 회전한다. **틱은 `TimeManager.asset`의 Fixed Timestep `0.016666668`초(60Hz)다** — `AuthorityTickScheduler`가 `FixedUpdate`를 틱 경계로 삼는다. 0.02초(50Hz)로 잡으면 경계값이 어긋난다.
- 총 0.4초 동안 누적 회전이 12도를 넘지 않는다.
- 목표 방향을 지나쳐 흔들리거나 180도 되돌아가지 않는다.
- NaN, 0벡터, despawn target에서 예외 없이 직진한다.

### 9.2 L2 — Dev_Combat

각 항목 최소 10회:

| 조건 | 기대 결과 |
|---|---|
| 비락온 정면·상하 표적 | 조준점과 실제 탄도가 일치 |
| 비락온 0.39m/0.41m 스침 | 경계 안 hit, 밖 miss |
| 락온 11.9도/12.1도 | 안쪽만 초기 보정 |
| 5m/10m/15m 횡이동 | 거리별 명중률 기록, 순간이동식 추적 없음 |
| 발사 0.2초 뒤 대상 사망 | 예외 없이 직진 전환, 재타겟 없음 |
| 적 앞 벽/적 뒤 벽 | 벽 뒤 피해 0회 |
| 카메라만 엄폐물 밖, 총구는 안쪽 | 화살이 벽에 맞음 |
| 대상이 화살 뒤로 이동 | U턴 없이 직진 |
| 관통 2대 정렬 | 유도 없이 직선으로 순서대로 명중 |

기록할 값:

- request 방향
- 후보 netId와 후보 거부 사유
- 초기 보정 각도
- 유도 적용 시간과 누적 회전각
- 첫 충돌 종류/거리
- 화살별 hit netId 목록과 소멸 사유

### 9.3 L3 — 3인 접속

- 호스트 1 + 원격 클라이언트 2에서 신궁 발사·궤적·명중·소멸 결과가 세 화면에 일치한다.
- 0ms, 30~50ms, 150ms 조건에서 락온/비락온을 각 20회 실행한다.
- 같은 적을 세 명이 동시에 공격해도 대상별 중복 피해, 화살 netId 충돌, 자원 이중 차감이 0회다.
- 유도 중 대상 death/despawn을 각 10회 실행해 null 예외와 유령 피해가 0회다.
- 동시 잡귀 18~22마리에서 공격 steady-state GC Alloc 0 B/frame, query buffer overflow 0을 확인한다.

## 10. 튜닝 순서

명중률이 낮다고 네 값을 한꺼번에 올리지 않는다.

1. 조준점 위치가 가슴에 맞는지 확인
2. 카메라-총구 시차와 벽 충돌 확인
3. 락온 후보가 의도한 적인지 확인
4. `LockedHitRadius` 조정
5. `GuidanceDegreesPerSecond` 조정
6. 마지막에 `GuidanceDuration` 조정

권장 목표 명중률은 플레이 테스트용 가설이다.

| 상황 | 목표 |
|---|---:|
| 락온, 8~12m, 정지 잡귀 | 95% 이상 |
| 락온, 8~12m, 평범한 횡이동 | 75~90% |
| 락온, 돌진/회피 직후 | 명중 보장하지 않음 |
| 비락온, 8~12m, 정지 잡귀 | 플레이어 조준에 따라 결정 |
| 관통 | 자동 유도 0% |

락온 명중률이 너무 높으면 순서대로 `LockedHitRadius → 유도 속도 → 유도 시간`을 낮춘다. 비락온이 너무 어렵다면 유도를 붙이지 말고 `UnlockedHitRadius`만 조정한다.

## 11. 이번 구현에서 하지 않을 것

- 자동 headshot 또는 약점 자동 선택
- 이동 속도 기반 완전 선행 조준
- 화살이 벽을 돌아가는 경로 탐색
- 대상 사망 후 다른 적으로 재유도
- 클라이언트 명중 판정 또는 rewind
- 모든 무기를 포괄하는 범용 targeting 프레임워크
- 카메라 연출·줌·히트스톱의 완성

## 부록 A. 폐기된 락온 결론 (2026-09-03 오전)

**아래는 초판 1장 결론이다. 같은 날 오후에 락온을 폐기했으므로 구현 지시가 아니다.** 왜 그런 결론이 나왔는지 추적하기 위해서만 남긴다.

> 그믐의 신궁은 **소울류의 명시적 락온**과 **Monster Hunter: World식 수동 조준의 주도권**을 섞는 것이 맞다.
>
> - 락온: 대상 중심을 향해 발사 방향을 한 번 보정하고, 발사 후 `0.4초` 동안만 초당 최대 `30도`로 약하게 추적한다.
> - 비락온: 카메라 중앙 조준점을 향해 직선 발사한다.
> - 관통 특성: 초기 자동 조준과 유도를 모두 끈다.
> - 판정: 클라이언트는 `조준 방향 + 락온 후보 netId`만 보내고, 서버가 대상·거리·각도·생존·시야를 다시 검증한다.
> - 기존 기획 수치 `12도 / 30도·초 / 0.4초 / 비락온 반경 0.4m`.

**폐기 사유:** 정밀 사격([게임 디자인 4.5](../02-game-design.md))과 배타적이다. 자동 조준이 맞혀주면 "멈춰 서서 겨눠 맞힌다"가 성립하지 않고, 신궁의 그로기 진입로가 사라진다. 시그니처가 둘일 수 없다.

**2장의 레퍼런스 조사는 폐기 대상이 아니다.** 엘든 링·다크소울·몬헌의 조준 구조 비교는 자유 조준 수치를 튜닝할 때 그대로 쓴다.

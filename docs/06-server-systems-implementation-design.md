# 그믐 - 잔여 서버 기능 시스템 기획서

작성: 2026-09-08 / 담당: 김민성(@AidenKim923)

## 0. 목적과 문서 지위

**목표는 세 명이 파밍, 성장, 구매, 보스전, 정산, 다음 런까지 같은 결과로 완주하는 것이다.** 서버 기능은 AI·Combat·Systems·Network 폴더 구분과 무관하게 전부 김민성이 구현한다. 폴더는 코드 책임을 나누는 기준이지 작업을 다른 팀원에게 넘기는 기준이 아니다.

이 문서는 남은 P1뿐 아니라 P1을 실제로 작동시키는 P0 선행 기능, 통합·복구, 선택적 P2까지 다룬다. 코드 구현을 요청하는 문서가 아니라 **다음 구현 작업의 입력으로 사용할 시스템 설계**다. 이번 문서 작성으로 런타임 구현이나 미정 밸런스를 확정하지 않는다.

## 3. 전체 구조와 불변식

### 3.1 책임 배치

| 계층 | 권위 원본 | 다른 계층에 제공 |
|---|---|---|
| Network | 런 ID, 참가자, 씬 전환, 정지 사유, 시계, 종료 확정 | 런 수명 이벤트, 시간/참가자 인터페이스, 결과 snapshot |
| Systems | 장비 소유, 보관함, 레벨/포인트, 특성, 팀 지갑, 거래, 통계 | 유효 전투 snapshot, 지급/차감 결과, 정산 함수 |
| Combat | 입력 수락, 자원, 플레이어 생명, 판정과 실제 적용량 | 피해/회복/카운터 사실, 플레이어 상태 인터페이스 |
| AI | 적 실행, 보스 패턴/부위/원혼, 스폰/몰이 | 타격 원본, 예고, 적 사망/부위 파괴 사실 |
| Common | 계층 간 인터페이스와 값 타입 | 구체 클래스 대신 연결할 계약 |
| Art·UI | 권위 상태의 표현만 | 요청 입력. 피해/구매/전멸을 확정하지 않음 |

상호작용 요청부터 결과까지의 의존 흐름은 다음과 같다.

```text
플레이어 소유 요청
  -> 신원/런/세대/중복 검사
  -> 도메인 검증과 변경 계획
  -> 서버 원본 1회 커밋
       -> 소비자용 snapshot 갱신
       -> SyncVar/SyncList 또는 RPC로 결과 전달
       -> 서버 사실 집계
```

새 네트워크 프레임워크, 서버 이전, 이벤트 저장소 전체 재설계는 하지 않는다. 기존 `PlayerActionPipeline`, `AuthorityTickScheduler`, carrier, provider, 로케이터를 확장한다. 패링은 현재의 별도 시간 보정 프로토콜을 유지한다.

### 3.2 반드시 지킬 불변식

1. 런 결과는 하나이며 결과 확정 후 자원·아이템·점수가 더 바뀌지 않는다.
2. 장비 ID 하나는 월드 드랍, 한 참가자의 보관함, 장착 중 하나에만 존재한다.
3. 거래 실패는 잔액·슬롯·장비·효과를 바꾸지 않는다.
4. 행동 한 번은 수락 시점의 전투 snapshot을 끝까지 사용한다.
5. 재접속은 새 참가자 생성이 아니라 같은 `ParticipantId`의 복구다.
6. 게임 시간이 멈추면 성장/시전/표식/그로기/원혼/몰이 타이머도 멈춘다.
7. 한 그로기에서 꼬리는 최대 한 덩이만 파괴되고 초과 피해는 이월되지 않는다.
8. 원혼 제거 진척은 실패 시에도 남으며 어떤 직업 편성도 일반 피해로 돌파 가능하다.
9. 표현이 없거나 늦어도 서버 결과가 바뀌지 않는다. 단, 표현 미검증을 플레이 완료로 보지는 않는다.

## 4. 공통 요청·시간·복구 계약

### 4.1 요청 검증과 중복 처리

제안 요청 헤더: `RunId`, `SceneRevision`, `RequestId`, 재접속 요청 세대. 아이템 작업은 `ItemInstanceId`, `InventoryRevision`; 구조는 대상 `ParticipantId`, `DeathGeneration` 또는 `SwallowGeneration`을 추가한다.

- 호출자는 연결의 소유 플레이어에서 정한다. 클라이언트가 보낸 송신자 ID를 믿지 않는다.
- 일반 게이트: 런 진행 중, 정지/전환 아님, 허용 생명 상태, 요청 빈도 및 유한한 입력.
- 대상 게이트: 같은 런/씬, 아직 살아 있는 대상, 서버 위치 기반 거리/시야, 현재 소유권과 revision.
- 같은 요청은 다시 적용하지 않는다. 거래는 최근 결과를 제한된 캐시에 보관해 재전송에 같은 결과를 반환하는 방식을 제안한다. 오래된 요청은 만료로 거부한다.
- 멱등 키는 `RunId + ParticipantId + 요청 세대 + RequestId + 작업 종류`. 요청 ID 래핑과 새 연결의 0부터 시작을 구분한다.
- 무한 로그/캐시를 만들지 않는다. 캐시 크기와 빈도 제한은 계약 상수로 지정하고 런 종료/세대 변경에서 정리한다.

`InvalidState`, `Paused`, `StaleRevision`, `OutOfRange`, `InventoryFull`, `InsufficientCurrency`, `AlreadyConsumed`, `Expired` 등을 제안 공통 거부 사유로 둔다. UI 문구와 서버 로그가 같은 이유를 보게 한다.

### 4.2 시계의 역할

| 시간 | 사용할 곳 | 주의 |
|---|---|---|
| `IRunTimeSource.GameplayElapsedSeconds` 및 구간 시계 | 표식, 상점·거래, 보스 상태, 게임 진행 타이머 | 이탈 대기/전환/컷신 정지 시간 제외 |
| `NetworkTime.time` | 기존 패링 보정, 네트워크 예고의 절대 시각, 통신 관련 제한 | 정지 시간에도 증가하므로 그대로 게임 만료 시각으로 쓰지 않음 |
| 실시간 대기 | 씬 로드/연결 도착 제한 | 게임 정지 때문에 통신 타임아웃까지 영구 정지시키지 않음 |

보스 실행은 게임 진행 시간으로 남은 양을 보존하고, 재개 시 예고의 네트워크 절대 시각과 패링 창을 **동일한 시간 보정 경로**로 갱신한다. 한쪽만 밀면 보이는 예고와 성공 창이 어긋난다. 로컬 렌더러에는 정지 상태/잔여 시간도 전달한다.

### 4.3 복구 데이터

`RunParticipantSnapshot`에 장착 장비, 인벤토리 12칸 고정 배열, 인벤토리 revision, 레벨/누적 XP, 특성 배분/미사용 포인트, 개인 지표, 생명 세대, 삼켜짐 잔여 시간을 추가한다. 팀 지갑은 참가자 snapshot마다 복제하지 않고 런 소유 상태로 유지한다.

복구 순서 제안: 헤더 전체 검증 -> 성장/소유권 -> 무기/특성 -> 유효 최대치 계산 -> 현재 HP/자원/생명 -> 위치 -> 행동 허용. 현재 HP를 먼저 clamp하면 아직 낮은 기본 최대 HP 때문에 복구 HP를 잃을 수 있다.

전송·복구 schema 버전과 `CaptureRevision`을 검사한다. 검증이 하나라도 실패하면 전원 복구/준비가 끝난 것으로 커밋하지 않는다. 부분 복구된 객체는 입력 잠금 상태로 두고 기존 전환 실패 경로로 정리한다.

씬을 떠날 때 일회성 공격/거래는 종료한다. 같은 씬 재접속은 멈춘 월드 상태를 유지하되 과거 연결의 요청은 받지 않는다. 효과 소유자는 netId가 아닌 참가자 ID로 보존한다.

줍기·양도·객주는 서버 기준으로 피해를 주거나 받은 뒤 5초가 지나야 한다. 구조에는 이 조건을 적용하지 않는다. 거리와 시야는 서버가 검사한다. 안내 프롬프트가 떠 있었다는 사실은 승인 근거가 아니다.

시작 시 플레이어에 인터페이스 참조를 캐시한다. 물건마다 Command를 추가해 검증을 복제하지 않는다. `IInteractable.CanInteract` 성공 후 시간이 지난 상태로 `Interact`만 따로 실행하지 않는다.

**완료 기준:** 3인 동시 줍기의 소유자 합계 1, 양도 수락 직전 장착/드랍/재접속 시 복제 0, 실패 시 슬롯/재화 변화 0, 복구 후 인벤토리 12칸과 각 칸 수량이 서버 원본과 일치.

## 7. S03 - 레벨, 특성, 전투 snapshot

대응: U06·U07·U12. 장비 골격과 함께 만들되 행동 변형은 단계적으로 연결한다.

### 7.1 성장

제안 `GrowthManager`가 적 보상 사실을 중복 없이 받아 파티 XP를 누적하고 `LevelCurveSO`를 따른다. 사망/관전 중인 참가자도 성장 상태를 유지한다. 이탈 시 진행 자체가 멈추지만, 연결 객체 유무 때문에 확정 보상이 누락되지 않도록 참가자 원본을 갱신한다.

한 번의 XP로 여러 레벨을 넘으면 반복 계산한다. 레벨 상한과 포인트 총량을 검증한다. 최대 HP 증가와 현재 HP 회복은 별개다. 레벨업으로 자동 부활하지 않는다. 현재 HP 증가 정책은 확정 전까지 17장의 결정 항목으로 남긴다.

### 7.2 특성

현재 `TalentTreeSO.NodeEntry.Value` 하나로는 효과 의미를 안전하게 구분할 수 없다. 제안 필드: `EffectKind`, 적용 무기, 선행 노드 ID, 포인트 비용, 수치/스택 정책. 효과별 해석은 enum/작은 실행 전략으로 구현하고 문자열 이름 비교를 하지 않는다.

수락 조건: 유효 노드, 현재 무기, 선행 충족, 중복 미구매, 가용 포인트, 최신 revision. 확정 후 포인트 차감과 배분을 함께 반영한다. 무료 초기화는 포인트 환급/배분 제거/효과 재계산을 한 번에 한다. 이전 snapshot을 계속 더하는 방식으로 효과를 누적하지 않는다.

핵심 변형 범위: 차사 패링 성장과 검 3타 변형, 신궁 연사/관통, 무녀 치유 강화/지원 버프. 실제 노드 30개의 수치·선행·해금표는 비어 있으므로 생산 에셋 확정이 필요하다. 무녀 부활 시간 변경 노드는 만들지 않는다.

### 7.3 유효 수치 산출과 소비

Systems의 계산기가 `ICombatLoadoutProvider`를 구현한다. 현재 `CombatStatsSnapshot`에는 revision/최대 HP/근접·원거리 공격력만 있으므로 비용·속도·치명·패링·관통·회복·버프 필드를 소비자와 함께 확장한다.

계산 순서 **제안**: 기본 무기 또는 장비 공격력 선택 -> 합산 가능한 고정 증가 -> 같은 계열 비율 증가 합산 -> 별도 곱연산 효과 -> SO 상한/하한 적용. 옵션/특성 간 합산 정책은 17장에서 확정한다. 시작 무기에는 현재 CombatConfig 기본값을 명시적으로 사용하고, 필수 provider 누락을 정상 무기 없음으로 숨기지 않는다.

**수락 순간 snapshot 고정**을 기존 타입의 계약대로 지킨다. 시전/연사 도중 장비나 특성이 바뀌어도 이미 수락된 행동의 피해·비용·발 수는 바뀌지 않는다. 연사의 각 화살은 같은 action ID에 shot index를 갖고, 자원/치명 준비/패링 게이지 소비는 행동 단위로 한 번이다.

피해를 받는 쪽의 현재 무적·그로기·꼬리 활성·표식 여부는 명중 시 판정한다. 공격자의 고정 snapshot과 대상의 현재 방어 상태를 혼동하지 않는다.

**완료 기준:** 같은 입력의 합산 결과 결정적, 초기화/무기 교체 후 포인트 보존, 연사 N발에도 비용 1회, 시전 중 장비 변경으로 이중 이득 없음, 재접속 후 같은 수치 복구.

## 8. S04 - 공용 재화, 구매, 물약, 부활 비용

대응: U10·U11·U13.

제안 `CurrencyManager`가 런의 단일 정수 잔액을 소유한다. UI는 이 값만 표시한다. 구매·권 사용은 **검증 -> 변경 계획 -> 원본 커밋 -> 결과 통지**로 처리하며 커밋 중 코루틴/yield/외부 호출을 넣지 않는다. 메인 스레드여도 이벤트 콜백의 재진입이 있으므로 중간 상태를 이벤트로 공개하지 않는다.

| 작업 | 검사 | 한 번에 확정하는 것 |
|---|---|---|
| 물약 구매 | 객주 단계/거리/비전투, 상품, 잔액, 빈 칸 또는 스택 여유 | 잔액 차감 + 인벤토리 칸의 수량 증가 |
| 재조정 | 장비 소유/ID/revision, 상품/잔액 | 차감 + 같은 등급 범위의 새 롤 결과 |
| 등급 상승 | 최대 등급 아님, 장비 소유/revision | 차감 + 한 등급 상승/재굴림 |
| 물약 사용 | 생존/허용 행동, 수량, 자원 부족, 회복 허용 | 실제 회복 성공 + 수량 1 감소 |
| 일반 부활 | 현재 사망 세대, 부활 미확정, 런 진행 중 | 부활 상태 + 잔액 비율 손실 |

상품 가격/효과/소지 제한은 `ShopSO`, 부활 비율은 `CombatConfigSO`를 사용한다. 티켓을 실제 보관 아이템으로 만들지, 객주에서 즉시 서비스를 적용할지는 기존 상세 설계의 즉시 적용을 우선 제안하며 17장에 남긴다.

HP 회복은 `IRecoveryTarget`이 결계 배수를 한 번 적용한다. 회복 실패에는 물약을 쓰지 않는다. 신력 회복도 같은 원칙의 공용 창구를 추가하되 현재 인터페이스가 이미 제공한다고 가정하지 않는다. 결계 밖 회복 봉쇄·최대 자원에서의 소비를 검증한다.

부활 손실은 `floor(확정 직전 잔액 × 손실 비율)`. 자동 20%, 구조 10%이며 현재 사망 세대에 한 번만 적용한다. 잔액 0이어도 부활을 막지 않는다. 구조와 자동 부활이 같은 틱에 완료되는 경우의 우선순위는 **구조 우선 제안**으로 17장에서 확정한다.

**완료 기준:** 잔액 하나로 2명이 동시 구매해도 음수/무상 지급 없음, 최대 등급 상승 실패 무차감, 회복 실패 무소비, 같은 사망 세대의 자동/구조 경합에 비용 1회.

## 9. S05 - 표식 수명과 3직업 카운터

대응: U05·U16·U20.

### 9.1 표식

기존 `MarkRegistry`를 단일 원본으로 유지한다. 키는 소유 `ParticipantId`와 대상 `RunId/SceneRevision/netId/PartId`다. 무녀마다 2슬롯, 8초 지속. 부여 시각을 일반 타격마다 갱신하지 않는다.

현재 `ServerNotifyPatternEnded`와 `MarkRegistry.IsMarkedWithin`이 본체 표식의 최근 부여를 검사하고 공격당 한 번 감소시킨다. 이 연결을 다시 만들지 않는다. 현재 조회는 `NetworkTime.time`이고 “패턴 종료”를 판정 종료로 취급하므로, 아래 게임 시간·정상 종료 정의로 정합성을 보강해야 한다.

- 런 초기화/이전 씬 대상 폐기에서 해당 표식을 정리한다. 대상 파괴 시 즉시 해제한다.
- 같은 씬 이탈 대기는 표식도 정지하며 소유자는 유지한다. 역할 변경으로 더 이상 유지할 수 없는 표식은 규칙에 따라 해제한다.
- 본체의 판정 창 확대, 부위 추가 피해, 그로기 시 신력 환급을 각각 **서버 소비 지점 하나**에 연결한다. 보스 그로기 총 시간은 늘리지 않는다.
- 취소된 패턴을 자연 종료한 것으로 처리하지 않는다. 무녀 공명은 패턴 4/8의 정상 종료에서만 검사한다.
- 검사 조건은 본체 표식 활성 AND `0 <= 종료 게임 시각 - 부여 게임 시각 <= BrandWindow`. 별도 3초 디버프가 아니다.
- 슬롯에서 밀려난 표식을 즉시 재부여하는 것으로 대상별 재부여 제한을 우회할 수 없는지도 확인한다. 필요하면 활성 슬롯과 별개로 제한된 재부여 이력을 둔다.

### 9.2 카운터 수락

제안 Common 카운터 입력: 원본 공격 ID, 카운터 종류, 가해 참가자, 대상 부위, 서버 명중 시각. 플레이어가 직접 “게이지를 깎아라”라는 Command를 보내는 구조는 금지한다.

| 종류 | 서버가 확인할 사실 | 효과 |
|---|---|---|
| 차사 | 현재 패링 가능한 실행의 성공 통지 | 실행 취소, SO 게이지 감소 |
| 신궁 | 정밀 플래그를 가진 서버 발사체가 중단 허용 창에 명중 | 해당 실행 취소, SO 게이지 감소 |
| 무녀 | 허용 패턴 정상 종료 때 최근 본체 표식 존재 | SO 게이지 감소, 표식 보상 규칙 적용 |

그로기/면역 중 감소는 버리고 적립하지 않는다. 제안 공통 중복 키는 **공격 전체 ID + 카운터 종류**다. 같은 연사/펄스의 통지가 반복돼도 보스 게이지를 여러 번 깎지 않는다. 현재 무녀 감소는 공격당 1회이므로 이를 기준선으로 유지하고, 다수 무녀의 귀속/신력 보상은 17장에서 확정한다. 슬롯 자체는 소유자별로 분리한다.

### 9.3 정밀 사격

서버 상태 제안: Idle -> Holding -> PrecisionReady -> Released -> Recovery. 우클릭 유지로 시작, 0.6초 후 정밀 준비, 해제 때 발사. 홀드 중 이동 속도 40%, 발사 비용 스태미나 15는 SO에 둔다. 미충전 해제/홀드 취소의 비용과 동작은 17장에서 확정한다.

클라이언트는 방향과 시작/해제 의도를 보낸다. 서버는 시작 시간을 기록하고 최소 유지 시간을 직접 검증한다. 조준 원점의 허용 범위·방향의 유한성/길이·각도·거리·현재 상태를 확인한다. 클라이언트가 보낸 명중 대상은 판정 결과로 쓰지 않는다.

자유 조준 목표점까지의 선과 실제 총구에서 나가는 사선을 구분한다. 벽 뒤 총구에서는 벽이 먼저 맞는다. 락온 보조는 유지하되 머리/꼬리의 서버 판정 콜라이더를 기준으로 한다. 명중 시 중단 가능 여부는 그 순간 서버 실행 상태에서 판단하고, 끝난 공격을 되돌려 취소하지 않는다.

**완료 기준:** 준비 시간 위조/NaN/벽 뒤 발사 차단, 연사 중복 카운터 없음, 오래된 표식은 창 확대에는 쓰여도 보스 감소에는 실패, 면역 중 지연 명중의 게이지 변화 0.

## 10. S06 - 데이터 기반 보스 실행과 예고

대응: U17·U18·U21·U22.

### 10.1 이미 구현한 취소를 확장한다

`CancelActiveAttack`과 `Exit`를 유지하고 페이즈 교체·그로기·사망·Result에서 예약 타격/창/예고를 정리한다. 새로운 연타/장판/원혼 실행도 같은 취소 소유권 아래 둔다. 코루틴을 개별로 시작하고 핸들 없이 버리지 않는다.

현재 `OnDisable`의 재개 가능한 정지와 최종 종료가 분리돼 있다. 일시 비활성화 후 재개를 영구 종료로 되돌리지 않는다. 이 객체 수명 정지/재개와 런 일시정지의 절대 예고 시각 보정은 서로 다른 문제다.

### 10.2 SO 이관과 선택기

1차는 코드 상수의 **동일 값 이관**이다. 현재 사거리·각도·돌진 속도·반복 수를 SO로 옮기며 RNG 순서와 동작을 바꾸지 않는다. 2차에서 선택기/연타를 변경한다.

제안 PatternEntry 추가 항목: TemplateKind, Phase, Range/Radius/Angle, TargetPolicy, RepeatCount/Interval, ParryableRepeatIndex, Interruptible, IndividualCooldown, SelectionWeight, DerivedFrom, ConditionalTrigger, RecoveryDuration. 관련 데이터가 빠진 패턴을 기본값 공격으로 대체하지 않는다.

선택 순서: 현재 페이즈/봉인/조건 확인 -> 거리 필터 -> 개별 쿨다운과 직전 반복 제외 -> 가중치 추첨. 1페이즈 오프닝 1→2→4는 별도 고정 시퀀스다. 파생 2번과 조건부 10번을 쿨다운 0인 일반 후보로 만들지 않는다. 후보가 없으면 대기/접근하고 매 틱 오류 로그를 쏟지 않는다.

네 템플릿만 사용한다: MeleeArc, TargetedDash, MarkedCircle, ConeBurst. 8번은 생존 대상 목록과 순서를 서버가 고정한 순차 예고로, 9번은 반복 실행으로 확장한다. 대상 사망/소실 시 남은 대상 처리와 이미 지난 타격 재실행 금지를 테스트한다.

### 10.3 공격 ID와 다중 예고

현재 9번은 펄스마다 새 공격 ID를 발급하고 예고는 SyncVar 한 건이다. 이 상태로 다중 대상/연타 전체 취소를 완성했다고 보지 않는다.

**제안:** 연속 패턴 한 실행에 AttackInstanceId 하나, 하위 타격에 RepeatIndex, 개인 원에는 TargetId를 부여한다. 예고 키는 `(보스 식별자, AttackInstanceId, RepeatIndex, TargetId)`다. 공격 전체 취소는 모든 하위 키를 종료한다. 패링 window도 어느 하위 타격인지 명시한다.

활성 예고 집합은 제한된 크기로 동기화하여 재접속/늦은 구독이 현재 상태를 복원하게 한다. Begin/Cancel RPC를 쓰더라도 활성 snapshot과 revision을 함께 제공한다. 취소 tombstone보다 오래된 Begin은 버리고, impact가 지난 예고는 재생하지 않는다. 구체 전송 형식은 최대 동시 예고 수를 확정한 뒤 선택한다.

현재 SyncVar 한 건은 동기화 간격 안에서 시작과 취소가 모두 일어나면 중간 상태를 전달하지 않을 수 있다. 간격을 줄이는 것만으로 이벤트 전달을 보장하지 않는다. 현재 활성 상태 복원과 반드시 보일 일회성 피드백을 나누어 전송하고 L3에서 확인한다.

### 10.4 광폭화·그로기 기상

보스 시계의 경고 720초, 광폭화 810초를 한 번씩 전이시키고 제한 840초의 종료는 RunManager에 남긴다. 광폭화 배율/간격은 SO에서 읽는다. 이미 시작한 공격은 수락 시점 수치를 유지하고 이후 실행부터 광폭화 수치를 적용하는 방식을 제안한다.

그로기 무저항 8초와 기상 예고 2초, 전체 10초, 이후 면역 8초는 서버 상태/시각으로 전달한다. 기상 후 고정 공격과 꼬리 봉인 정책이 충돌하지 않도록 일반 선택과 기상 강제 선택을 분리한다. 최종 기상 PatternId와 봉인 목록은 생산 데이터 확정 항목이다.

**완료 기준:** 1~10 각 실행과 취소 경로 재현, 모든 반복 피해 1회, 늦은 예고로 유령 장판 없음, pause 중 광폭화/쿨다운 진행 0, 경고/광폭화/종료 경계 시각 시험 통과.

## 11. S07 - 꼬리 파괴와 25% 본체 게이트

대응: U19·U20.

제안 `BossPartController`가 부위 순서/HP/파괴/활성 그로기 세대를 관리하고 부위 collider adapter가 `IDamageable`로 전달한다. 본체/부위는 기존 `DamageTargetResolver`를 사용한다. 서버 콜라이더는 고정된 판정 기준이며 클라이언트 꼬리 본 흔들림에 붙여 판정 결과를 바꾸지 않는다.

1. 2페이즈 그로기 진입 시 남은 꼬리 중 하나를 지정한다. 선택은 고정 PartId 순서를 초기 제안으로 둔다.
2. 지정한 꼬리만 피해를 받는다. 그로기 부위 배율과 표식 배율은 서로 다른 효과이며 각각 한 번 적용한다.
3. 해당 HP가 0이면 그 그로기의 파괴 가능 횟수를 소진한다. 남은 피해는 버리고 다음 꼬리를 즉시 열지 않는다.
4. 파괴로 확정된 PatternId만 봉인하고 드랍은 부위 세대별 1회 지급한다. 백귀야행 ID는 봉인 대상에서 제외한다.
5. 지정 꼬리가 그로기 종료까지 남으면 미결 공격력 배율을 적용한다. 누적하지 않으며 대상 파괴 시 해제한다.
6. 모든 꼬리가 파괴되기 전 본체 HP는 최대 HP의 25% 아래로 내려가지 않는다. 부위 피해는 본체에 전달하지 않는다.
7. 마지막 부위 파괴에서는 최종 구간 진입/본체 무적을 같은 서버 변경으로 확정한다. 같은 틱의 뒤늦은 본체 피해가 보스를 먼저 죽이지 않게 한다.

**완료 기준:** 3인 동시 치명/관통에도 1그로기 최대 1파괴, 부위 오버킬 본체 유출 0, 한 타격의 중복 collider 피해 0, 마지막 파괴와 본체 타격 경합에서도 최종 구간 1회 진입.

## 12. S08 - 원혼, 백귀야행, 삼켜짐

대응: U23. 최종 구간 상태 소유자는 보스 실행 안의 전용 상태로 둔다.

| 상태 | 진입/처리 | 다음 상태 |
|---|---|---|
| 진입 | 이전 공격 취소, 본체 무적, 원혼 3체 생성, 제거 비트 0 | 원혼 창 |
| 원혼 창 | 정면 패링/후방 정밀 중단/중앙 표식 맥동을 각각 판정. 일반 피해 처치도 허용 | 전부 제거면 처치 구간, 창 만료면 백귀야행 |
| 백귀야행 | `3 - 누적 제거 수` 갈래를 한 번 실행. 제거 진척 유지 | 남은 원혼으로 새 창 |
| 처치 구간 | 본체 무적 해제, 아직 삼켜진 참가자를 HP 30%로 복귀 | 일반 보스 처치/런 종료 |

세 원혼에 별도 상태/HP/식별자를 두고 순서를 강요하지 않는다. 창 종료 틱에 마지막 원혼도 제거되면 **그 틱의 유효 제거 결과를 모은 뒤** 실패 여부를 결정하는 방식을 제안한다. 실패 진입 전 제거가 끝났으면 백귀야행을 생성하지 않는다. 실패 패턴 중 마지막 원혼이 사라질 때 예약 공격을 즉시 취소할지 끝낼지는 17장에서 결정한다.

### 삼켜짐 생명 전이

무적 기믹 구간에서 HP 0 -> Swallowed(사망 아님, 이동/공격 금지, 10초 제한).

- 동료가 2초 구조 유지 성공: HP 30% 복귀. 사망 통계·재화 손실 없음.
- 개인 제한 만료: 일반 사망으로 전환. 이때 사망 통계 1회, 이후 관전/부활 규칙 적용.
- 기믹 성공: 아직 Swallowed인 사람을 해제한다. 이미 사망 전환된 사람까지 공짜 부활시키지 않는다.
- 전원 Swallowed만으로 PartyWipe를 만들지 않는다. 전멸은 일반 사망 상태 기준으로 판단한다.
- 일반 구조와 삼켜짐 구조는 시간/보상/허용 상태를 구분한다. 세대 ID로 만료·구조·기믹 성공 경합을 한 번만 처리한다.

현재 Common의 `PlayerLifeSnapshotState.Swallowed`와 잔여 시간 필드는 저장 형태만 있다. Combat 생명 상태, 이동/입력 게이트, 구조, 스냅샷 변환, 전멸 판정까지 연결해야 기능이다.

**완료 기준:** 3개 독립 제거, 동일 직업 3인 일반 피해 돌파, 부분 성공 뒤 제거 원혼 재생성 0, 삼켜짐 구조와 만료 동시 발생에 전이 1회, 재접속 후 잔여 시간 동일.

## 13. S09 - 이동 결계와 잡귀 몰이

대응: U24, 선택적 U25.

현재 `IBarrierState`는 보간 중 현재 원만 제공한다. 목표 원과 전환 revision 조회를 추가하고 BarrierController가 같은 원본을 노출하게 한다.

| 판단 | 사용할 기준 |
|---|---|
| 플레이어의 결계 피해/회복 | 보간 중 현재 원, XZ 거리 |
| 곧 밀려날 잡귀/클러스터 선정 | 서버가 확정한 목표 원 |
| 강화 중복 방지 | 개체가 마지막으로 적용받은 전환 revision |

목표 원을 경고 시점에 이미 확정해 공유한다. 확정 시각과 소비 시각을 함께 정하지 않으면 “축소 전 몰이”를 구현할 수 없다. 몰이는 기존 Brain에 전용 행동 상태를 추가하며 유효 경로를 따라 안쪽으로 이동한다. 경로 실패 재시도 간격/대체 지점은 SO 정책으로 두고 텔레포트를 무단 대체재로 쓰지 않는다.

강화는 전환당 한 번, 현재 HP 비율 보존, 보상 배수는 강화 시점 값으로 개체에 저장한다. 전환 직후 60초 신규 스폰 정지와 임시 동시 상한 1.5배는 기존 기획대로 적용한다. 3차 일반 잡귀 신규 스폰 중단도 유지한다.

기본 몰이 검증 뒤 접두사 속도/사망 장판/1회 부활을 선택적 P2로 추가한다. 부활 적은 첫 죽음과 최종 사망의 보상 계약을 먼저 고정한다. 이 작업을 위해 독립 범용 버프 프레임워크를 만들지 않는다.

**완료 기준:** 현재 원과 목표 원이 크게 다른 장면에서도 선정 정확, 같은 revision 강화 1회, 부상 적 HP 비율 보존, pause/재접속/두 번째 런에서 몰이 재현.

## 14. S10 - 정산, 개인 지표, 기록

대응: U14.

제안 `RunStatistics`는 사실을 모으고 `IRunResultProvider` 구현은 전달받은 사실에 `ScoreRuleSO` 계산만 적용한다. 현재 인터페이스는 **점수 계산 함수**이므로 누락된 처치/잔액 원본을 이 함수 안에서 씬 탐색으로 메우지 않는다.

- 서버 피해 적용 지점에서 실제 감소 HP를 집계한다. 요청 피해량이나 오버킬을 그대로 개인 피해로 더하지 않는 방식을 제안한다.
- 회복도 실제 증가 HP를 기록해 과치유를 제외한다. 피해/치유 통계 정의는 생산 적용 전 17장에서 확정한다.
- 처치/사망/구조는 고유 대상 생명 세대와 action ID로 중복을 막는다. 삼켜짐 자체는 사망 횟수가 아니다.
- 가해 netId를 사건 시점에 ParticipantId로 변환한다. 결과 시점에 파괴된 NetworkIdentity를 찾아 귀속하지 않는다.
- 참가자별 피해·치유·구조와 팀 처치·사망·잔액·잔여 HP, 두 시계, RunMode를 최종 snapshot에 담는다.
- 종료 후보 중재 후 사실을 동결하고 점수·등급을 한 번 계산한다. 객체 정리 뒤 잔여 HP를 읽지 않는다.
- 저장 키는 런/결과 revision. Standard 승리만 리더보드 대상이며 실패도 결과 화면은 표시한다.

로컬 저장은 서버 확정 결과를 각 클라이언트가 기록하는 수준이다. 로컬 파일이 위변조 불가능한 온라인 순위라는 주장은 하지 않는다. 온라인 백엔드/안티치트 서버는 범위 밖이다. 10/8 절단 판단에서 저장을 빼더라도 결과창과 점수 원본은 남긴다.

**완료 기준:** 세 화면의 팀 점수/항목 동일, 이탈자 기록 보존, overkill/과치유 정의 일치, 중복 사망/구조 집계 없음, 트라이·실패 저장 제외, 두 런 기록 독립.

## 15. S11 - 표현 공급과 출시 안전장치

대응: U01·U26~U29·U32·U35~U39·U41 중 서버 범위.

| 항목 | 서버에서 남길 산출물 | 이 문서 범위 밖 |
|---|---|---|
| 행동/애니메이션 | 행동 ID, 종류, 시작/종료·취소, snapshot revision | 클립·Animator·VFX 제작 |
| 보스 아레나/컷신 | phase, 전환 revision, 시작 시각, 단계별 입력/공격 잠금 | Timeline·카메라·재질 연출 |
| HUD·결과·상점 | 현재 상태 조회와 요청 결과/거부 사유 | 화면 배치/아이콘 |
| 낮밤/날씨 | 필드/보스 게임 시계 | 조명과 날씨 렌더링 |
| 보스 트라이 | 서버 모드, 준비된 편성/장비, 재시도 초기화, 기록 제외 | 트라이 메뉴 디자인 |
| 부트 검증 | 필수 SO, ID/참조/범위, 빈 특성, 패턴 형상, collider/레이어, 등록 prefab 검사 | 에셋 조달 |
| 서버 목표 검증 | 락온 대상·부위·거리·시야, 원격 투사체 권위 회귀 | 조준점 외형 |

컷신 완료를 클라이언트 애니메이션 이벤트가 서버에 알려 주는 구조로 만들지 않는다. 서버 타임라인이 잠금을 풀고 클라이언트는 그 상태를 따른다. 입력 잠금 8초 뒤 회복 구간 7초에도 보스가 공격을 재개하지 않도록 **플레이어 입력 잠금과 보스 공격 잠금을 분리**한다.

필수 데이터가 빠진 릴리스는 명시적으로 부트를 실패시킨다. `FrameRecorder` 등 개발 도구가 빠졌다는 이유로 정상 릴리스를 거부하지 않도록 프로필을 분리한다. 이미 반영한 SO YAML 기본값을 다시 미구현으로 세지 않고, 새 필드의 검증을 확장한다.

작성 중 `DevToolHost`의 개발 도구 자동 생성과 빌드 시작 씬 Boot 전환이 반영됐다. 이를 미착수로 되돌리지 않는다. 남은 것은 실제 부트 검사 프로필과 릴리스 빌드 경로에서 불필요한 필수 의존이 없는지 확인하는 일이다.

## 16. 실제 구현 순서와 납품 단위

기존 U번호의 P등급과 아래 순서를 혼동하지 않는다. **구현 순서는 의존성 순서**이며, P1을 먼저 요청받았어도 지갑/소유권 없이 구매나 특성을 붙이지 않는다.

| 단계 | 작업 묶음 | 선행 | 이 단계가 끝났다는 증거 |
|---|---|---|---|
| A | S01 런 완주 + 공통 요청/시간/표식 수명 | 기존 보스 취소 기반 | 게이트부터 결과/다음 런, 승리·시간초과 경합 |
| B | S02 장비/줍기 + S03 레벨/기본 snapshot | A | 처치 -> 보상 -> 장착 -> 실제 피해 증가 -> 재접속 복구 |
| C | S04 경제 + S02 양도 + S03 특성 핵심 | B | 구매/부활 차감/양도 경합, 특성으로 행동이 달라짐 |
| D | S05 정밀·공명 + S06 데이터/다중 예고 | A, 기본 snapshot B | 세 직업 카운터, 연타 취소, 일시정지 보정 |
| E | S07 꼬리 -> S08 원혼·삼켜짐, S06 광폭화 | D | 보스전 전체 승리/실패, 자유 편성 돌파 |
| F | S09 몰이 + S10 실제 정산 + S11 통합 | B~E. 통계 수집 지점은 B부터 함께 연결 | 필드·경제·보스·결과 전부 같은 빌드에서 완주 |
| G | 경합/두 런/재접속 집중 검증, 선택적 P2 판단 | F | 10/15 통합 빌드, 10/22 동결 게이트 |

S09 기본 몰이는 B 이후 E와 독립적으로 착수할 수 있다. 담당자가 한 명이므로 동시 착수를 전제로 일정을 계산하지 않는다. 파트별 명칭으로 작업을 나누기보다 위의 플레이 가능한 단위로 나눈다.

각 단위의 체크리스트는 동일하다: Common 계약 -> 순수 규칙/단위 테스트 -> 서버 실행 -> 저장/복구 -> 표현용 결과 -> 프리팹 배선 -> L1/L2 -> 3PC 경합 검사. 정산 이벤트와 복구 필드를 마지막 주까지 미루지 않는다.

U15 실행기 추출은 특성 구현에서 중복이 실제로 생길 때만 하고, U25 접두사 확장은 기본 루프 이후로 둔다. 10/22 이후 신규 기능을 끼워 넣지 않는다. 서버 담당 변경 후 남은 공수는 단계 B/D의 실제 소요를 보고 재산정하며 이 문서는 완료일을 보장하지 않는다.

## 17. 구현 전에 닫아야 할 결정

**2026-09-08 전 항목 확정.** 아래 16건은 팀장 결정으로 닫혔다. 구현 중 임의로 뒤집지 않는다.
수치 자체(특성 30노드 값, 꼬리별 봉인 PatternId, 패턴 가중치 2차 조정)는 별도 밸런싱 작업이며 이 표의 결정 대상이 아니다.

|---|---|---|---|
| D01 | 초기 기본 무기와 인벤토리 관계 | 기본 무기(`InstanceId == 0`)는 인벤토리에 들어가지 않는다. 교체 시 소멸하며 언제든 재생성한다. 인벤토리는 `InstanceId >= 1`만 받는다 | B |
| D02 | 레벨업 현재 HP | 최대 HP 증가분과 같은 절대량만 현재 HP에 더한다. 비율 보존도 전회복도 아니다. 사망 중 레벨업으로 자동 부활하지 않는다 | B |

| D06 | 정밀 홀드 조기 해제 | 0.6초 미만 해제는 발사 없이 취소하고 비용 0. 미충전 일반 사격은 나가지 않는다 | D |
| D07 | 여러 무녀의 동일 공격 공명 | 보스 게이지 감소는 공격당 1회. 신력 환급은 조건을 충족한 무녀 전원에게 지급한다. 공명은 표식을 소비하지 않는다 | D |

| D10 | 마지막 원혼과 실패 패턴 경합 | 창 안의 제거는 성공으로 백귀야행이 발동하지 않는다. 이미 시작한 백귀야행은 뒤늦은 제거로 취소하지 않는다 | E |
| D11 | 구조와 시간 만료 동시 처리 | 구조 우선. 손실 비율은 구조 10%만 적용하고 자동 20%는 적용하지 않는다. 같은 사망 세대에 비용은 1회 | C/E |

| D13 | 통계 인정 범위 | 실제 적용량 기준(오버킬 제외). 꼬리·원혼 피해는 기여도에 포함하고, 삼켜짐 구조는 별도 지표로 센다. 자기 치유는 회복량에 넣지 않는다 | B/F |
| D14 | 보스 선택/파생 데이터 | 1차 SO 이관은 선택 가중치를 전부 1.0으로 두어 현재 동작과 동일하게 한다. 가중치·파생 확률 조정은 2차에서 한다 | D |
| D15 | 반복 예고와 캐시 상한 | 동시 예고 8, 동시 드랍 16, 양도 제안은 참가자당 1건 | A/D |
| D16 | 무녀의 "패턴 종료" 정의 | 마지막 impact 시각. `ActiveDuration` 종료가 아니다. 후딜 중 늦게 건 표식은 통과되지 않는다 | D |

모든 밸런스 값은 기존 도메인 SO를 우선 확장한다. 새로운 SO 도메인이 정말 필요할 때만 [기술 설계 3.1](03-technical-design.md)의 목록과 GameDB·에셋·부트 검증을 함께 추가한다. 위 제안 클래스 이름을 맞추려고 빈 클래스를 먼저 만들지 않는다.

순수 규칙은 EditMode, 실제 실행은 담당 개발 씬 L2로 확인한다. 네트워크 항목은 예외 없이 3PC L3에서 호스트/원격 모두 확인한다. 지연 조건과 반복 횟수는 멀티플레이 절차에 맞추고 타이밍 경합은 최소 10회 반복한다. 자동 테스트 통과를 L3 통과로 바꾸어 적지 않는다.

런타임 코드에는 Allman/4칸/필드 명명·정렬/가드 절, GameDB 초기화 이후 캐싱, NonAlloc, 이벤트 구독 해제, 코루틴 취소를 적용한다. 새 스크립트·폴더에는 유효한 `.meta`를 포함하며 씬/프리팹 변경은 배선 작업으로 분리해 기록한다.

**서버 기능 완료**는 A~F 산출물, V01~V15의 적용 가능한 검사, 3인 두 런 완주, 재접속, 결과 일치까지 충족한 상태다. 미정값·미배선·미검증은 각각 별도로 남긴다. “메서드가 생겼다” 또는 “컴파일됐다”만으로 게임 기능 완료라고 보고하지 않는다.

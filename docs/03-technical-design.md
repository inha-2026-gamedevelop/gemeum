## 1. 기술 스택

| 항목 | 선택 | 비고 |
|---|---|---|
| 엔진 | Unity 6.4.7f1 | |
| 렌더 파이프라인 | URP | Unity 6 기본. **프로젝트 중간 변경 금지** |
| 네트워크 | **Mirror** · 호스트 권위 (리슨 서버) | 추후 데디케이티드 전환 가능성 열어둠 |
| 트랜스포트 | KCP Transport | Steam 출시 시 FizzySteamworks 검토 |
| 지형 | Gaia for Unity 6 | 에디터 타임 생성, 런타임 생성 아님 |
| 형상 관리 | Git + **Git LFS** | 대용량 에셋 필수 |

### 1.1 렌더 파이프라인 고정 사유

Gaia, 건축 에셋, VFX 에셋이 전부 파이프라인에 종속된다. 중반에 변경하면 머티리얼이 전부 깨진다. 킥오프 시점에 URP로 확정하고 이후 논의하지 않는다.

### 1.2 네트워크 전환 여지

현재는 호스트 권위 리슨 서버로 설계한다. 다만 **권위 판정 로직을 호스트 전용 코드에 직접 박지 말고 별도 레이어로 분리**해둘 것. 추후 데디케이티드 서버로 옮길 때 그 레이어만 이전하면 되도록 한다.

## 3. 데이터 주도 설계 원칙

**모든 밸런스 수치는 코드 상수로 박지 않는다.** ScriptableObject 또는 CSV로 분리하여 인스펙터에서 조정 가능하게 만든다.

10월 집중개발 중 밸런싱 조정이 반복될 것이고, 그때마다 코드를 고치고 빌드하면 팀 전체가 병목에 걸린다.

### 3.1 ScriptableObject 대상

| 데이터 | 내용 |
|---|---|
| `CombatConfigSO` | 스태미나, 신력, 이동 속도, 구르기, 패링 수치 (**HP는 제외**) |
| `ArrowConfigSO` | 화살 발사각 보정, 유도 각도 · 지속 시간 |
| `WeaponAbilityConfigSO` | 직업별 공격 능력의 구조값 — 사거리 · 범위 · 각도 · 쿨다운 · 자원 비용 · 치유/버프 환산 비율. **공격력 자체는 갖지 않는다** — 피해량은 `EquipmentSO`가 롤한 무기 공격력을 그대로 쓴다 |
| `EquipmentSO` | 등급별 스탯 롤 범위, 특수옵션 풀 |
| `DropTableSO` | 필드 레벨별 등급 가중치 |
| `EnemySO` | 잡귀 3종 스탯, 강화 배수 |
| `BarrierPhaseSO` | 결계 단계별 시간, 반경, 피해량 |
| `SpawnConfigSO` | 구간별 동시 존재 수, 구성 비율, 리스폰 주기 |
| `BossPatternSO` | 보스 페이즈별 패턴, 쿨다운, 예고·판정 정보 |
| `TalentTreeSO` | 특성 노드 구성과 수치 |
| `ShopSO` | 객주 상품 목록과 가격 |
| `LevelCurveSO` | 레벨별 필요 경험치, **1레벨 기본 HP와 레벨별 최대 HP 전체** |
| `ScoreRuleSO` | 점수 항목별 배점 |
| `DayCycleSO` | 실시간과 게임 내 시각 매핑, 시간대별 조명 프리셋 |

**최대 HP는 `LevelCurveSO`가 단독으로 소유한다.** 1레벨 기본값 100을 `CombatConfigSO`에도 두면 두 에셋이 서로 다른 최대 HP를 주장할 수 있다. `CombatConfigSO`는 레벨과 무관한 값(스태미나 · 신력 · 이동 · 구르기 · 패링)만 가진다.

## 3.2 서버 · 클라이언트 책임 경계

판단 기준은 하나다. **이 값이 사람마다 다르면 게임 결과가 달라지는가.**
달라지면 서버, 달라지지 않으면 클라이언트가 각자 처리한다.

### 서버(호스트)가 처리 — 게임 상태

| 항목 |
|---|
| 플레이어 위치, HP, 스태미나, 신력 |
| 공격 판정, 피격 판정, 패링 성공 여부 |
| 화살 궤적과 명중 판정 |
| 잡귀 AI 상태와 HP |
| 드랍 결정, 노잣돈 잔액, 아이템 소유권 |
| 결계 반경과 단계, 범위 밖 피해 |
| 경과 시간 (초 단위 값 하나) |
| 사망 · 부활, 전멸 판정 |
| 경험치, 레벨, 특성 포인트 |

### 클라이언트가 각자 처리 — 표현

| 항목 |
|---|
| 조명, 스카이박스, 안개, 포스트프로세싱 |
| 파티클, 히트 이펙트 재생 |
| 카메라, 애니메이션 블렌딩 |
| 사운드 |
| UI 렌더링 |
| LOD, 오클루전 컬링 |

### 파생 계산 원칙

서버는 **원본 값 하나만** 보내고, 클라이언트가 그 값으로 표현을 계산한다.

| 서버가 보내는 것 | 클라이언트가 만드는 것 |
|---|---|
| 경과 시간 900초 | 해당 시각의 조명, 스카이박스, 안개 색 |
| 결계 반경 120m | 원통 셰이더, 미니맵 원, 경계 파티클 |
| 플레이어 HP 42 | 체력바 애니메이션, 저체력 화면 효과 |

시간대 조명 프리셋 자체는 네트워크를 전혀 타지 않는다. `DayCycleSO`는 로컬 리소스다.

### 예외 — 보이지만 판정에 걸리는 것

아래는 이펙트처럼 보이지만 클라이언트마다 위치가 다르면 안 된다.

- 보스 공격 예고 표식 (장판, 범위 표시)
- 결계 경계선
- 액귀 투사체

**서버가 이벤트만 보내고(어떤 패턴을 · 언제 · 어디서) 클라이언트가 그것을 렌더링**한다. 클라이언트가 스스로 위치를 계산하게 두면 안 된다.

### 요청 검증 규칙

`[Command]`는 입력을 전달할 뿐 권한을 부여하지 않는다. 서버는 모든 요청에서 호출자, 런 상태, 현재 무기·생명 상태, 입력 순서, 재사용 대기시간을 확인한다. 공격·상호작용·아이템 양도처럼 다른 네트워크 오브젝트를 대상으로 하는 요청은 대상과의 거리·시야·소유권까지 검증한 뒤 적용한다. `requiresAuthority = false`가 필요한 요청은 이 검증을 생략할 수 없다.

## 3.3 타격감 연출의 책임 분담

엘든 링 계열의 타격감은 여러 파트에 걸쳐 있다. 한 사람이 전부 가져가면 병목이 된다.

| 구분 | 담당 | 내용 |
|---|---|---|
| 타이밍 | 네트워크 · 전투 | 히트스톱, 셰이크 트리거, 패링 슬로우모션 진입 시점, 치명의 일격 트리거 |
| 표현 | 테크니컬 아트 | 히트 이펙트, 검흔 트레일, 셰이크 커브와 강도, 화면 효과, 사운드 |

### 인터페이스 분리

전투 파트는 아래와 같은 호출부만 만들고, 내부 구현은 테크니컬 아트가 채운다.

```csharp
public interface ICombatFeedback
{
    void PlayHit(HitStrength strength, float duration);
    void PlayParrySuccess();
    void PlayCritical(float multiplier);
}
```

이렇게 하면 전투 파트는 타이밍만 책임지고, 연출 튜닝은 넘길 수 있다.

### 직업별 카메라 연출 배분

3직업 각각에 고유 카메라 연출을 넣으면 작업량이 3배가 되지만 체감 이득은 그만큼 나오지 않는다.
**패링이 시그니처 메커닉이므로 차사에 몰아준다.** 셋 다 화려하면 아무것도 특별하지 않다.

| 직업 | 카메라 연출 |
|---|---|
| 차사 | 패링 성공, 치명의 일격에 전용 연출 (집중 투자) |
| 신궁 | 관통 명중 시 짧은 줌. 락온 중에는 카메라 고정 |
| 무녀 | 없음. 이펙트와 사운드로만 |

신궁은 원거리라 카메라가 크게 움직이면 조준을 방해하고, 무녀는 힐과 버프가 주력이라 타격 연출을 넣을 자리가 적다.

### 착수 시점

**프로토타입(08.30–09.19)에는 연출을 넣지 않는다.**
카메라 연출은 판정이 확정된 뒤에 얹는 층이다. 판정 수치가 계속 바뀌는 프로토타입 단계에서 만들면 전부 다시 만들게 된다.
집중개발 4~5주차(10.17–10.24)에 착수한다.

## 4. 파트별 기술 스펙

### 4.1 네트워크 · 전투 (팀장)

**핵심 기술: 네트워크 환경에서의 패링 판정 동기화**

#### 담당 범위

- Mirror `NetworkManager` 기반 세션 관리 (최대 3명, 3명 준비 완료 후 시작, 호스트 생성, 연결 해제 처리)
- 플레이어 이동 · 구르기 · 공격 입력 처리와 동기화
- 패링 판정과 패링 게이지 동기화
- 사망 · 부활 처리

> 현재 구현 기준(`57cb59d`): `ServerBootGate`, `GeumeumNetworkManager`,
> `LobbyController`, `RunManager`, `RunPhaseTimeline`, `RunTimelineBuilder`가 존재한다.
> 부트 게이트와 런 시계는 L2까지 확인됐고, 3인 준비·무기 배분·이탈 경로는 M2 검증 대기다.
> 플레이어는 이동과 패링의 초기 Command만 있으며 상태·공격·부활은 아직 계획 단계다.

#### 권위 모델

| 대상 | 판정 주체 | Mirror |
|---|---|---|
| 이동 | 클라이언트 예측 + 호스트 검증 | 입력 `[Command]` → `[Server]` 검증 → 스냅샷·마지막 입력 순서 회신. `NetworkTransform`은 **원격 플레이어 보간 전용** |
| 공격 판정 | 호스트 | `[Command]` → `[Server]` |
| 패링 성공 여부 | 호스트 | `[Command]` (입력 순서 + 추정 서버 시각) → `[Server]` 보정 후 판정 |
| 피해 계산 | 호스트 | `[Server]` + `[SyncVar]` |
| 드랍 결정 | 호스트 | `[Server]` + `NetworkServer.Spawn` |

`NetworkTransform`에 예측·재조정을 맡기지 않는다. 근거는 아래 "패링 동기화의 기술적 과제" 마지막 항을 따른다.

공격 입력의 클라이언트 Command 진입점은 `PlayerAttack` 하나로 고정한다.
활도 `PlayerAttack`이 현재 무기의 `BowAbility`를 선택하고, 서버 전용 `ArrowLauncher`가
화살을 스폰한다. `ArrowLauncher`에 별도의 클라이언트 Command를 두지 않는다.

전체 API 매핑은 [네트워크 권위 5.5절](unity/NETWORK_AUTHORITY.md).

#### 패링 동기화의 기술적 과제

패링 판정 창이 0.32초인데, 네트워크 지연이 50~150ms 발생하면 판정 결과가 클라이언트 체감과 어긋난다.

**설계 방향**:
1. 클라이언트가 패링 입력 순서와 추정 서버 시각을 함께 전송
2. 호스트가 연결별 시간 오차를 보정하되, 미래 시각과 허용 범위를 벗어난 값은 잘라낸 뒤 판정
3. 클라이언트는 즉시 패링 모션을 재생하되, 결과 연출은 호스트 응답 후 확정
4. 판정 불일치 시 롤백 대신 호스트 결과를 우선하고 시각 효과로 무마

입력 시각은 클라이언트가 임의로 판정을 확정하는 값이 아니다. 서버가 수신 시각·입력 순서·현재 생명 상태를 함께 검증한다. 이 부분이 포트폴리오의 핵심 어필 지점이므로 설계 근거와 대안 비교를 문서로 남긴다.

이동도 같은 원칙을 따른다. 클라이언트는 입력을 예측 적용하고 순서가 있는 입력 버퍼를 보관한다. 서버는 동일한 이동 모델로 검증한 스냅샷과 마지막 입력 순서를 돌려보내며, 클라이언트는 그 순서 이후 입력만 재적용해 보정한다. `NetworkTransform`은 원격 플레이어 보간과 서버 상태 전달을 담당하고, 예측·재조정 자체를 대신하지 않는다.

#### 화살 보정 (신궁)

투사체는 호스트 권위로 처리한다. 클라이언트는 발사 모션만 즉시 재생하고, 실제 판정은 호스트가 담당한다.

| 상태 | 처리 |
|---|---|
| 락온 | 발사각 12도 이내 보정, 비행 중 초당 30도 유도, 0.4초간 |
| 비락온 | 보정 없음, 반경 0.4m 구형 판정 |
| 관통 특성 | 유도 없음, 직선 비행 |

유도 대상이 죽거나 유도 시간이 끝나면 직진으로 전환한다. 유도 상태 변화는 호스트가 판단하고 결과만 동기화하여, 클라이언트마다 궤적이 갈라지지 않게 한다.

#### 부활 처리

```
사망 감지 (호스트)
  → 관전 상태 전환, 30초 타이머
  → 팀 공용 노잣돈 20% 차감 후 전원에게 브로드캐스트
  → 사망 좌표 그대로 부활 (결계 안팎 보정 없음)
  → HP 50%, 스태미나 100%, 무적 2초 부여
  → 3인 전원의 HP가 0인 상태면 런 종료 처리
```

전멸 판정은 "동시 사망"이 아니라 **서버 틱에서 3인의 생명 상태를 확인하여 전원 사망 상태인지** 판정한다.
`ReviveController`가 전멸 조건을 감지하고 `RunManager.AbortRun`을 요청하며,
`RunManager`만 `RunPhase.Result`를 커밋한다. 타이밍 차이로 인한 판정 누락을 막고,
사망 이벤트가 중복으로 노잣돈을 차감하지 않도록 플레이어별 부활 상태를 함께 기록한다.

### 4.2 몬스터 · 보스

**핵심 기술: 보스 패턴 상태 머신**

#### 담당 범위

- 잡귀 3종 AI
- 스폰 매니저 (구간별 밀집도, 거점 배치, 리스폰)
- 보스 페이즈와 패턴

결계 시스템은 게임플레이 시스템 파트가 소유한다(4.3). 스폰과 잡귀 강화는 결계 단계를 **읽기만** 한다 — `RunPhase` 이벤트를 구독하고 반경은 `BarrierController`의 SyncVar를 참조한다.

#### 잡귀 AI 요구사항

| 잡귀 | AI 요구 |
|---|---|
| 허깨비 | 근접 추적, 무리 행동. 선딜을 길게 하여 초보자 대응 여유 확보 |
| 창귀 | 돌진 후 경직. **패링 타이밍이 명확하게 읽히도록** 선딜 모션 강조 |
| 액귀 | 사거리 유지, 투사체 시전. 근접 시 후퇴 |

#### 스폰 매니저 설계

- 거점(Spawn Cluster) 단위 배치. 클러스터당 3~5마리
- 클러스터 위치는 고정 맵에 미리 배치하고, 구성만 랜덤화
- 결계 축소 시 범위 밖 클러스터 비활성화
- 리스폰 타이머는 구간별로 다름 (개활 150초, 1차 120초, 2차 없음)
- 3차 축소가 시작되면 일반 잡귀의 신규 스폰과 리스폰을 중단하고, 보스맵에는 일반 잡귀를 배치하지 않는다
- 잡귀 AI의 경로 재계산은 프레임당 처리 수를 정해 분산한다. 개활 구간의 동시 22마리를 호스트 한 대가 전부 돌기 때문이다 ([Unity 엔지니어링 패턴](unity/UNITY_ENGINEERING_PATTERNS.md))

#### 보스 상태 머신

`BossPhaseBase`를 상속한 페이즈별 클래스로 분리하고, `BossController`는 현재 페이즈에 위임만 한다.
enum + switch 방식은 패턴 추가 시 수정 범위가 넓어진다.

**제약**: 페이즈마다 패링 가능 패턴 최소 1개.
패턴의 수치·쿨다운·예고 시간은 `BossPatternSO`가 소유하고, 페이즈 클래스는 서버에서 패턴 선택과 상태 전환만 담당한다.

### 4.3 게임플레이 시스템

**핵심 기술: 가중치 기반 절차적 아이템 생성**

#### 담당 범위

- 장비 드랍과 스탯 랜덤 롤
- 인벤토리 (슬롯형 3~4칸)
- 특성 트리 데이터와 UI
- 노잣돈 경제와 객주 상점
- 전투 스탯 파이프라인
- 점수 정산과 리더보드
- 결계 시스템 (단계별 축소, 범위 밖 피해)

#### 결계 시스템

```
BarrierController (호스트 권위)
  ├ 고정된 BarrierCenter, 현재 단계, 목표 반경, 축소 진행률
  ├ 30초에 걸친 반경 보간
  ├ 축소 10초 전 경고 이벤트 브로드캐스트
  └ 매 초 범위 밖 플레이어에게 피해 적용
```

반경 정보는 모든 클라이언트에 동기화되어야 UI(미니맵 원)가 정확히 그려진다.
범위 판정과 피해량 계산은 `BarrierJudge` 같은 순수 C# 레이어에서 수행하고, `BarrierController`는 서버 틱에 결과를 `IDamageable`에 적용한다. `Boss` 단계에서는 결계 피해와 회복 봉쇄를 종료한다.

#### 장비 생성 2단계 구조

```
1단계 — 등급 결정
  필드 레벨 참조 → DropTableSO 가중치 룰렛 → 등급 확정

2단계 — 스탯 롤
  등급에 해당하는 EquipmentSO의 롤 범위 내에서 무작위 값 생성
  등급별 확률에 따라 특수옵션 부여
```

#### 데이터 구조 분리

**설계도와 인스턴스를 분리한다.**

| 구분 | 역할 |
|---|---|
| `EquipmentSO` (ScriptableObject) | 원본 설계도. 등급, 이름, 롤 범위, **무기 종류별 특수옵션 풀** |
| `EquipmentInstance` (런타임 클래스) | 개별 드랍 결과. 실제 굴려진 수치 보유 |

이렇게 해야 같은 무기라도 드랍마다 스탯이 달라지는 구조가 깔끔하게 나온다.

`EquipmentInstance`에는 ScriptableObject나 Unity 오브젝트 참조를 넣지 않는다. Mirror에 전달할 때는 `EquipmentInstanceSerializer`가 장비 ID, 무기 종류, 등급, 공격력 롤, 옵션 ID·값만 명시적으로 직렬화하고, 클라이언트는 동일한 `GameDB`에서 표시 정보를 조회한다.

#### 스탯 재조정권 · 등급 상승권

- 재조정권: 같은 `EquipmentSO`로 `EquipmentInstance`를 재생성
- 등급 상승권: 상위 등급 `EquipmentSO`로 교체 후 재생성

두 기능 모두 위 구조를 그대로 재사용하므로 추가 구현 비용이 거의 없다.

#### 노잣돈 동기화

팀 공용 재화이므로 **호스트가 단일 값을 관리**하고 브로드캐스트한다.
동시 구매 요청은 서버 메인 스레드의 도착 순서대로 `TrySpend` 한 번씩 원자적으로 처리하여 잔액 음수를 방지한다. 클라이언트가 계산한 가격이나 잔액은 신뢰하지 않는다.

#### 아이템 양도

파티원에게 아이템을 넘기는 기능이 있으므로, 소유권 이전도 호스트 권위로 처리한다.
서버는 양도 요청에서 발신자 소유권, 대상 플레이어의 연결 상태, 두 플레이어의 거리, 대상 슬롯 여유, 현재 전투·관전 상태를 모두 확인한다.

### 4.4 테크니컬 아트 (팀장 겸임)

**핵심 기술: URP 기반 렌더링 및 아트 파이프라인**

3인 팀이라 아트 전담자를 두지 않고 팀장이 겸임한다. 네트워크 · 전투가 먼저이므로, 아트 작업은 프로토타입 구간에서 톤 기준만 잡고 집중 개발 구간에 몰아서 한다.

#### 담당 범위

- 셰이더 작성과 머티리얼 관리
- VFX (전투 이펙트, 결계 연출, 부활 연출)
- **맵 구성** (Gaia 지형 + 건축물 배치 + 잡귀 거점 위치 설계)
- 시간대 조명 (아침 8시부터 자정까지의 조명 · 스카이박스 전환)
- 사운드

#### 맵 배치의 필수 제약

레이아웃을 자유롭게 잡되, 아래 두 가지는 게임 진행이 성립하기 위한 조건이므로 반드시 지킨다 ([시스템 기획 2.1](01-system-design.md)).

| 제약 | 이유 |
|---|---|
| **보스맵 입구는 3차 결계 최종 반경 안에 둔다** | 3차 구간 30초 동안 결계 밖 피해는 초당 5에 회복 봉쇄까지 걸린다. 누적 150 피해는 10레벨 최대 HP 180의 대부분이므로, 결계 밖을 지나야 보스맵에 닿는 배치는 보스전 진입 자체를 전멸 구간으로 만든다 |
| **객주는 2차 결계 최종 반경 안에 둔다** | 이용 가능 구간이 실시간 12:00–15:00뿐이다. 결계 밖에 있으면 초당 2.5 피해와 쇠약을 맞으며 쇼핑하게 된다 |

결계 중심은 씬의 `BarrierCenter` 마커로 고정하고, 위 거리 조건은 3인 통합 테스트에서 실측해 확인한다.

#### 최대 리스크: 아트 톤 통일

Gaia 기본 지형(사실적 자연) + 여러 출처의 건축 에셋 + 저승 컨셉을 섞으면 톤이 따로 논다.

**대응 방향**:
- 포스트프로세싱과 안개로 덮는다. 저승 컨셉이므로 오히려 유리하다
- 짙은 분홍·자주 계열 안개, 낮은 채도, 어두운 조명으로 재질 차이를 가린다
- 조명을 통일된 컬러 그레이딩으로 강제한다

이 작업 자체가 "이질적 구매 에셋의 아트 톤 통일 파이프라인 구축"으로 포트폴리오 항목이 된다.

#### 결계 연출 요구사항

- 반경이 시각적으로 명확할 것 (원통형 셰이더 또는 파티클 벽)
- 축소 진행 중임이 보일 것
- 밖에 있을 때 화면 효과로 위험을 즉각 인지시킬 것

#### 성능 제약

리슨 서버 구조에서는 **호스트 PC가 게임 로직과 렌더링을 동시에 부담**한다.
- LOD와 오클루전 컬링 필수
- 파티클 밀도 상한 설정
- 맵 크기 500~800m 제한 준수

## 5. UI 담당 원칙

**UI 전담자를 둔다.** 게임플레이 시스템 담당(@kjw1237)이 겸임한다. 화면이 어느 파트 소재인지와 무관하게 모든 UI(HUD, 보스 HP 바, 인벤토리 · 특성 트리 · 상점, 결계 경고 · 미니맵 원, 사망 관전 화면, 연출성 UI · 트랜지션 포함)를 전담자가 구현·수정한다. 폴더 구성은 [프로젝트 구조 설계서 4.6](04-architecture.md#46-06ui--게임플레이-시스템kjw1237이-전담)을 따른다.

> 기존에는 각자 자기 시스템의 UI를 담당해 전담자로 인한 병목을 피했으나, 2026-08-30부로 담당 체계를 UI 전담으로 바꿨다.

### 5.1 UI 작업 방식 — 씬 우선, 코드는 최소한

**씬 · 프리팹에서 만들 수 있는 것은 전부 씬 · 프리팹에서 만든다.** 레이아웃, 앵커, 색상, 폰트, 계층 구조, 버튼 · 슬라이더 등 컴포넌트 배치는 Unity 에디터 작업이다. 코드로는 **에디터에서 할 수 없는 것만** 작성한다.

| 작업 | 방식 |
|---|---|
| 레이아웃 · 앵커 · 정렬 | 씬/프리팹 (RectTransform, Layout Group) |
| 색상 · 폰트 · 스타일 | 씬/프리팹 (컴포넌트 인스펙터) |
| 패널 계층 구조, 버튼 · 슬라이더 배치 | 씬/프리팹 |
| 게임 상태 → 텍스트 · 값 · 활성화 갱신 (바인딩) | 코드 |
| 이벤트 구독 (버튼 클릭 → Command 호출 등) | 코드 |
| 데이터 기반 반복 생성 (인벤토리 슬롯 등 개수가 가변인 목록) | 코드 |

코드에서 `new GameObject`로 UI 계층을 조립하거나, 인스펙터로 될 색상 · 크기 값을 코드 상수로 박아 넣지 않는다. Unity 런타임 패턴은 [Unity 엔지니어링 패턴 9장](unity/UNITY_ENGINEERING_PATTERNS.md).

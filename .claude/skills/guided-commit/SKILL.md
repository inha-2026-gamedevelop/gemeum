# 가이드 커밋

## 언제 발동하나

사용자가 지금 있는 변경 사항을 커밋하고 싶다는 의사를 밝히면 발동한다. 예: "커밋할게", "커밋해줘", "이거 커밋하자", "커밋 진행해줘".
**바로 `git commit`을 실행하지 않는다** — 아래 절차를 먼저 거친다.

이미 이 절차를 거쳐 사용자가 메시지까지 확정한 뒤 "그대로 커밋해"라고 재요청하는 경우는 재점검 없이 바로 실행한다.

## 절차

### 1. 변경 사항 파악

- `git status`, `git diff`(staged + unstaged 전부)로 무엇이 바뀌었는지 읽는다.
- 서로 관련 없는 변경이 섞여 있는지 확인한다 (예: 문서 수정 + 특정 시스템 코드 + 무관한 설정 변경).

### 2. 커밋 컨벤션 확인

- `CONTRIBUTING.md`의 커밋 메시지 규칙을 기준으로 삼는다 — 타입(`feat`/`fix`/`refactor`/`docs`/`chore`) + 무엇을 했는지 + (필요한 경우만) 왜.
- 그 문서가 없어졌거나 내용이 바뀌었으면 다시 읽고 그 기준을 따른다. 임의로 새 컨벤션을 만들지 않는다.

### 3. 코딩 컨벤션 위반 점검 (C#/Unity 변경분만)

- 변경된 `.cs` 파일이 있으면 `docs/coding-convention.md` 기준으로 diff를 검토한다: 네이밍(`_camelCase` / `UPPER_SNAKE_CASE` / `PascalCase`), 중괄호(Allman, 단일 문장도 필수), 매직넘버 금지, 필드 정렬, using 그룹 순서, null 체크 관용구, SerializeField vs public 등.
- 위반이 있으면 **커밋 메시지에 지적만 하고 넘어가지 않는다 — 먼저 코드를 고친다.** 고친 뒤 무엇을 왜 고쳤는지 사용자에게 짧게 알린다.
- 코드가 아닌 변경(문서, 에셋, 씬, 설정)은 이 점검 대상이 아니다.
- 컨벤션 위반인지 스타일 취향 차이인지 애매하면 임의로 판단하지 않고 사용자에게 확인한다.

### 4. 커밋 단위로 묶기

- "한 커밋에 한 가지 일만 담는다"(`CONTRIBUTING.md`) 원칙에 따라 관심사별로 변경을 나눈다.
- 나뉜다면 몇 개의 커밋이 될지, 각 커밋에 어떤 파일이 들어가는지 목록으로 사용자에게 보여준다.
- 자연스럽게 하나의 작업이면 억지로 쪼개지 않는다 — 나누는 것 자체가 목적이 아니라 이력을 읽기 좋게 만드는 것이 목적이다.

### 5. 커밋 메시지·설명 작성

- 각 커밋 단위마다 `<타입>: <무엇>` 제목과, 필요하면 왜 했는지 본문을 작성한다.
- **`Co-Authored-By` 트레일러를 넣지 않는다.** 도구 기본 설정이 붙이게 되어 있어도 제외한다. 이미 붙은 채로 커밋했고 푸시 전이면 `git commit --amend`로 지운다.
- 실제로 `git commit`을 실행하기 전에 사용자에게 메시지 전체(제목 + 본문, 여러 개면 각각 구분해서)를 보여주고 **확인을 받는다.**

### 6. 기준 문서를 코드와 동기화한다

커밋하는 변경이 **기능의 구현 상태를 바꿨으면 그 기능을 서술한 문서도 같은 커밋에서 고친다.**
코드만 고치고 문서를 두면 다음 사람이 문서를 믿고 이미 있는 것을 다시 만들거나, 없는 것을 있다고 여긴다.

대상 문서와 판단 기준.

| 무엇이 바뀌었나 | 어느 문서를 |
|---|---|
| 클래스 · 파일이 새로 생기거나 사라졌다, 상속이 바뀌었다 | `docs/04-architecture.md`의 파일 트리와 표 |
| 기능이 계획에서 구현으로 넘어갔다 | `docs/04-architecture.md`의 `[계획]`을 `[현재]`로 |
| 파트 간 인터페이스 · 데이터 흐름 · 기술 선택이 바뀌었다 | `docs/03-technical-design.md` |
| 밸런스 수치 · 콘텐츠 규칙이 바뀌었다 | `docs/02-game-design.md` |
| 스코프 · 일정 · 시스템 구성이 바뀌었다 | `docs/01-system-design.md` |

지켜야 할 것.

- **`[현재]`와 `[계획]` 표기를 실제 코드 기준으로 맞춘다.** 예를 들어 패링이 구현되면 그 항목을
  `[계획]`에서 `[현재]`로 바꾸고, 아직 연결되지 않은 하위 항목은 `[계획]`으로 남긴다.
  전부 되지 않았는데 통째로 `[현재]`로 올리지 않는다.
- **진행 중이면 진행 중이라고 적는다.** 완료 표시는 실제로 동작을 관찰한 것에만 한다.
  검증하지 않았으면 문서에도 미검증임을 남긴다.
- 문서와 코드가 다르면 **코드가 기준이다.** 문서를 코드에 맞추고, 차이를 사용자에게 보고한다.
- 기획 선택이 걸린 불일치(어느 쪽이 맞는지 팀이 정해야 하는 것)는 임의로 고치지 않는다.
  무엇이 충돌하는지만 사용자에게 알리고 그대로 둔다.
- 문서 수정은 코드와 같은 커밋에 넣는다. 따로 떼면 어느 커밋 기준의 문서인지 알 수 없게 된다.
  단, 문서만 대량으로 손보는 작업이면 `docs:` 커밋으로 분리한다.
- `.claude/` 아래 문서는 여기서 말하는 기준 문서가 아니다. `.gitignore` 대상이라 팀에 공유되지 않는다.

### 7. 다른 담당자에게 넘길 것이 있으면 전달 문서를 만든다

커밋한 변경 때문에 **다른 파트가 해야 할 일이 생겼거나**, 작업 중에 다른 사람 소유 영역의 문제를
발견해 직접 고치지 못하고 남긴 것이 있으면, 그 담당자에게 건넬 문서를 따로 쓴다.

- 팀원이 함께 확인할 전달 문서는 `docs/`에 둔다. 개인 전달 초안만 `.claude/docs/`에 두며 날짜는 작성일을 적는다.
- 문서 이름은 누구에게 무엇을 넘기는지 알 수 있게 짓는다. 예: `몬스터파트-전달-런종료-잡귀정리.md`
- **이 문서는 그대로 복사해서 상대에게 건넨다. 따라서 자립적이어야 한다.**
  다른 문서 경로나 저장소 내부 문서를 참조하지 않는다. 감사서 항목 번호처럼 상대가 모르는 약칭도 풀어 쓴다.
  받는 사람이 이 파일 하나만 보고 착수할 수 있어야 한다.
- 담을 것: 왜 지금 보내는지, 증상, **재현 절차**, 원인(파일과 메서드까지), 제안, 예상 비용, 권하는 순서,
  되물을 창구. 상대 파트 코드를 대신 고치지 않고 판단은 상대에게 맡긴다.
- `.claude/handover/`는 `.gitignore` 대상이라 커밋되지 않는다. 저장소에 남겨야 하는 결정은 `docs/`에 쓴다.
- 세션 인수인계(`.claude/docs/{날짜}/`)와 혼동하지 않는다. 인수인계는 **다음 세션의 나**를 위한 것이고,
  전달 문서는 **다른 사람**에게 건네는 것이다. 둘 다 필요하면 둘 다 쓰고, 인수인계 쪽에서 전달 문서 경로를 가리킨다.

### 8. 확인 후 커밋

- 승인받은 내용 그대로 커밋한다. 사용자가 메시지 수정을 요청하면 반영 후 다시 확인받는다.
- push는 이 스킬의 범위가 아니다 — 별도로 명시적인 요청이 있을 때만 한다.

## 하지 않는 것

- 사용자 확인 없이 바로 `git commit` 실행
- 코딩 컨벤션 위반을 발견하고도 그냥 커밋
- 서로 관련 없는 변경을 하나의 커밋에 몰아넣기
- 커밋 메시지에 `Co-Authored-By` 트레일러 넣기
- 요청받지 않은 push
- 전달 문서에 저장소 내부 문서 경로를 참조로 남기기 - 복사해서 건네는 순간 끊긴다
- 다른 파트가 해야 할 일을 커밋 메시지에만 적고 전달 문서를 만들지 않기
- 구현 상태가 바뀌었는데 기준 문서를 그대로 두고 커밋하기
- 검증하지 않은 기능을 문서에 `[현재]`나 완료로 표시하기

## 공유 문서와 개인 기록의 경계

- 팀원에게 필요한 계약·사용법·담당자 인계는 `docs/`에 자립적으로 작성한다.
- 팀장 개인 실행 이력·계정/비용·모델 선호·다음 세션 기록은 `.claude/docs/`에 보관한다.
- `docs/` 문서가 `.claude/docs/` 또는 다른 개인 보관 경로의 문서를 참조해야만 이해되는 구조를 만들지 않는다. 필요한 공용 사실은 공유 문서 본문에 적고 코드·공유 문서를 근거로 삼는다.
- 기존 세션 기록의 개인 문서 간 링크와 포인터는 유지할 수 있다.

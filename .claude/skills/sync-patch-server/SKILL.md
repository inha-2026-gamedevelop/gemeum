# 배포 서버 동기화

## 언제 발동하나

- 새 Unity 빌드를 팀원에게 배포하려 한다. 예: "서버에 올려줘", "패치 올려", "이 빌드 배포해줘".
- 지금 서버에 무엇이 올라가 있는지 알고 싶다. 예: "빌드 버전 확인해줘", "서버랑 같은 버전이야?".
- 런처를 고쳤고 팀원 런처가 바뀌어야 한다. 예: "런처 업데이트 올려".

배경 설계는 `docs/unity/PATCH_SYSTEM_DESIGN.md`(11장 런처 자기 업데이트, 13장 운영)에 있다. 동작이 문서와 다르면 스크립트 코드를 기준으로 삼고 차이를 보고한다.

## 버전이 무엇인가

| 대상 | 로컬 원본 | 서버 쪽 |
|---|---|---|
| 게임 빌드 | `Builds/Development/gemeum_Data/StreamingAssets/build-identity.json`의 `releaseId` (Unity 빌드 메뉴가 빌드 시각으로 찍는다, 예: `win64-20260919-2027`) | `Builds/PatchRepo/channels/internal/envelope.json`이 가리키는 releaseId |
| 런처 | `launcher/Launcher.UI/Launcher.UI.csproj`의 `<Version>` | `Builds/PatchRepo/launcher/latest.json`의 version |
| 게임 테스트 버전 (사람이 보는 번호) | 게시할 때 매긴다. 마지막 번호는 `Builds/test-version.json` | manifest의 displayVersion, 런처 화면·게임 로그에 표시 |

**테스트 버전 규칙.** 0.0.1부터 시작해 새 빌드를 게시할 때마다 끝자리를 하나 올린다(0.0.1 → 0.0.2 …). 게시 스크립트가 번호를 정해 빌드 폴더의 `build-identity.json`에 적은 뒤 패키징하므로 게임·manifest·런처가 같은 번호를 본다. Unity의 `bundleVersion`(ProjectSettings)은 쓰지 않는다 — 빌드마다 공용 설정 파일이 바뀌어 팀원과 충돌한다. 사용자가 "0.1.0으로 올려"처럼 큰 단위를 요청하면 `-Version 0.1.0`을 준다. 번호는 올라가기만 하고, 이미 쓴 번호나 더 낮은 번호는 스크립트가 거부한다. 멀티플레이 호환은 여전히 releaseId로 판단한다 — 테스트 버전은 사람이 부르는 이름이다.

배포 서버는 `Builds/PatchRepo` 폴더를 그대로 내보낸다(`serve-repo.ps1`). 따라서 **로컬 저장소에 게시 = 서버에 반영**이고, 서버가 켜져 있어야 팀원이 받는다.

같은 releaseId끼리만 멀티플레이 접속이 된다. 게시하면 팀원 전원이 업데이트를 받아야 같이 놀 수 있다.

## 절차

### 1. 먼저 비교만 한다

```powershell
D:\gemeum\launcher\scripts\sync-server.ps1 -Check
```

PowerShell 도구로 실행한다. 출력의 `[게임 빌드]`·`[런처]`·`[서버]` 블록과 마지막 `판단:` 두 줄을 읽는다. 사용자가 "확인만" 요청했으면 여기서 보고하고 끝낸다.

### 2. 판단별로 처리한다

| 판단 문구 | 할 일 |
|---|---|
| 게임 "같다 — 할 일 없음" | 게임은 건드리지 않는다 |
| 게임 "다르다 — 로컬 빌드를 게시한다" | 3단계로 게시한다 |
| 게임 "로컬 빌드가 서버보다 오래됐다" | **게시하지 않는다.** 되돌리기(롤백)가 의도인지 사용자에게 묻고, 맞다고 하면 `-Force`로 게시한다 |
| 게임 "로컬 빌드가 없다" | 게시하지 않는다. Unity 메뉴 `그믐/빌드/개발용 빌드`를 먼저 하라고 안내한다. 에디터가 열려 있으므로 에이전트가 빌드를 대신 돌리지 않는다 |
| 런처 "소스 버전이 높다" | 3단계로 게시한다 |
| 런처 "코드가 바뀌었는데 버전이 그대로다" | 버전 관리는 이 스킬의 책임이다. `-BumpLauncher`를 붙여 패치 자리(1.2.0 → 1.2.1)를 올려 게시한다. 큰 변경이라 minor를 올려야 하면 사용자에게 먼저 확인한다 |
| 런처 "소스 버전이 게시본보다 낮다" | 게시하지 않는다. csproj를 누가 되돌렸는지 확인하라고 보고한다 |
| 서버 "응답 없음" | 게시는 해도 된다(로컬 저장소에 기록된다). 다만 사용자에게 `launcher\scripts\serve-repo.ps1` 창을 켜 달라고 안내한다. **에이전트가 서버를 백그라운드로 띄우지 않는다** — 세션이 끝나면 같이 꺼져 팀원이 모르고 받지 못한다 |
| 서버 "로컬 저장소와 내용이 다르다" | 게시하지 않는다. 서버가 다른 폴더를 내보내거나 다른 PC 서버를 보고 있을 수 있다. 사용자에게 확인한다 |

`[게임 빌드]`에 "HEAD가 아닌 커밋으로 만들어졌다"가 나오거나 커밋 값이 `-dirty`면 게시는 진행하되 보고에 반드시 적는다. 팀원이 받는 빌드가 저장소의 최신 코드와 다를 수 있다.

### 3. 게시한다

사용자가 동기화를 요청했으면 추가 확인 없이 실행한다(되돌리기·minor 올림만 예외).

```powershell
D:\gemeum\launcher\scripts\sync-server.ps1                 # 필요한 것만 게시
D:\gemeum\launcher\scripts\sync-server.ps1 -BumpLauncher   # 런처 코드 변경분까지
D:\gemeum\launcher\scripts\sync-server.ps1 -Only game      # 게임만 (launcher만도 가능)
D:\gemeum\launcher\scripts\sync-server.ps1 -Version 0.1.0  # 테스트 버전을 큰 단위로 올릴 때
```

- 패치 노트: 사용자가 내용을 불러 주면 `Builds/Launcher-config/notes-<releaseId>.txt`에 UTF-8로 써서 `-Notes`로 넘긴다. 없으면 스크립트가 서버 빌드와 로컬 빌드 사이의 git 커밋 제목으로 자동 작성한다.
- 런처를 먼저, 게임을 나중에 게시한다(스크립트가 이 순서로 한다).
- 한 번에 5분 이상 걸릴 수 있다(3.5GB 빌드 해시). 타임아웃을 넉넉히 준다.

### 4. 결과를 확인한다

- 출력 끝의 `서버 동기화 완료: internal seq N → <releaseId>`를 확인한다.
- 다시 `-Check`를 돌려 두 판단이 모두 "같다"인지 본다.
- `Builds/publish-history.md`에 줄이 추가됐는지 본다.

## 하지 말 것

- `Builds/PatchRepo` 안의 파일을 직접 고치거나 지우지 않는다. 게시는 스크립트로만 한다.
- 채널 sequence를 손으로 정하거나 `geumeum-pack publish-channel`을 직접 부르지 않는다. 스크립트가 다음 번호와 최소 런처 버전을 이어받는다.
- 서명 개인키(`%USERPROFILE%\.geumeum\keys\`)를 옮기거나 내용을 출력하지 않는다.
- 배포 서버를 끄거나 재시작하지 않는다. 팀원이 받는 중일 수 있다.
- Unity 빌드를 대신 실행하지 않는다.
- 게시 후 커밋하지 않는다. 커밋은 사용자가 요청할 때만 한다.

## 자주 나는 오류

| 메시지 | 원인·조치 |
|---|---|
| `서명 개인키가 없다` | 이 PC에 키가 없다. 게시는 팀장 PC에서만 한다 |
| `패치 노트 파일이 없다` | `-Notes` 경로가 틀렸다. 빼면 자동 작성된다 |
| `geumeum-pack … 사용 중` / 파일 잠김 | 다른 게시가 돌고 있다. 끝난 뒤 다시 실행한다. `serve-repo.ps1`은 별도 폴더라 원인이 아니다 |
| `이미 더 높은 런처 … 게시돼 있다` / `같은 버전 … 다른 exe` | csproj 버전을 올려야 한다. `-BumpLauncher`로 다시 실행한다 |
| `로컬 빌드가 서버보다 오래됐다` | 최신 Unity 빌드를 했는지 확인한다. 롤백이 의도면 사용자 확인 후 `-Force` |

## 보고 형식

결론부터 한 줄로 쓴다. 테스트 버전을 앞세운다. 예: "테스트 빌드 0.0.3을 서버에 올렸다. 런처는 그대로 1.2.6."

그다음 짧게:

- 게임: 테스트 버전 이전 → 새 번호, releaseId (seq), 소스 커밋, `-dirty`·HEAD 불일치 여부.
- 런처: 이전 → 새 버전(올렸으면 왜 올렸는지).
- 패치 노트 내용 전체.
- 서버 상태: 켜져 있음 / 꺼져 있어 켜야 함.
- 팀원 영향: 런처를 켜면 런처는 자동으로, 게임은 **업데이트** 버튼으로 받는다. 받기 전까지는 새 빌드 사용자와 접속되지 않는다.
- 확인만 요청받았으면 표 형태로 로컬·서버 버전과 "같음/다름"만 보고한다.

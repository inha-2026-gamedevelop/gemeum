# 가이드 풀 리퀘스트

## 언제 발동하나

사용자가 지금 브랜치의 작업을 PR로 올리고 싶다는 의사를 밝히면 발동한다.
예: "PR 올려줘", "풀리퀘 보내자", "풀리퀘스트 만들어줘", "develop에 PR 보내줘".

**바로 `gh pr create`를 실행하지 않는다** — 아래 절차를 먼저 거친다.
이미 이 절차로 본문을 확정한 뒤 "그대로 올려"라고 재요청하는 경우는 재점검 없이 실행한다.

## 절차

### 1. 브랜치와 커밋 상태 확인

- `git branch --show-current`로 현재 브랜치를 확인한다. `feature/{이름}` 형식이어야 한다.
- **`main`이나 `develop` 위에 있으면 PR을 만들지 않는다.** 사용자에게 알리고 멈춘다.
- `git status`로 커밋되지 않은 변경이 남았는지 본다. 남아 있으면 이번 PR에 포함할지 사용자에게 묻는다 — 임의로 커밋하지 않는다(커밋은 `guided-commit`의 범위다).
- `git log origin/develop..HEAD --oneline`으로 이번 PR에 들어갈 커밋 목록을 확인한다. 비어 있으면 올릴 것이 없다고 알리고 멈춘다.
- 푸시되지 않은 커밋이 있으면 `git push -u origin {브랜치}`가 필요함을 알리고 **사용자 승인을 받은 뒤** 푸시한다.

### 2. 변경 내용 분석

- `git diff origin/develop...HEAD --stat`으로 변경 파일 전체를 본다.
- 커밋 메시지와 diff를 읽고 **무엇을 왜 했는지**를 스스로 요약할 수 있을 때까지 파악한다. 커밋 메시지를 그대로 나열하는 것은 요약이 아니다.
- 아래를 판정한다. 이후 체크리스트 작성의 근거가 된다.
  - 씬 파일(`.unity`)이 포함됐는가. `Main.unity`가 있는가.
  - `.meta` 없이 추가된 에셋이 있는가.
  - Mirror 관련 변경(`[Server]`, `[Command]`, `[SyncVar]`, `NetworkBehaviour` 등)이 있는가.
  - 대용량 바이너리(모델·텍스처·사운드)가 추가됐는가.
  - `.cs` 파일에 새 상수로 박힌 밸런스 수치가 있는가.

### 3. PR 크기 점검

`CONTRIBUTING.md` 7장 기준으로 확인하고, 넘으면 **막지는 말되 알린다.**

| 기준 | 권장 |
|---|---|
| 변경 파일 수 | 15개 이하 |
| 씬 파일 | PR당 1개 |

초과하면 "파일 N개 / 씬 M개 — 권장치 초과"라고 알리고, 나눠서 올릴 수 있는 경계가 보이면 제안한다.

### 4. 본문 작성 — 템플릿 그대로

**`.github/PULL_REQUEST_TEMPLATE.md`를 매번 읽고, 그 파일의 섹션 구조·순서·문구를 그대로 따른다.**
템플릿이 바뀌었으면 바뀐 쪽을 따른다. 기억으로 재구성하거나 섹션을 임의로 추가·삭제하지 않는다.

- 안내용 HTML 주석(`<!-- ... -->`)은 지운다. 내용을 채우는 것이 목적이다.
- **제목**: 브랜치가 `feature/{이름}`이라 제목이 유일한 단서다. 무슨 기능인지 반드시 제목에 적는다. 커밋 타입 접두어(`feat:` 등)를 붙여 커밋 컨벤션과 톤을 맞춘다.
- **무엇을 했나**: 한두 문장. 제목에 "왜"가 안 드러나면 여기에 적는다.
- **관련 이슈**: 아는 이슈 번호가 있으면 `Closes #N`. 모르면 사용자에게 묻는다. 번호를 지어내지 않는다.
- **담당 파트**: `.github/CODEOWNERS`에서 변경 파일 경로가 속한 파트를 찾아 체크한다.
- **테스트 방법**: 리뷰어가 그대로 따라 할 수 있는 순서로 쓴다. 확인 절차가 없으면 "해당 없음"이라고 쓴다.
- **스크린샷 / 영상**: 시각적 변경이 있으면 사용자에게 첨부를 요청한다. 없으면 섹션을 지운다.
- **남은 것 / 알려진 문제**: 이번에 하지 않은 것, 미검증 항목을 적는다. 비워두지 않는다 — 없으면 "없음".

### 5. 체크리스트는 근거가 있을 때만 체크

**확인하지 않은 항목을 체크하지 않는다.** 이 체크리스트는 리뷰어가 신뢰하는 유일한 신호다.

- 코드·파일로 확인 가능한 항목(씬 수정 여부, `.meta` 동반, 코드 상수 밸런스 수치, LFS 대상 확장자, `git lfs status`)은 **직접 확인하고** 체크한다.
- 실행해야만 아는 항목(콘솔 경고·에러, 3인 접속 테스트)은 **사용자에게 물어서** 답을 받은 뒤 체크한다.
- 해당 없는 섹션(예: 네트워크 변경이 없는 PR의 Mirror 섹션)은 통째로 지우지 말고 남긴 채 체크하지 않는다. 대신 사용자에게 "이 PR은 네트워크 무관으로 판단했다"고 알린다.
- **네트워크가 걸린 변경이면 3인 접속 테스트(L3)가 필수다.** 안 했으면 체크하지 않고, "남은 것"에 미검증으로 명시한다. 테스트 등급 `M__`은 사용자에게 확인해 채운다.

### 6. 리뷰어와 담당자 지정

**리뷰어를 반드시 지정한다. 생략하면 리뷰 없이 병합된다.**

이 저장소는 private이고 조직이 Free 플랜이라 `.github/CODEOWNERS`의 자동 리뷰어 요청이 **동작하지 않는다**(2026-09-02 확인 — 브랜치 보호·ruleset API도 403, 병합된 PR들의 `reviewRequests`가 전부 비어 있었다). CODEOWNERS 파일이 있으니 알아서 붙겠지라고 가정하지 않는다.

- **리뷰어는 팀장 `AidenKim923`을 기본으로 지정한다.**
- 단 **PR 작성자가 팀장 본인이면 리뷰어를 지정하지 않는다.** `--reviewer`를 빼고 만든다. GitHub이 작성자 자신을 리뷰어로 요청하는 것을 막고, 팀장이 사실상 전 영역의 CODEOWNERS라 대신 넣을 사람을 임의로 고를 이유도 없다. 다른 팀원의 리뷰가 필요하면 사용자가 직접 말할 것이다.
- 작성자 확인은 `gh api user --jq .login`으로 한다. 결과가 `AidenKim923`이면 리뷰어 없이 진행한다.
- **담당자(assignee)는 항상 `@me`로 넣는다.** 리뷰어와 담당자는 다르다 — 담당자는 이 작업을 책임지는 사람, 리뷰어는 봐줄 사람이다.

### 7. 사용자 확인 후 생성

- `gh pr create`를 실행하기 전에 **제목과 본문 전체, 그리고 지정할 리뷰어·담당자를 함께 보여주고 확인받는다.**
- 승인 후 실행한다. base는 `develop`이다.

```bash
# 팀원이 올리는 PR — 리뷰어를 지정한다
gh pr create --base develop --head feature/{이름} \
  --assignee @me --reviewer AidenKim923 \
  --title "..." --body-file {임시파일}

# 팀장(AidenKim923)이 올리는 PR — 리뷰어를 빼고 담당자만 넣는다
gh pr create --base develop --head feature/{이름} \
  --assignee @me \
  --title "..." --body-file {임시파일}
```

- 리뷰어 지정에 실패해도(권한·오타 등) PR 자체는 만들어진다. 실패하면 조용히 넘기지 말고 알린 뒤 `gh pr edit {번호} --add-reviewer {계정}`으로 다시 시도한다.

- 본문은 스크래치패드의 임시 파일로 넘긴다. 저장소 안에 임시 파일을 만들지 않고, 생성 후 남기지 않는다.
- `gh`가 없거나 인증되지 않았으면 본문을 그대로 출력하고, 사용자가 웹에서 붙여넣을 수 있게 안내한다.
- 생성 후 PR URL을 보고한다.

## 하지 않는 것

- 사용자 확인 없이 `gh pr create` 실행
- **팀원 PR을 리뷰어 없이 생성** — CODEOWNERS가 자동으로 붙여줄 거라 가정하기
- 팀장이 작성자인 PR에 리뷰어를 억지로 넣기 (이 경우는 지정하지 않는 것이 정상이다)
- 확인하지 않은 체크리스트 항목 체크
- `main` · `develop`에서 PR 생성
- 템플릿 섹션을 임의로 바꾸거나 빼기
- 이슈 번호·테스트 결과를 추측해서 채우기
- 승인 없이 push
- PR 본문에 `Co-Authored-By`나 AI 생성 표기 넣기

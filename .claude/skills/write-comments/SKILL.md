# 주석 작성

## 언제 발동하나

사용자가 코드에 주석을 달아달라고 요청하면 발동한다. 규칙은 `docs/coding-convention.md` 12장(주석)이 원본이다 — 여기서는 그 규칙을 실제로 적용하는 절차만 다룬다. 두 문서가 어긋나면 `docs/coding-convention.md`가 우선한다.

## 규칙 요약 (원본: docs/coding-convention.md §12)

1. **꼭 필요한 곳에만.** 무엇을 위해 만들었는지(의도·이유)를 적는다 — 코드가 "무엇을 하는지"를 그대로 옮기지 않는다.
2. **코드를 읽어서 알 수 있으면 주석을 달지 않는다.** 변수·함수 이름이 이미 설명하고 있으면 주석은 잉여다.
3. **마침표(`.`)로 끝내지 않는다.** 짧은 구절로 쓴다.
4. **public API는 XML 문서 주석(`<summary>`), 그 외(내부 로직 · private 멤버)는 일반 주석(`//`).** 대상이 public이라고 무조건 summary를 붙이는 게 아니라, 외부에 노출되는 계약을 설명할 때 summary를 쓴다.
5. **남은 작업은 TODO 주석으로 적극 남긴다.** `// TODO(이름): 할 일` 형식으로 담당자를 남긴다.

## 절차

1. 주석을 달 대상 코드를 읽고, 코드 자체가 이미 말하고 있는 것과 실제로 설명이 필요한 부분(왜 이렇게 했는지, 숨은 제약, 다음에 할 일)을 구분한다.
2. 코드가 이미 명확한 곳에는 주석을 추가하지 않는다 — "주석을 달아달라"는 요청이 모든 줄에 주석을 달라는 뜻은 아니다. 필요 없는 곳은 비워두고, 왜 비웠는지 설명하지 않는다(그 설명 자체가 또 하나의 잉여 주석이 된다).
3. 대상이 public API(다른 파트/팀원이 호출하는 메서드·프로퍼티·클래스)면 `<summary>` XML 주석으로, 내부 구현이면 일반 `//` 주석으로 작성한다.
4. 문장 끝에 마침표를 붙이지 않는다.
5. 미완성이거나 후속 작업이 필요한 지점을 발견하면 `// TODO(이름): 내용` 을 남긴다 — 이름은 코드를 작성 중인 사람 기준으로 붙인다. 담당자를 모르면 사용자에게 묻는다.
6. 작성 후 다시 훑어서, "코드를 읽으면 알 수 있는" 주석이 섞이지 않았는지 스스로 점검하고 제거한다.

## 예시

```csharp
// ✅ public API — summary, 마침표 없음, 이유가 아니라 계약을 설명
/// <summary> 피해를 입힌다, 체력이 0이 되면 사망 처리 </summary>
public void TakeDamage(float damage) { }

// ✅ 내부 로직 — 코드만으론 알 수 없는 이유를 짧게
private void ApplyKnockback()
{
    _rb.isKinematic = true; // 넉백 중 물리 끄기
}

// ❌ 코드가 이미 말하는 것을 반복
_health -= damage; // 체력 감소

// ❌ 마침표로 끝남
_rb.isKinematic = true; // 넉백 중 물리 끄기.

// ✅ 남은 작업
// TODO(민성): 서버 재접속 시 스냅샷 복구 처리
```
